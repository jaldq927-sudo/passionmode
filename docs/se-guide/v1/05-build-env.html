開発環境をつくる

JDK・Maven・IDE・Git・ローカルDB・Tomcat がそれぞれ何をしているかを理解し、「設定ファイルにURLを登録する」の意味をはっきりさせます。エラーを1つずつ切り分けて、mvn clean package が通り、ローカルでアプリを起動してデバッグできるところまでを目指します。

この章でわかること
  • 開発環境を構成する道具の役割と、どれがどれに頼っているか
  • Maven が部品（ライブラリ）をどこから、どうやって取ってくるか
  • ~/.m2/settings.xml の mirrors / servers / proxies の書き方と、pom.xml の repositories との違い
  • JAVA_HOME と PATH の設定、社内プロキシと証明書エラー（PKIX）の直し方
  • エラーメッセージから原因を切り分ける手順と、先輩への質問の仕方
なぜつまずくのか全体像環境変数Mavenの仕組みsettings.xmlプロキシと証明書エラー対処表切り分け手順ゴールまで確認リスト練習問題用語チェックリスト

なぜ環境構築でつまずくのか

Maven の環境構築が何か月もできていないと、「自分には向いていないのでは」と感じるかもしれません。でも、社内ネットワークでの環境構築は、ベテランでも半日〜数日かかることがよくある作業です。つまずく理由ははっきりしています。

  • 道具が多く、どれが失敗しているか分からない：JDK、Maven、IDE、プロキシ、社内リポジトリが絡み合い、1つのエラーメッセージに複数の原因が隠れています。
  • 会社固有の値が必要：社内リポジトリのURL、認証情報、プロキシのホスト名は、ネットで検索しても出てきません。知らないのが当たり前で、聞くしかない情報です。
  • 手順書が「分かっている人」向け：「settings.xml にURLを登録してください」の一文に、実は5つくらいの前提知識が詰まっています。

この章では、その前提知識を1つずつほどいていきます。大事なのは「全部いっぺんに直そうとしない」ことです。下から順に、1段ずつ確認すれば必ずどこで止まっているかが分かります。

この章のゴール（3段階）

① mvn clean package が BUILD SUCCESS になる → ② ローカルでアプリが起動する → ③ IDE でブレークポイントを置いてデバッグできる。①までできれば、残りはぐっと楽になります。

全体像：道具とその役割

まず登場人物を整理します。Java の業務アプリ開発を「お店（Webアプリ）を開く」ことにたとえると、次のようになります。

JDK（javac / java）

翻訳機と実行機。javac が Java のソースを機械が読める形（.class）に翻訳し、java がそれを動かす。Maven も Java で動くので、JDK が全ての土台。

Maven

ビルド係 兼 部品の取り寄せ係。pom.xml（注文書）を読み、必要なライブラリを倉庫から取り寄せ、コンパイル・テスト・WAR/JAR作成までを一括で行う。

IDE（Eclipse / IntelliJ / VS Code）

作業机。編集・検索・実行・デバッグを1か所でできる。中では JDK と Maven を呼んでいるだけなので、IDE がどの JDK・どの設定を使っているかが重要。

Git

セーブポイント付きの書類保管庫。ソースの履歴を管理し、社内の Git サーバーからプロジェクトを取ってくる（clone）。

ローカルDB（PostgreSQL）

練習用の台帳。自分のPCに本番と同じ形のDBを作り、壊しても誰にも迷惑がかからない場所でアプリを動かす。

Tomcat

お店の建物。Web アプリを載せて、ブラウザからのリクエストを受け付ける。Spring Boot なら JAR の中に組み込まれていることも（04 起動の流れ）。

この図で大事なのは、ネットワークの壁を越えるのは主に Maven（と Git）だけということです。「Maven がビルドできない」問題の多くは、Java のコードではなく、この壁の越え方（URL・認証・プロキシ・証明書）の問題です。

環境変数：JAVA_HOME と PATH

環境変数は、PC 全体で共有される「メモ書き」です。コマンドを打ったとき、OS は PATH に書かれたフォルダを順番に探してプログラムを見つけます。Maven は JAVA_HOME を見て、どの JDK を使うか決めます。

たとえ話受付で「山田さんを呼んで」と言うと、受付係は館内の座席表（PATH）を上から順に見て探す。座席表に載っていなければ「そんな人はいません」と言われる。
＝
実際にはmvn と打つと、OS は PATH のフォルダを順に探す。Maven の bin が PATH に無ければ「'mvn' は認識されていません」になる。
変数中身（例）ポイント
JAVA_HOMEC:\Program Files\Java\jdk-17JDK のフォルダそのもの。末尾に \bin を付けない。JRE ではなく JDK を指す
MAVEN_HOME / M2_HOMEC:\tools\apache-maven-3.9.xMaven を展開したフォルダ。今の Maven（3.5以降）は必須ではないが、手順書で求められたら設定する
PATH%JAVA_HOME%\bin と %MAVEN_HOME%\bin を追加ここには bin まで書く。古い Java が先に書かれていると、そちらが使われる

Windows での設定手順

  1. JDK と Maven を用意するJDK は社内指定のバージョン（例：17）をインストール。Maven は公式サイトの apache-maven-3.9.x-bin.zip を展開し、スペースを含まないフォルダ（例：C:\tools\）に置く。バージョンは社内の指定に合わせます。
  2. 環境変数の画面を開くスタートメニューで「環境変数」と検索 →「システム環境変数の編集」（または「アカウントの環境変数を編集」）→「環境変数」ボタン。
  3. JAVA_HOME を新規作成「新規」で変数名 JAVA_HOME、値に JDK のフォルダを入力（エクスプローラーでフォルダを開き、アドレスバーからコピーすると確実）。
  4. MAVEN_HOME を新規作成（任意）変数名 MAVEN_HOME、値に Maven のフォルダ。
  5. PATH を編集Path を選んで「編集」→「新規」で %JAVA_HOME%\bin と %MAVEN_HOME%\bin を追加。古い Java のパスがあれば、「上へ」で新しい方を上にする。
  6. コマンドプロンプトを開き直す環境変数は、開いていたウィンドウには反映されません。IDE も再起動します。
setx コマンドに注意

ネットの記事にある setx PATH "%PATH%;..." は、長い PATH を1024文字で切り捨ててしまうことがあります。PATH は画面から編集する方が安全です。

Mac / Linux の場合

~/.zshrc（Mac）または ~/.bashrc（Linux）に追記する例
# Mac：インストール済みの JDK 17 の場所を自動で取得
export JAVA_HOME=$(/usr/libexec/java_home -v 17)
# Linux：実際のインストール先に合わせる（例）
# export JAVA_HOME=/usr/lib/jvm/java-17-openjdk
export MAVEN_HOME=$HOME/tools/apache-maven-3.9.x
export PATH=$JAVA_HOME/bin:$MAVEN_HOME/bin:$PATH

保存したら source ~/.zshrc を実行するか、ターミナルを開き直します。

確認コマンド

> java -version
openjdk version "17.0.x" ...
> javac -version
javac 17.0.x
> mvn -v
Apache Maven 3.9.x
Maven home: C:\tools\apache-maven-3.9.x
Java version: 17.0.x, vendor: ..., runtime: C:\Program Files\Java\jdk-17
> echo %JAVA_HOME%        （PowerShell なら  $env:JAVA_HOME ／ Mac なら echo $JAVA_HOME）
> where java              （Mac / Linux なら which java）

mvn -v の「Java version」と「runtime」の行が、使いたい JDK になっているかを必ず見ます。java -version は 17 なのに Maven は 8 を使っている、ということがよくあります。javac -version が動かない場合は、JDK ではなく JRE を指している可能性があります。

Maven の仕組み：部品はどこから来るのか

pom.xml には「Spring Boot の Web 部品を使う」「PostgreSQL のドライバを使う」といった注文（依存関係）が書かれています。Maven はこれを読み、部品（JAR ファイル）を次の順番で探します。

3種類のリポジトリ

ローカルリポジトリ
自分のPCの ~/.m2/repository（Windows なら C:\Users\ユーザー名\.m2\repository）。一度取得した部品がここに貯まる。中は org/springframework/boot/… のようにフォルダ分けされている。
Maven Central
世界中のオープンソース部品が置かれた公式の倉庫（https://repo.maven.apache.org/maven2/）。何も設定しなければ Maven はここに行く。
社内リポジトリ
Nexus や Artifactory という製品で会社が立てた倉庫。Central の中継（キャッシュ）と、社内で作った部品（共通ライブラリなど）の置き場を兼ねることが多い。認証が必要なことが多い。

社内ネットワークでは、PC から Central へ直接は出られず、社内リポジトリを経由するよう決められていることがよくあります。これが「社内リポジトリのURLを設定ファイルに登録してください」と言われる理由です。

「URLを設定ファイルに登録する」とは：settings.xml

「設定ファイル」とは、ほとんどの場合 Maven のユーザー設定ファイル settings.xml のことです。置き場所は次のとおりです。

OS場所
WindowsC:\Users\ユーザー名\.m2\settings.xml
Mac / Linux~/.m2/settings.xml（/Users/ユーザー名/.m2/ や /home/ユーザー名/.m2/）

最初は存在しないので、自分で作ります。.m2 フォルダが無ければ一度 mvn -v 以外の Maven コマンドを実行するか、手で作成します（Windows のエクスプローラーで「.m2」というフォルダ名は作れない場合があるので、コマンドプロンプトで mkdir %USERPROFILE%\.m2 とします）。Maven 本体の conf\settings.xml にもひな形がありますが、自分用の設定はユーザー側に書くのが基本です。

settings.xml の実例

注意：以下の URL・ホスト名・ID はすべてダミーです

nexus.example.co.jp や proxy.example.co.jp は説明用の架空の値です。実際の値は社内Wikiや先輩に確認してください。

~/.m2/settings.xml（一般的な例）
<?xml version="1.0" encoding="UTF-8"?>
<settings xmlns="http://maven.apache.org/SETTINGS/1.0.0"
          xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
          xsi:schemaLocation="http://maven.apache.org/SETTINGS/1.0.0 https://maven.apache.org/xsd/settings-1.0.0.xsd">

  <!-- (1) mirrors：本来の行き先（Central など）の代わりに、社内Nexusへ向ける -->
  <mirrors>
    <mirror>
      <id>company-nexus</id>
      <name>社内Nexus（ダミー）</name>
      <url>https://nexus.example.co.jp/repository/maven-public/</url>
      <mirrorOf>*</mirrorOf>   <!-- * = すべてのリポジトリへの要求をここに回す -->
    </mirror>
  </mirrors>

  <!-- (2) servers：その行き先に入るための ID とパスワード -->
  <servers>
    <server>
      <id>company-nexus</id>          <!-- mirror の id と完全に同じにする -->
      <username>yamada.taro</username>
      <password>ここにパスワード</password>
    </server>
  </servers>

  <!-- (3) proxies：社内から外に出るための門 -->
  <proxies>
    <proxy>
      <id>corp-proxy</id>
      <active>true</active>
      <protocol>http</protocol>
      <host>proxy.example.co.jp</host>
      <port>8080</port>
      <username>yamada.taro</username>     <!-- 認証付きプロキシの場合のみ -->
      <password>ここにパスワード</password>
      <nonProxyHosts>localhost|*.example.co.jp</nonProxyHosts>
    </proxy>
  </proxies>
</settings>

3つの要素を言葉で説明すると

要素役割たとえ
<mirrors>「Central（や pom に書かれた倉庫）に行く代わりに、この URL に行って」という振り替え。<mirrorOf>*</mirrorOf> で全部を、central なら Central 宛てだけを振り替える「本店ではなく、社内の取次窓口に注文して」
<servers>リポジトリに入るための認証情報。<id> で、mirror や repository の <id> と結びつく取次窓口の入館証
<proxies>社内ネットワークから外へ出るための中継サーバー。<nonProxyHosts> は「門を通らず直接行く宛先」を | 区切りで書く会社の正門。守衛さんに名乗って出る
一番多いミス：id の不一致

<server> の <id> と <mirror> の <id> が1文字でも違うと、Maven は認証情報を送らず、401 Unauthorized になります。大文字・小文字、ハイフンとアンダースコアの違いも区別されます。

  • 社内Nexusがプロキシの内側（社内）にあるなら、<nonProxyHosts> に社内のホストを入れないと、わざわざ外の門を通ろうとして失敗することがあります。
  • プロキシの <protocol> の扱いで、https の通信に効かないケースがあります。社内手順で <protocol>https</protocol> の proxy をもう1つ追加するよう指示されていれば、それに従います。
  • パスワードを平文で置きたくない場合、Maven にはパスワード暗号化の仕組み（mvn --encrypt-password と settings-security.xml）があります。社内ルールを確認してください。
  • XML なので、1つでもタグが閉じていないと全体が読めません。mvn help:effective-settings を実行すると、Maven が実際に読み込んだ設定が表示されるので（パスワードは伏せ字）、読めているかの確認に使えます。

pom.xml の repositories との違い

pom.xml にも <repositories> という似た設定があり、混乱のもとになります。

pom.xml の <repositories>

プロジェクトの設定。Git で全員に共有される。「この部品は Central ではなく、この倉庫にあるよ」とプロジェクトとして宣言する。パスワードは書かない（全員に見えてしまう）。

settings.xml

あなたのPCだけの設定。共有しない。認証情報・プロキシ・mirror のように、人や場所によって違う値を書く。mirrorOf が * なら、pom の repositories への要求も mirror に振り替えられる。

pom.xml 側の例（社内の共通部品を置く倉庫を宣言）
<repositories>
  <repository>
    <id>company-releases</id>   <!-- 認証が要るなら settings.xml の server id をこれに合わせる -->
    <url>https://nexus.example.co.jp/repository/maven-releases/</url>
  </repository>
</repositories>

IDE にも settings.xml の場所を教える

IDE は独自に Maven を内蔵していることがあり、コマンドでは成功するのに IDE では失敗する、ということが起こります。

  • Eclipse：ウィンドウ ＞ 設定 ＞ Maven ＞ ユーザー設定（User Settings）で settings.xml を指定。プロキシは 一般 ＞ ネットワーク接続。
  • IntelliJ IDEA：Settings ＞ Build, Execution, Deployment ＞ Build Tools ＞ Maven の「User settings file」と「Maven home path」。プロキシは Appearance & Behavior ＞ System Settings ＞ HTTP Proxy。
  • VS Code：Java 拡張の設定 java.configuration.maven.userSettings で指定。

メニュー名は IDE のバージョンや日本語化の有無で少し異なります。

mvnw があるプロジェクト

プロジェクト直下に mvnw / mvnw.cmd（Maven Wrapper）があれば、mvnw.cmd clean package のように使うと、プロジェクト指定の Maven が自動でダウンロードされます。ただし、そのダウンロードにも settings.xml のプロキシ・mirror 設定や、場合によっては .mvn/wrapper/maven-wrapper.properties の URL 変更が必要になることがあります。

社内プロキシと証明書エラー（PKIX）

プロキシは道具ごとに設定する

プロキシ設定は「PCに1回」ではなく、道具ごとに別々です。Maven が通っても Git が通らない、ということがよくあります。

# Maven：settings.xml の <proxies>（前の節）

# Git：グローバル設定に登録（値はダミー）
git config --global http.proxy http://proxy.example.co.jp:8080
git config --global https.proxy http://proxy.example.co.jp:8080
# 確認と解除
git config --global --get http.proxy
git config --global --unset http.proxy

# IDE：それぞれのプロキシ設定画面（前の節）

認証付きプロキシで URL に ユーザー名:パスワード@ を埋め込む方法もありますが、記号を含むパスワードは URL エンコードが必要で、設定ファイルに平文で残ります。社内の推奨方法を確認しましょう。

PKIX path building failed とは

HTTPS では、接続先が「本物か」を証明書で確認します。Java は、JDK の中にある cacerts という信頼する発行元の一覧と照らし合わせます。社内プロキシが通信の中身を検査するために、社内の認証局（社内CA）で証明書を発行し直していると、Java の一覧にはその社内CAが載っていないため「信頼できる経路が作れない」と判断して接続を拒否します。これが PKIX エラーです。

社内Nexus 自体が社内CAの証明書を使っている場合も、同じエラーになります。

対処：社内CA証明書を cacerts に登録する

  1. 社内CA証明書のファイルをもらう情報システム部門や社内Wikiで配布されていることが多いです（例：corp-root-ca.cer）。自分でブラウザから書き出す方法もありますが、どれが正しいルート証明書かは社内に確認するのが確実です。
  2. 管理者権限でコマンドプロンプトを開くC:\Program Files の下の JDK を書き換えるため、管理者として実行が必要です。
  3. keytool で登録する下のコマンドを実行します。cacerts の初期パスワードは一般に changeit です。
  4. 登録を確認し、ビルドをやり直す-list で別名（alias）が表示されれば成功です。
# JDK 9 以降（-cacerts で JDK 付属の cacerts を指定できる）
keytool -importcert -cacerts -alias corp-root-ca -file C:\certs\corp-root-ca.cer -storepass changeit

# ファイルの場所を直接指定する書き方（JDK 9 以降は lib\security\cacerts）
keytool -importcert -alias corp-root-ca -file C:\certs\corp-root-ca.cer ^
  -keystore "%JAVA_HOME%\lib\security\cacerts" -storepass changeit
# JDK 8 の場合は "%JAVA_HOME%\jre\lib\security\cacerts"

# 確認
keytool -list -cacerts -alias corp-root-ca -storepass changeit
JDK が複数あると、別の JDK に登録してしまう

cacerts は JDK ごとに別ファイルです。mvn -v の runtime に表示された JDK に登録します。IDE が内蔵の JDK で Maven を動かしている場合は、IDE の JDK にも登録するか、IDE の設定で使う JDK を揃えます。JDK を入れ替えたら登録し直しが必要です。

Git でも証明書エラー（SSL certificate problem: unable to get local issuer certificate）が出ることがあります。Windows の Git なら git config --global http.sslBackend schannel で Windows の証明書ストアを使う方法が一般的です。社内の推奨設定を確認してください。

よくあるエラーと対処

エラーメッセージは「どこで止まったか」を教えてくれる手がかりです。全文をよく読み、下の表から近いものを探してください（表記は Maven や OS のバージョンで少し違います）。

The JAVA_HOME environment variable is not defined correctlyMaven が使う JDK が見つからないJAVA_HOME 未設定、末尾に \bin が付いている、JRE を指している、存在しないフォルダecho %JAVA_HOME% の結果をエクスプローラーで開けるか、その下に bin\javac.exe があるか確認
Could not resolve dependencies for project com.example:kintai:war:1.0.0必要な部品が揃わなかったこの下に本当の理由（401、PKIX、timeout など）が続くことが多い。または指定した部品がリポジトリに存在しないメッセージの続きと Caused by を読む。社内専用部品ならリポジトリの URL と権限を確認

… 403, reason phrase: Forbidden (403)認証はできたが権限がないアカウントにそのリポジトリの閲覧権限がない、URL が別のリポジトリを指しているURL を確認し、管理者に権限付与を依頼
… 407, reason phrase: Proxy Authentication Required (407)プロキシに認証で拒否されたproxies に username/password が無い・誤りsettings.xml の proxy 認証を確認。IDE・Git 側も同様に
PKIX path building failed: … unable to find valid certification path to requested target接続先の証明書を信頼できない社内CA証明書が、Maven を動かしている JDK の cacerts に無い前の節の keytool で登録。mvn -v の JDK に入れたか確認
Fatal error compiling: invalid target release: 11指定された Java バージョンでコンパイルできないpom.xml は Java 11 以上を要求しているのに、Maven が JDK 8 で動いている（17 なら release version 17 not supported などと出る）mvn -v の Java version を確認し、JAVA_HOME を正しい JDK に変更
Connect to repo.maven.apache.org:443 … failed: Connection timed out相手に届かないプロキシ未設定で直接外へ出ようとしている、mirror 未設定で Central に行っている、VPN 未接続エラーに出ているホスト名を見る。Central なら mirror 設定を、社内ホストなら nonProxyHosts を確認
エラーの「行き先」を必ず見る

多くのエラーには、どの URL に接続しようとしたかが書かれています。repo.maven.apache.org が出ていれば「mirror が効いておらず Central に直接行っている」、nexus.example.co.jp のような社内ホストなら「mirror は効いているが、その先で失敗している」と分かります。

トラブルシュートの手順

あれこれ同時に変えると、何が効いたのか分からなくなります。1回に1か所だけ変えて、毎回同じコマンドで確かめるのが鉄則です。変えたことはメモに残します。

  1. 土台を確認するjava -version、javac -version、mvn -v。Maven が使う JDK が想定どおりかを見る。ここが通らなければ先に進まない。
  2. 設定が読まれているか確認するmvn help:effective-settings で mirror・server・proxy が表示されるか。表示されなければ、ファイルの場所か XML の書き方が間違っている。
  3. 依存関係だけを取得してみるmvn dependency:resolve。コンパイルと切り離して「部品の取り寄せ」だけを試せる。
  4. 詳細ログを出すmvn -X clean package > build.log 2>&1 でデバッグログをファイルに保存。「Using mirror」「proxy」「Downloading from」の行で、実際の接続先とプロキシ使用の有無が分かる。
  5. 失敗の記録を消して再試行する一度失敗すると Maven はそれを覚えて、しばらく再試行しません（was cached in the local repository, resolution will not be reattempted until the update interval … has elapsed or updates are forced）。mvn -U clean package の -U で強制的に再確認させる。
  6. 壊れたファイルを削除するローカルリポジトリに残った *.lastUpdated ファイルや、途中までしかダウンロードされていない JAR を消す。該当フォルダ（例：~/.m2/repository/org/springframework/boot/）ごと消しても、次回のビルドで取り直されるので問題ありません。
  7. それでもだめなら質問するここまでの結果を持って、質問テンプレで先輩に聞く。
# よく使うコマンドまとめ
mvn -v                              # Maven と JDK のバージョン
mvn help:effective-settings         # 実際に効いている settings.xml
mvn dependency:resolve              # 依存関係の取得だけ
mvn -U clean package                # 失敗キャッシュを無視して再取得
mvn -X clean package > build.log 2>&1   # デバッグログを保存
mvn clean package -DskipTests       # テストを飛ばして固める（原因切り分け用）

-DskipTests はテストの失敗とビルド環境の問題を切り分けるためのものです。常用せず、テストが落ちる理由はチームに確認しましょう。

-X ログで見るべき行（一般的な形）
[DEBUG] Reading user settings from C:\Users\yamada\.m2\settings.xml
[DEBUG] Using mirror company-nexus (https://nexus.example.co.jp/repository/maven-public/) for central (https://repo.maven.apache.org/maven2).
[DEBUG] Using transporter ... with priority ... for https://nexus.example.co.jp/...
[INFO] Downloading from company-nexus: https://nexus.example.co.jp/repository/maven-public/org/...

1行目で「どの settings.xml を読んだか」、2行目で「mirror が効いているか」が確認できます。1行目のパスが想定と違えば、別の場所のファイルを編集していたということです。

ゴールまでの3段階

① ビルドが通るmvn clean package で BUILD SUCCESS。target/ に WAR か JAR ができる
② ローカルで起動ローカルDBにつながり、ブラウザで画面が開く
③ デバッグできるIDEでブレークポイントを置き、変数の中身を見られる

① mvn clean package

clean は前回の成果物（target フォルダ）を消し、package はコンパイル → テスト → WAR/JAR 作成までを行います。最後に [INFO] BUILD SUCCESS と出れば成功です。

② ローカルDBを用意して起動する

PostgreSQL をインストールし、アプリ用の DB とユーザーを作ります。テーブル作成用の SQL（DDL）や初期データがリポジトリ内にあるか、どう作るのかは現場ごとに違うので確認が必要です。

# 一般的な例（DB名・ユーザー名はダミー）
psql -U postgres
postgres=# CREATE USER kintai_app WITH PASSWORD 'devpass';
postgres=# CREATE DATABASE kintai OWNER kintai_app;
postgres=# \q
psql -U kintai_app -d kintai -f db/ddl/create_tables.sql

接続先はアプリの application-local.properties などに書きます（04 設定ファイル）。起動方法は構成によって違います。

  • JAR（組み込みTomcat）：IDE で @SpringBootApplication の付いたクラスを右クリックして実行、または mvn spring-boot:run。
  • WAR（外部Tomcat）：ローカルに Tomcat を入れ、Eclipse の「サーバー」ビューや IntelliJ（Ultimate）の Tomcat 実行構成で WAR を載せて起動。または target/*.war を Tomcat の webapps にコピー。

③ ブレークポイントでデバッグ

IDE の「デバッグ」で起動し、Controller のメソッドの行番号の左をクリックして赤い丸（ブレークポイント）を置きます。ブラウザで打刻ボタンを押すとそこで処理が止まり、変数の中身を見ながら1行ずつ進められます（ステップオーバー：Eclipse は F6、IntelliJ は F8）。外部Tomcat の場合は、Tomcat を catalina.bat jpda start で起動し（既定ではポート 8000 で待ち受け）、IDE の「リモート Java アプリケーション」（IntelliJ は Remote JVM Debug）で接続する方法もあります。

デバッグができると世界が変わる

ログを読んで推測するしかなかった処理が、目の前で1行ずつ動くのを見られます。AIの回答が正しいかも、自分で確かめられるようになります。ここまで来たら、07 ログと障害調査 の内容が一気に身近になります。

練習問題

Q1. JAVA_HOME に C:\Program Files\Java\jdk-17\bin と設定しました。何が問題ですか？

JAVA_HOME は JDK のフォルダそのもの（C:\Program Files\Java\jdk-17）を指します。\bin まで書くのは PATH の方です。Maven は %JAVA_HOME%\bin\java を探すので、bin\bin\java を探すことになり失敗します。

Q2. エラーに https://repo.maven.apache.org/maven2 への接続タイムアウトが出ています。社内では Nexus 経由のルールです。まず何を疑いますか？

mirror が効いていない（settings.xml が読まれていない、場所が違う、mirrorOf の指定が違う）ことを疑います。mvn help:effective-settings や mvn -X の「Reading user settings from」「Using mirror」の行で確認します。

Q3. 401 と 407 の違いを説明してください。

401 は接続先（社内Nexus など）での認証失敗で、settings.xml の <servers> を確認します。407 は途中のプロキシでの認証失敗で、<proxies> の username/password を確認します。

Q4. keytool で社内CA証明書を登録したのに PKIX エラーが消えません。考えられる原因は？

Maven（または IDE）が、登録したのとは別の JDK で動いている可能性が高いです。mvn -v の runtime を確認し、その JDK の cacerts に登録します。IDE 内蔵の JDK や、JDK の入れ替えにも注意します。
