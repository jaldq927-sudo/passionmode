CHAPTER 09 ・ 仕事の進め方

要望から改修まで

「深夜残業を別集計したい」のような顧客要望を、聞き返し・影響調査・方式比較・テストを経て、安全な改修にする流れを身につける章です。AIの改修案を自分で検証する観点もまとめます。

この章でわかること
  • 要望を受けてからリリース後の確認までの全体の流れ
  • 要望をそのまま作らず、目的・背景・期限を聞き返す方法
  • 画面からテーブルまでを追う影響調査のやり方と、漏れを防ぐチェックリスト
  • 勤怠ならではの注意点（締め済み月、法令、端数処理、日またぎなど）
  • 方式比較表とテスト観点表のテンプレート
  • AIに改修案を作らせたとき、自分で確認すべきポイント
なぜ流れが大事かたとえ話全体の流れ要望の聞き返し影響調査方式比較と見積テスト観点AIの改修案つまずき練習問題用語明日から

なぜ「流れ」を知ることが大事なのか

顧客から「通勤費申請に経路の添付を必須にしたい」と言われたとします。XMLの required="false" を true にすれば終わりに見えます。でも実際には、次のような疑問が残ります。

  • すでに添付なしで出されて、差戻し中の申請はどうなるのか
  • 「必須」は新規申請だけか、変更申請も含むか
  • 徒歩通勤のように添付が用意できない人は例外にするのか
  • いつから適用するのか。社員への周知は誰がするのか

改修で事故が起きるのは、たいていコードの書き間違いより「確認しなかったこと」が原因です。逆に言えば、決まった流れに沿って確認していけば、経験が浅くても事故はかなり防げます。

いまはAIに聞けば改修案は出てきます。でも、その案が「顧客の本当の目的に合っているか」「他の機能を壊さないか」を判断するのは、あなたの仕事です。この章の流れは、その判断の土台になります。

たとえ話：改修は「家のリフォーム」

リフォーム「キッチンを広くしたい」と言われたら、まず「料理を家族でしたいのか、収納が足りないのか」を聞く。壁を壊す前に、その壁に柱や配管が通っていないか調べる。複数のプランと見積を出し、工事後に水漏れがないか確かめる。
＝
システム改修要望の目的を聞き返し、変更箇所を通る処理（バッチ・帳票・連携）を調べる。方式を比較して見積り、実装後は既存機能が壊れていないか回帰テストで確かめる。

リフォーム業者がいきなり壁を壊したら怖いですよね。システムでも同じで、「とりあえず直す」はいちばん危険です。壁の中の配管にあたるのが、同じテーブルを使っている別の処理です。

全体の流れ：要望からリリース後の確認まで

図1 要望確認からリリース後の確認までの10ステップ

前半の5ステップ（考える）は、手を動かしていないので進んでいないように感じます。でも、ここを飛ばすと後で「作り直し」になり、結果的に一番時間がかかります。目安として、小さな改修でも全体の3〜4割の時間を前半に使うつもりでいてください。

小さな改修でも流れは同じ

ラベル1文字の修正なら、各ステップは数分で終わります。それでも「影響はないか」「確認したか」を一度は通る。この習慣が、大きな改修のときに自分を守ってくれます。

要望の聞き返し：作る前に確かめること

要望は「解決策」の形で届くことが多いです。「深夜残業を別集計したい」の裏には、「深夜割増の支給額を給与担当がExcelで手計算していて大変」という本当の困りごとがあるかもしれません。それが分かれば、別集計の列を足すのか、給与連携CSVに項目を足すのが良いのか、選択肢が変わります。

基本の聞き返しリスト

観点質問例なぜ聞くか
目的この集計は何に使いますか？誰が見ますか？目的が分かれば、より簡単な方法が見つかることがある
背景今はどうやって対応していますか？現状の手作業が、要件の正解を教えてくれる
いつから何月分から適用しますか？期限は？締め処理・給与支給日との関係で期限が決まる
誰が全社員ですか？特定の雇用区分だけですか？パート・管理職・派遣で扱いが違うことが多い
何件対象は何人・月何件くらいですか？性能やバッチ時間に影響する
過去データ過去分もさかのぼって出しますか？データ移行・再計算が必要かが変わる
例外当てはまらないケースはありますか？徒歩通勤、休職中、月途中入社など
完了の基準どうなっていれば「できた」と言えますか？受け入れテストの基準になる

勤怠特有の観点

締め済み月

締め処理が終わった月のデータを変えるか。給与計算済みなら再計算・差額精算が必要になる。

法令

深夜（22時〜翌5時）割増、時間外労働の上限、年5日の有給取得義務など。法令の解釈は顧客の人事・社労士に確認する。

就業規則

会社ごとに所定労働時間、休憩、時間単位有給の上限などが違う。規則のどの条文に基づくかを聞く。

端数処理

1分単位か、15分・30分単位か。切り捨て・切り上げ・四捨五入か。日ごとか月合計でか。

日またぎ

22:00〜翌3:00の勤務はどちらの日に計上するか。勤務日基準か暦日基準か。

休日

法定休日と所定休日の区別、振替休日・代休、祝日の扱い。

異動・入退社

月途中で所属や勤務体系が変わる人。集計の所属はどちらか、承認者は誰か。

シフト・変形労働

変形労働時間制やフレックスの人は、残業の判定基準が通常と違う。

聞き返しのコツ

「質問が多くてすみません」と遠慮しなくて大丈夫です。むしろ「作ってから違った」が一番迷惑をかけます。質問は箇条書きにして、自分の推測を添えると答えやすくなります。例：「過去データは対象外（来月分から）という理解でよろしいでしょうか」。伝え方は11 伝える技術でも扱います。

例：「有給の半日単位を時間単位に」を聞き返す

  • 半日単位は廃止しますか？併用しますか？
  • 1日は何時間として換算しますか？（所定労働時間が人によって違う場合は？）
  • 年間の時間単位取得の上限は何日分ですか？（法令上は年5日分が上限。就業規則の規定も確認）
  • 残日数の表示は「日＋時間」ですか？
  • 申請画面・承認・残数計算・給与連携・有給管理簿のどこまで変えますか？
  • 年度途中から始める場合、すでに取った半日休はどう換算しますか？

影響調査：変更がどこまで波及するかを追う

影響調査は「この変更で、他に変わってしまうところはないか」を探す作業です。基本は画面からテーブルまで縦に追い、次にテーブルから他の利用者を横に探すの2方向です。

図2 縦に追う調査（変更の入口から）と横に探す調査（同じデータを使う他の処理）

Spring Bootのアプリで画面からControllerへ、ControllerからServiceへどうつながるかは04 Spring Bootの正体、全体の配置は02 システムの全体像を見てください。

grepで探す：名前を手がかりにする

影響調査のいちばん強い武器は「名前で全文検索」です。テーブル名、カラム名、画面項目名、帳票名など、変更に関係する名前を全部のソース・XML・SQL・設定ファイルから探します。

# 深夜残業に関係しそうな名前を探す（例：カラム名 late_night_minutes）
grep -rn "late_night_minutes" src/ resources/ batch/ forms/

# 大文字小文字を区別しない（SQLは大文字で書かれていることもある）
grep -rni "t_attendance_daily" .

# Javaのフィールド名はキャメルケースになっていることが多い
grep -rn "lateNightMinutes" src/

# ファイル名だけ一覧にする
grep -rli "commute_allowance" . | sort
名前の「表記ゆれ」に注意

DBでは late_night_minutes、Javaでは lateNightMinutes、画面では「深夜時間」、CSVでは「深夜残業」、帳票では略して「深夜」。1つの概念に複数の名前があるので、全部の表記で検索します。VS Codeの「フォルダーを指定して検索」（Ctrl+Shift+F）も使えます。

呼び出し元を確認する

変更するメソッドが見つかったら、「このメソッドを誰が呼んでいるか」を確認します。IntelliJなら「Call Hierarchy（呼び出し階層）」、Eclipseなら「呼び出し階層を開く」、VS CodeのJava拡張なら「すべての参照を検索」で一覧が出ます。共通ユーティリティ（例：TimeUtil.roundMinutes()）を変えると、思いもよらない画面やバッチに影響することがあります。

漏らさないためのチェックリスト

影響調査の結果は「影響あり／なし／要確認」の3つに分けて表にすると、レビューで伝わりやすくなります。「なし」と書くときは、なぜなしと言えるか（例：grepで該当なし、該当カラムを参照していない）も一言添えます。

方式検討と見積：案は必ず2つ以上出す

やり方が1つしか思いつかないときは、まだ調査が足りないことが多いです。「深夜残業を別集計したい」なら、例えば次のような案が考えられます。

観点案A：日次テーブルに列追加案B：集計時に計算案C：CSV出力だけ追加
概要打刻確定時に深夜時間を計算して保存帳票・CSV出力のSQLで打刻から計算給与担当向けのCSVに深夜列を追加
改修範囲DB・計算処理・バッチ・画面集計SQLのみCSV出力処理のみ
過去データ再計算バッチが必要自動で過去分も出る自動で過去分も出る
性能集計は速い件数が多いと遅くなる出力時のみ計算
リスク計算処理を触るため影響大計算ロジックが2か所に分散画面では見られない
工数（例）大中小
目的への適合◎ 画面・帳票すべてで使える○△ 給与担当の手計算解消のみ

※ 工数・評価は説明用の例です。実際は現状のつくりによって変わります。

比較表は「おすすめはどれか」を書いて終わりにします。決めるのは顧客や上司ですが、判断材料をそろえて推奨を述べるのがSEの役割です。

方式比較表のテンプレ

【要望】       （顧客の言葉のまま）
【目的】       （聞き返して分かった本当の困りごと）
【案A / 案B / 案C】
  概要 / 改修範囲 / 過去データ / 性能 / リスク / 工数 / 目的への適合
【推奨】       案○。理由：……
【未確定事項】  （顧客に確認中のこと）

見積のコツ

  • 作業を細かく分ける（調査・設計・実装・テスト・リリース準備・本番確認）。
  • テストは実装と同じくらいかかることが多い。回帰テストを忘れない。
  • 分からない部分は「要調査：+○日」と別に書く。全部まとめて丸めない。
  • レビュー待ち・顧客確認待ちの時間も期間に入れる。

設計書に書くこと（最低限）

変更の目的、変更箇所の一覧（ファイル・メソッド・SQL・テーブル）、変更前後の動き、影響調査の結果、テスト方針、リリース手順と戻し方。半年後の自分が読んで分かることを基準にします。

テスト：単体・結合・回帰と、勤怠の境界値

単体テストメソッドやSQL単位で、計算が正しいか
結合テスト画面→保存→バッチ→帳票まで通して正しいか
回帰テスト変更していない既存機能が壊れていないか

新しく作った部分のテストは誰でもやります。差が出るのは回帰テストです。影響調査で「影響あり」「要確認」にしたものは、すべて回帰テストの対象にします。

回帰テストの簡単なやり方

テスト環境で、改修前と改修後に同じ月の帳票やCSVを出力し、WinMergeや diff で比べます。「変わってほしい列だけが変わっている」ことを確認できれば、強い証拠になります。

リリースでは、手順書に「戻し方（ロールバック）」も書きます。DB列追加なら列を消す手順、XMLなら前のファイルに戻す手順です。リリース後は本番で、少なくとも1件、実データで期待どおりかを確認して完了です。

AIに改修案を作らせるときに、自分で確認すること

AIは改修案をすばやく出してくれますが、あなたのシステムの全体を知っているわけではありません。見せたコードの範囲でしか判断できず、見せていないバッチや帳票への影響は考慮されません。

そのまま使う

「深夜残業を別集計するコードを書いて」→ 出てきたコードを貼り付け → 画面で1回動いたのでOK。

検証して使う

案を受け取ったら「どのファイルのどこを変えるか」「なぜそこか」「他に影響する場所は」「どうテストするか」を自分で確かめてから採用する。

確認ポイント

影響調査を手伝ってもらうプロンプト例

次のメソッドを変更して、深夜時間（22時〜翌5時）を別に集計したいです。
（コードを貼る。社員番号や顧客名は伏せる）

1. 変更が必要な箇所と、その理由を教えてください。
2. このメソッドを変更したとき、影響を受けそうな処理の種類を挙げてください。
   私が grep で確認すべきキーワードも提案してください。
3. 境界値を含むテストケースを表にしてください。
4. あなたが前提として仮定したことを列挙してください。

4番の「仮定を列挙して」は特に役立ちます。AIの仮定が自社の仕様と違えば、そこが事故の芽です。AIとの付き合い方は10 AIと一緒に強くなるで詳しく扱います。

よくあるつまずき

つまずき

要望の文言どおりに作ったら「そういう意味じゃない」と言われた。

対策

作る前に「目的」と「完了の基準」を文章で確認し、返事をもらっておく。

つまずき

画面は直したが、月次の帳票だけ古い計算のままだった。

対策

テーブル名・カラム名でgrepし、帳票・バッチ・CSVの利用箇所を全部書き出す。

つまずき

テスト環境では問題なかったのに、本番で締め済み月のデータが変わった。

対策

締め済み月を観点表に必ず入れる。更新系の処理は対象期間の条件を確認する。

つまずき

見積が実装だけで、テストとリリース準備の時間が足りなくなった。

対策

作業を分解して見積る。テストは実装と同程度を見込む。

練習問題

Q1. 「通勤費申請に経路の添付を必須にしたい」と言われました。作る前に聞き返す質問を3つ挙げてください。

例：①いつ申請された分から必須にしますか（差戻し中の申請も含みますか）②徒歩・自転車など添付が用意できない人は例外にしますか ③添付の形式（PDF・画像）やサイズに制限はありますか。ほかに「変更申請も対象か」「目的は不正防止か、確認作業の効率化か」なども良い質問です。

Q2. 共通メソッド TimeUtil.roundMinutes() の端数処理を変えたい。最初にやるべきことは？

呼び出し元をすべて洗い出すことです（IDEの呼び出し階層、grep）。共通メソッドは残業計算・有給・帳票など多くの処理から使われている可能性があり、1か所の要望のために全体の計算が変わってしまうことがあります。影響が広いなら、新しいメソッドを作る案も比較します。

Q3. 深夜時間集計のテストで、境界値として必ず入れるべき時刻を4つ挙げてください。

21:59・22:00（深夜の開始）、4:59・5:00（深夜の終了）。加えて0:00（日またぎ）、月末・締め日・2月29日をまたぐケースも入れると安心です。

Q4. AIの改修案に「t_overtime テーブルの night_min 列を更新」とありました。採用前に確認することは？

そのテーブル・列が実在するかをDBやgrepで確認します。AIは「ありそうな名前」を作ることがあります。実在する場合も、その列を読んでいる他の処理（帳票・バッチ・連携）を調べます。
