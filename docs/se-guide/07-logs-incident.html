ログと障害調査

ログをAIに丸ごと渡して答えをもらう、から一歩進んで、「どのログを・どの順で・何を探すか」を自分で決められるようになる章です。スタックトレースの読み方、典型的な障害パターン、調査の手順とコマンドをまとめます。

この章でわかること
  • Apache・Tomcat・アプリ・PostgreSQLのログがどこにあり、それぞれ何が分かるか
  • ログ1行・アクセスログ1行の読み方
  • スタックトレースのどこを見れば根本原因にたどり着けるか
  • メモリ不足・コネクション枯渇・ロック待ちなど典型的な障害の「症状→証拠→原因→対処」
  • 発生時刻の確定から再発防止までの調査フローと、grep / awk / Select-String の使い方
  • AIにログを渡すときの注意と、AIの推測を自分で裏取りする方法
なぜ自分でログの地図1行の読み方スタックトレース例外の実例障害パターン調査フローコマンド影響調査AIに渡すときつまずき練習問題用語明日から

なぜ「自分で読める」必要があるのか

障害の連絡は、たいてい曖昧な形でやってきます。「朝、打刻ができなかったらしい」「申請画面が重い」。AIにログを貼れば、それらしい原因を答えてくれるでしょう。実際、それで解決できてきたと思います。

でも、次のような場面ではAIだけでは前に進めません。

  • ログが数GBあり、どこを渡せばいいか分からない
  • AIの答えが2つに割れて、どちらが正しいか判断できない
  • 上司から「影響は何人？いつから？データは大丈夫？」と聞かれる
  • 個人情報を含むログを社外のAIに渡せない

障害調査は、刑事ドラマの捜査に似ています。「いつ・どこで・何が起きたか」を確定し、証拠（ログ）を時系列に並べ、最初の異変を探し、動機（根本原因）を突き止める。AIは優秀な助手ですが、現場の証拠を集めて、どれを助手に見せるかを決めるのは担当者です。この章では、その「集め方」を身につけます。

ログの地図：どこに何が書かれるか

勤怠システムへのリクエストは、ブラウザ → Apache → Tomcat → アプリ（Spring Boot）→ PostgreSQL の順に流れます（全体像は 02 システムの全体像）。それぞれの層が、それぞれのログを書きます。どの層で止まったかによって、見るべきログが変わります。

ログ主な場所（一般的な例）何が分かるか
catalina.out$CATALINA_BASE/logs/Tomcatの標準出力・標準エラー。アプリがコンソールに出したログ、System.out、捕まえられなかった例外、OutOfMemoryError などがここに出ることが多い。肥大化しやすい
catalina.YYYY-MM-DD.log同上Tomcat本体のログ。起動・停止、アプリの配備（デプロイ）成功・失敗
localhost.YYYY-MM-DD.log同上ホスト（localhost）単位のログ。サーブレットやフィルタで発生しアプリが処理しきれなかった例外、アプリ初期化の失敗
localhost_access_log.YYYY-MM-DD.txt同上Tomcatが受けたリクエストの一覧（AccessLogValve）。URL・ステータス・処理時間
Apache access_log/var/log/httpd/（RHEL系）、/var/log/apache2/（Debian系）、Windowsは Apache24\logs\入口で受けた全リクエスト。利用者のIP、時刻、ステータス
Apache error_log同上Apache自体のエラー。Tomcatにつなげない（プロキシエラー、503）、設定ミス
アプリ独自ログlogback-spring.xml / log4j2.xml の設定次第業務処理のログ。どの社員の何の処理で失敗したか、スタックトレース
GCログJVM起動オプション（例：-Xlog:gc*:file=...）の設定次第ガベージコレクションの頻度と停止時間、ヒープ使用量。メモリ不足の兆候
PostgreSQLログデータディレクトリの log/ など（log_directory 設定次第）SQLのエラー、デッドロック、遅いSQL（log_min_duration_statement 設定時）、接続数超過
構成によって変わるところ
  • Windowsのサービスとして動くTomcatでは、catalina.out の代わりに tomcat9-stdout.日付.log / tomcat9-stderr.日付.log のようなファイルに出ます。
  • Spring Bootを実行可能jar（組み込みTomcat）で動かしている場合、catalina.* のファイルはなく、アクセスログは server.tomcat.accesslog.* の設定で出します。warをTomcatに配備している場合は上の表のとおりです。
先輩・社内Wikiに確認する項目
  • 本番・検証サーバーのホスト名と、各ログの実際の置き場所
  • アプリ独自ログのファイル名、ローテーション（何日分残るか、圧縮されるか）
  • ログを見るための権限・手順（直接ログインか、転送された場所を見るか）
  • アクセスログに処理時間（%D）が入っているか、GCログ・遅いSQLのログは有効か

ログ1行の読み方

アプリのログ（logbackの例）

形式は設定（パターン）で変わりますが、Spring Bootの既定に近い形はこうです。

2026-03-12 09:03:41.512 ERROR 21844 --- [nio-8080-exec-7] c.e.kintai.service.ClockService : 打刻登録に失敗しました employeeCode=E01234
部分例意味・使い方
日時2026-03-12 09:03:41.512いつ。他のログと突き合わせる軸。サーバー間で時計がずれていないかも意識する
レベルERROR重要度。ERROR（処理失敗）> WARN（注意・続行）> INFO（通常の記録）> DEBUG（開発用の詳細）。本番は通常INFO以上だけ出す
プロセスID21844どのJavaプロセスか。再起動するとかわる
スレッド名nio-8080-exec-7どの作業員が処理したか。Tomcatのリクエスト処理スレッド（http-nio-8080-exec-N の省略表示）。同じスレッド名で前後の行を追うと、1リクエストの流れが分かる
ロガー名c.e.kintai.service.ClockServiceどのクラスが書いたか（パッケージ名は省略される）。自社のコードかライブラリかの判別に
メッセージ打刻登録に失敗しました …開発者が書いた説明。直後にスタックトレースが続くことが多い

アクセスログ

Apacheでよく使われる combined 形式に、処理時間 %D を末尾に追加した例です。

10.20.31.45 - - [12/Mar/2026:09:03:41 +0900] "POST /kintai/clock/in HTTP/1.1" 500 1243 "https://kintai.example.local/kintai/top" "Mozilla/5.0 (Windows NT 10.0; ...)" 30215871
項目書式例と意味
クライアントIP%h10.20.31.45。プロキシ経由だとプロキシのIPになる
ユーザー%l %u- -。アプリのログインとは別物で、通常は空
時刻%t[12/Mar/2026:09:03:41 +0900]。応答を返した時刻ではなく、リクエストを受けた時刻
リクエスト行"%r"メソッド・URL・プロトコル。どの機能か
ステータス%>s500。2xx成功、3xx転送、4xx利用者側（404など）、5xxサーバー側の失敗（500アプリエラー、502/503は裏側につながらない、504は裏側の応答待ちタイムアウト）
バイト数%b返したデータ量。0や「-」が並ぶと中身なしの応答
参照元・ブラウザ"%{Referer}i" "%{User-Agent}i"どの画面から来たか、どのブラウザか
処理時間%D30215871。Apacheではマイクロ秒なので約30.2秒。Tomcatの AccessLogValve の %D は Tomcat 9 まではミリ秒、10.1以降はマイクロ秒
処理時間は既定では出ていないことが多い

Tomcatの既定のアクセスログパターンは %h %l %u %t "%r" %s %b で、処理時間は入っていません。「遅い」障害の調査には処理時間が欠かせないので、入っていなければ追加を改善提案にできます（設定変更は所定の手順で）。

スタックトレースの読み方

スタックトレースは「例外がどこで起き、どういう呼び出しの道をたどってきたか」の記録です。長くて怖く見えますが、見るべき場所は決まっています。

  • 例外クラス名とメッセージ：java.lang.NullPointerException や PSQLException の部分。まずここで「何の種類の失敗か」が分かります。
  • at 行：呼び出しの履歴。上ほど「最後に実行していた場所」です。クラス名.メソッド名(ファイル名:行番号) の形です。
  • 自社パッケージの行：com.example.kintai... のような自社のパッケージ名で始まる最初の行が、自分たちのコードの「現場」です。Spring・Tomcat・JDBCの行は道のりなので読み飛ばして構いません。
  • Caused by：例外が別の例外で包まれていることを表します。Springはよく低レベルの例外（PSQLExceptionなど）を自分の例外で包みます。一番下の Caused by が根本原因に一番近いので、そこのメッセージを最初に読みます。
  • ... 23 more：「残り23行は上の（外側の）トレースと同じなので省略」という意味です。消えた情報ではありません。
最初の1件を探す

障害時は同じ例外が何百回も出ます。調べるべきは一番最初に出たものです。後のエラーは、最初の失敗の巻き添え（連鎖）であることがよくあります。

例外の実例と読み方

勤怠システムでよく見る例外を、架空の例で並べます。クラス名やパッケージ名は一般的な例です。

NullPointerException：値がないのに使おうとした

java.lang.NullPointerException: Cannot invoke "java.time.LocalDateTime.isBefore(java.time.chrono.ChronoLocalDateTime)" because the return value of "com.example.kintai.domain.Attendance.getClockOut()" is null
	at com.example.kintai.service.OvertimeCalculator.calc(OvertimeCalculator.java:42)
	at com.example.kintai.service.MonthlyCloseService.closeEmployee(MonthlyCloseService.java:88)
	...

Java 14以降（標準で有効になったのは15以降）では「何がnullだったか」がメッセージに出ます。この例は「退勤時刻（clockOut）がnullなのに比較しようとした」、つまり打刻漏れのデータで締め処理が落ちた可能性を示します。OvertimeCalculator.java の42行目を開き、その社員のデータを 06 自分で書くSQL の方法で確認します。

PSQLException：データベースがSQLを拒否した

org.postgresql.util.PSQLException: ERROR: column "clock_out_time" does not exist
  Hint: Perhaps you meant to reference the column "attendance.clock_out".
  Position: 45

ERROR: の後ろはPostgreSQL自身のメッセージです。列名の間違い（デプロイ後ならSQLとテーブル定義の食い違い）、一意制約違反（二重登録）、value too long for type character varying(50)（入力が長すぎる）、canceling statement due to statement timeout（SQLが時間切れ）などがあります。同じ時刻のPostgreSQLログにも対応するエラーが出ているはずです。

SQLTransientConnectionException：コネクションプールが空

org.springframework.jdbc.CannotGetJdbcConnectionException: Failed to obtain JDBC Connection; nested exception is java.sql.SQLTransientConnectionException: HikariPool-1 - Connection is not available, request timed out after 30000ms.
	...
Caused by: java.sql.SQLTransientConnectionException: HikariPool-1 - Connection is not available, request timed out after 30000ms.
	at com.zaxxer.hikari.pool.HikariPool.createTimeoutException(HikariPool.java:696)
	...

HikariCPはDB接続を貸し出す「貸し傘置き場」です。傘（コネクション）が全部貸し出されていて30秒待っても返ってこなかった、という意味です。新しめのHikariCPでは (total=10, active=10, idle=0, waiting=25) のように内訳が付きます。原因は「傘が少ない」より「返ってこない」ことが多いので、同じ時刻に長時間SQLやロック待ちがないかをPostgreSQL側（pg_stat_activity、ログ）で確認します。

OutOfMemoryError: Java heap space：メモリが尽きた

Exception in thread "http-nio-8080-exec-15" java.lang.OutOfMemoryError: Java heap space
	at java.base/java.util.Arrays.copyOf(Arrays.java:3537)
	at java.base/java.util.ArrayList.grow(ArrayList.java:237)
	at com.example.kintai.export.CsvExportService.loadAll(CsvExportService.java:64)
	...

Javaに割り当てたメモリ（ヒープ）を使い切りました。at行は「最後にメモリを取ろうとした場所」で、犯人とは限りません（満員電車で最後に乗った人が悪いとは限らないのと同じ）。この例のように全件をリストに読み込むCSV出力などは疑わしいですが、GCログやヒープダンプで確かめる必要があります。OOM後のJVMは不安定なので、通常は再起動が必要です。

SocketTimeoutException：相手が応答しない

org.springframework.web.client.ResourceAccessException: I/O error on POST request for "https://payroll.example.local/api/attendance": Read timed out; nested exception is java.net.SocketTimeoutException: Read timed out

外部システム（この例では給与システム）に送ったが、決めた時間内に返事が来なかった、という意味です。connect timed out なら接続自体ができていない（相手が停止・ネットワーク不通）、Read timed out なら接続はできたが応答が遅い、と区別できます。相手側の障害やメンテナンス情報を確認します。

ClientAbortException：利用者が待たずに去った

org.apache.catalina.connector.ClientAbortException: java.io.IOException: Broken pipe

応答を返そうとしたら、ブラウザがもう接続を切っていた、という意味です。利用者がページを閉じた・再読み込みしただけなら単発では問題ないことが多いです。ただし、遅い処理に待ちきれず利用者が離脱した結果として大量に出ている場合は、「遅い」ことのほうが本当の問題です。

典型的な障害パターンと見るべきログ

障害の種類はそれほど多くありません。パターンを知っていると、症状から「まずどこを見るか」が決まります。

メモリ不足（OOM・GC多発）

症状全体が徐々に重くなり、最後は無応答。
証拠catalina.out の OutOfMemoryError、GCログでFull GCが頻発し停止時間が長い。
原因大量データの一括読み込み、メモリリーク、ヒープ設定不足。
対処再起動で一時回復→原因処理の特定、ページング化、設定見直し。

DBコネクション枯渇

症状DBを使う画面が30秒ほど待って500。
証拠アプリログの Connection is not available、pg_stat_activity で長時間のSQLや idle in transaction。
原因遅いSQL・ロック待ちで接続が返らない、接続の閉じ忘れ。
対処詰まっている処理の特定と解消。プール拡大は根本対策ではないことが多い。

スレッド枯渇（maxThreads）

症状静的なページまで遅い・つながらない。Apacheで502/503。
証拠アクセスログの処理時間が全体に伸びる、スレッドダンプ（jstack）で exec スレッドが同じ場所で待機。
原因各リクエストが何か（DB・外部連携）を待ち続け、Tomcatの作業員（既定200）が全員ふさがる。
対処待っている先を解消。タイムアウト設定。

長時間SQL・ロック待ち

症状特定の画面・更新だけ固まる。
証拠PostgreSQLログの遅いSQL・deadlock detected、pg_stat_activity の wait_event_type = Lock。
原因バッチと画面の同時更新、BEGINしたまま放置、インデックス不足。
対処ブロック元の特定（06章）、実行時間帯の調整、SQL改善。

ディスクフル

症状突然の書き込み失敗、ログが途中で途切れる、DBが停止。
証拠No space left on device、PostgreSQLの could not write to file、df -h で100%。
原因catalina.out の肥大化、ローテーション不備、ダンプファイルの放置。
対処不要ファイルの退避・削除（手順に従う）、ローテーション設定。

外部連携のタイムアウト

症状連携を伴う処理だけ遅い・失敗。
証拠SocketTimeoutException、連携先URLへのリクエストの処理時間。
原因相手側の障害・遅延、ネットワーク、証明書期限切れ（この場合はSSL系の例外）。
対処相手先への確認、再送手順、タイムアウトと再試行の設計見直し。

デプロイ後の起動失敗

症状リリース直後から全画面が404や503。
証拠catalina.日付.log の配備失敗、localhost.日付.log やアプリログの APPLICATION FAILED TO START、BeanCreationException。
原因設定ファイルの不足・誤り、DB接続情報、ライブラリの不整合、ポート競合。
対処一番下の Caused by を読む。切り戻し判断（04章）。

締め処理バッチの遅延

症状朝になってもバッチが終わらない、締め後の画面が使えない。
証拠バッチログの開始・終了時刻と件数の進み方、PostgreSQLの遅いSQL、ロック待ち。
原因データ量の増加、実行計画の変化、他処理とのロック競合。
対処進捗の確認、止めてよいかの判断（必ず責任者と）、SQL改善。

「再起動で直った」は解決ではない

再起動はサービスを戻すための応急処置です。原因がメモリリークやデータ量なら、同じ障害はまた起きます。再起動の前に、可能ならスレッドダンプやヒープの状態など「証拠」を残すべきか、手順書と先輩に確認しておきましょう。

調査フロー：最初の異変を探す

  1. 発生時刻と症状を確定する「朝」ではなく「3/12 9:03ごろから」。誰が、どの画面で、どういう表示（エラー画面・固まる・遅い）だったか。分からなければ問い合わせ元に確認します。
  2. 時系列を整理するその前後に何があったか：リリース、設定変更、バッチの実行、利用集中（始業・締め日）、外部システムのメンテナンス。
  3. アクセスログで影響範囲をつかむ500や遅いリクエストが何時から何時まで、何件、どのURLで、いくつのIP（利用者）から出ているか。「全画面か、特定機能か」もここで分かります。
  4. エラーログで最初のエラーを探す影響が始まった時刻の少し前から、アプリログ・catalina.out・PostgreSQLログを読み、最初に出たERRORを見つけます。
  5. 根本原因にたどり着く一番下の Caused by、自社コードの行、DB側の状態。「なぜ」を2〜3回繰り返して、表面の症状ではなく原因まで行きます。
  6. 影響調査をするどの機能が、どのデータが、何人に影響したか。登録されなかった打刻、二重登録、途中で止まったバッチのデータはないか。
  7. 再発防止を考える直接の修正だけでなく、検知（監視・アラート）、手順、設計の改善まで。

このタイムラインのように、問い合わせが来た時刻・エラーが大量に出た時刻・最初の異変の時刻はそれぞれ違います。報告で「9:10に障害発生」と書くと、9:02〜9:10に打刻できなかった人を見落とします。

ログを絞り込むコマンド

巨大なログをエディタで開くと固まります。コマンドで「時刻で絞る」「数える」「種類ごとに集計する」のが基本です。

Linux（grep / less / tail / awk）

# 流れてくるログをリアルタイムに見る（ローテーションに追従するなら -F）
tail -F /opt/tomcat/logs/catalina.out

# less で開く：/文字列 で検索、n 次、N 前、G 末尾、F 追従（Ctrl+C で解除）
less /opt/tomcat/logs/catalina.out

# 例外名を含む行と、後ろ30行（スタックトレース）を表示
grep -n -A 30 'SQLTransientConnectionException' app.log | less

# 圧縮済みの古いログも検索
zgrep -c 'OutOfMemoryError' catalina.out-20260311.gz

# アプリログ：9:00〜9:30 の行だけ（行頭が日時の形式の場合）
awk '$1" "$2 >= "2026-03-12 09:00" && $1" "$2 < "2026-03-12 09:30"' app.log > app_0900.log

# アクセスログ（combined形式）：ステータス500の件数（9番目の項目がステータス）
awk '$9 == 500' access_log | wc -l

# 500が出たURLの上位
awk '$9 == 500 {print $7}' access_log | sort | uniq -c | sort -rn | head

# 9時台の500を、1分ごとに数える（時刻の「時:分」まで切り出す）
grep '12/Mar/2026:09:' access_log | awk '$9 == 500 {print substr($4, 2, 17)}' | uniq -c

# 500を受けたIPの種類数（影響を受けた端末数の目安）
awk '$9 == 500 {print $1}' access_log | sort -u | wc -l

# 処理時間（末尾の %D、マイクロ秒）が10秒を超えたリクエスト
awk '$NF > 10000000' access_log | head

# 例外名ごとの件数
grep -oE '[A-Za-z.]+(Exception|Error)' app.log | sort | uniq -c | sort -rn | head
時刻で絞るときの落とし穴

スタックトレースの行は日時で始まらないので、上の awk の時刻絞り込みでは消えてしまいます。原因を読むときは grep -A や less の検索を使い、awk は件数を数えるために使うと分けて考えましょう。また、ログの時刻がサーバーごとにずれていないか（NTPで同期されているか）も意識してください。

Windows（findstr / PowerShell）

REM 例外名を含む行を探す（/N 行番号、/C: で文字列そのもの）
findstr /N /C:"OutOfMemoryError" catalina.2026-03-12.log

# PowerShell：tail -f 相当
Get-Content .\app.log -Wait -Tail 50

# ステータス500の件数（" 500 " を含む行）
(Select-String -Path .\localhost_access_log.2026-03-12.txt -Pattern '" 500 ').Count

# 例外名の行と、その後ろ30行
Select-String -Path .\app.log -Pattern 'SQLTransientConnectionException' -Context 0,30

# 例外名ごとの件数
Select-String -Path .\app.log -Pattern '[A-Za-z.]+(Exception|Error)' -AllMatches |
  ForEach-Object { $_.Matches.Value } | Group-Object | Sort-Object Count -Descending |
  Select-Object -First 10 Count, Name

GUIなら、サクラエディタのGrep（メニュー「検索」→「Grep」）が便利です。フォルダとファイル名（*.log）を指定し、「正規表現」にチェックを入れれば、複数ファイルを横断して検索でき、結果の行をダブルクリックすると該当箇所に飛べます。

文字コードに注意

ログがUTF-8だと、findstr では日本語の検索がうまくいかないことがあります。PowerShellの Select-String では -Encoding UTF8 を指定できます（PowerShell 7 は既定でUTF-8）。サクラエディタは文字コードの自動判別か、指定を確認しましょう。

影響調査：事実を集める型

障害の後に必ず聞かれるのが「影響は？」です。この章では事実の集め方を扱い、それをどう伝えるかは 11 伝える技術 で扱います。集めるべき事実は次の型で整理すると漏れません。

項目何を調べるか根拠にするもの
発生時間帯最初の異変〜回復の時刻エラーログの最初と最後、アクセスログの500の分布
事象利用者から見て何が起きたか（エラー画面、固まった）問い合わせ内容、ステータスコード
影響機能どの画面・処理かアクセスログのURL集計
影響人数・件数失敗したリクエスト数、利用者数アクセスログの件数・IP数、アプリログの社員コード
データへの影響登録漏れ、二重登録、途中で止まった更新SQLでの確認（例：その時間帯の打刻の欠落）
原因判明しているもの／推定のもの（区別して書く）スタックトレース、DBの状態
対応状況実施済みの対処、残作業、回避策作業記録
あいまいな報告

「朝、DBが重くて打刻できない人がいたようです。今は直っています。」

事実がそろった報告

「3/12 9:02〜9:25、打刻と申請の画面で500エラー。アクセスログ上の失敗は打刻412件・申請37件、端末数は298。締めバッチのロック待ちでDB接続が枯渇したと見ています（ロック待ちはログで確認済み、バッチ側SQLの特定は調査中）。失敗した打刻は再登録が必要で、対象者の一覧を作成中です。」

「確認済み」と「推定」を分けて書くのが大事です。AIの答えをそのまま書くと、推定が事実のように見えてしまいます。

AIにログを渡すときの注意

  • 個人情報・機密を消す：氏名、社員コード、メールアドレス、IPアドレス、セッションID、パスワードを含む接続文字列など。そもそも社外のAIにログを渡してよいか、社内のルールを先に確認してください。
  • 全体ではなく範囲を絞る：発生時刻の前後数分、最初のエラーとそのスタックトレース、同時刻のアクセスログ数行。大量に貼ると、AIは目立つが無関係なエラーに引っ張られます。
  • 状況を言葉で添える：「9:02から打刻で500。9:00に締めバッチ開始。構成は Apache + Tomcat 9 + Spring Boot + PostgreSQL」。
  • AIの推測を自分でログで裏取りする：「コネクション枯渇です」と言われたら、Connection is not available が本当に出ているか、何時からか、pg_stat_activity で詰まった処理が見えるかを自分で確認します。
  • 「なぜそう判断したのか」を聞く：根拠の行を示してもらい、自分で読めるかを試す。これが一番の学習になります（10 AIと一緒に強くなる）。
# 渡す前の簡易マスキングの例（IPアドレスと社員コードを置き換え）。完全ではないので目でも確認する
sed -E -e 's/[0-9]{1,3}(\.[0-9]{1,3}){3}/x.x.x.x/g' \
       -e 's/employeeCode=[A-Z0-9]+/employeeCode=****/g' app_0900.log > app_0900_masked.log

よくあるつまずき

一番上の例外だけ読む

外側の包みしか見ていない。一番下の Caused by まで下りる。

最後のエラーを原因と思う

大量のエラーの後半は巻き添え。最初の1件を探す。

問い合わせ時刻＝発生時刻

利用者が連絡するまでには時間差がある。ログで本当の開始時刻を確定する。

ログの日付を間違える

日付ごとのファイルは日付の切り替わりで分かれる。日をまたぐ障害は前日のファイルも見る。ローテーション済みの .gz も忘れずに。

ClientAbortException に驚く

単発なら利用者の離脱。大量なら「遅さ」が本当の問題。

WARNを全部無視する

普段から出ているWARNを知っておくと、「いつもと違うWARN」に気づける。平常時のログを一度眺めておく。

練習問題

架空のログです。まず自分で原因の仮説と、次に確認することを考えてから答えを開いてください。

Q1. 3月の締め日、9時過ぎから打刻画面がエラーになりました。アプリログに次の行が大量にあります。原因の候補と、次に見るべきものは？

2026-03-31 09:04:12.033 ERROR 21844 --- [nio-8080-exec-41] o.a.c.c.C.[.[.[/].[dispatcherServlet] : Servlet.service() ... threw exception
org.springframework.jdbc.CannotGetJdbcConnectionException: Failed to obtain JDBC Connection; nested exception is java.sql.SQLTransientConnectionException: HikariPool-1 - Connection is not available, request timed out after 30000ms.
Q1 の答えを見る

候補：DBコネクションプールの枯渇。コネクションが「返ってこない」理由として、締め処理バッチの長時間SQLやロック待ちが疑わしいです。

次に見るもの：(1) この行が最初に出た時刻（9:04より前にもないか）。(2) 同時刻の PostgreSQL の状態：pg_stat_activity で長時間実行中・wait_event_type = 'Lock' のセッション、PostgreSQLログの遅いSQL。(3) バッチログの開始時刻。(4) アクセスログで500の件数と時間帯（影響範囲）。プールのサイズを増やすだけでは、詰まっている原因が残ります。

Q2. 昨日リリースした後、全画面が404になりました。catalina.日付.log に次のような記録があります。どこを読めば原因が分かりますか？

12-Mar-2026 22:15:03.118 SEVERE [main] org.apache.catalina.core.StandardContext.startInternal One or more listeners failed to start. Full details will be found in the appropriate container log file
12-Mar-2026 22:15:03.121 SEVERE [main] org.apache.catalina.core.StandardContext.startInternal Context [/kintai] startup failed due to previous errors
Q2 の答えを見る

これは「アプリ（/kintai）の起動に失敗した」という結果だけです。メッセージのとおり、詳細は別のログ（localhost.日付.log やアプリログ）にあります。そこで同時刻の例外を探し、一番下の Caused by を読みます。たとえば次のような行があれば、DB接続の設定（パスワードなど）が新しい環境で間違っていると分かります。

Caused by: org.postgresql.util.PSQLException: FATAL: password authentication failed for user "kintai_app"

アプリが起動していないので、URLが存在せず404になっていたわけです。対処は設定の修正か切り戻しで、どちらにするかは手順書と責任者の判断です。

Q3. 夕方から申請画面が少しずつ重くなり、19時ごろに応答しなくなりました。catalina.out の最後のほうにこうあります。何が起きた可能性が高く、何を確認しますか？

Exception in thread "http-nio-8080-exec-88" java.lang.OutOfMemoryError: Java heap space
	at java.base/java.util.Arrays.copyOf(Arrays.java:3537)
	at java.base/java.lang.AbstractStringBuilder.ensureCapacityInternal(AbstractStringBuilder.java:228)
	at com.example.kintai.report.ApplicationReportService.buildCsv(ApplicationReportService.java:112)
Q3 の答えを見る

可能性：ヒープ不足（OOM）。「少しずつ重くなった」のは、メモリが逼迫してGCが頻発していた兆候です。

確認すること：(1) GCログで、夕方からFull GCの回数と停止時間が増えていないか。(2) アクセスログで、OOMの前に申請一覧のCSV出力など重い処理が繰り返し呼ばれていないか（URLと処理時間）。(3) at行の buildCsv は最後にメモリを取ろうとした場所であって、犯人と断定はできない点に注意。ヒープダンプが取れていれば、何がメモリを占めていたかを分析できます。

用語まとめ

ログレベル
ERROR / WARN / INFO / DEBUG の重要度。設定より低いレベルは出力されない。
アクセスログ
受け付けたリクエストの台帳。影響範囲を数えるのに使う。
スタックトレース
例外が起きた場所と、そこまでの呼び出しの履歴。
Caused by
包まれた内側の例外。一番下が根本原因に近い。
コネクションプール
DB接続を使い回す仕組み。Spring Bootの既定はHikariCP。
maxThreads
Tomcatが同時に処理できるリクエスト数の上限（既定200）。
ヒープ / GC
Javaのオブジェクトを置くメモリ / 使われなくなったメモリを回収する仕組み。
スレッドダンプ
その瞬間に各スレッドが何をしているかの一覧。jstack などで取得。
ローテーション
ログファイルを日付やサイズで切り替え、古いものを圧縮・削除する運用。
根本原因
表面の症状ではなく、それを引き起こした元の原因。
影響調査
障害でどの機能・データ・利用者が影響を受けたかを事実で確定する作業。
