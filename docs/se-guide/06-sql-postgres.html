自分で書くSQL

AIが出したSQLを「実行するだけ」から、「読んで、確かめて、自分で書ける」へ。勤怠の架空テーブルを使って、PostgreSQLの基本から更新の作法・ロック・遅いSQLの見方までを一通り歩きます。

この章でわかること
  • 勤怠テーブルのつながり（ER図）と、SQLが実際に動く順番
  • SELECT / JOIN / GROUP BY / サブクエリ / CTE / CASE / ウィンドウ関数の読み書き
  • PostgreSQLの日付時刻とNULLの扱い（ここでの勘違いが一番バグになります）
  • UPDATE・DELETEを安全に流す手順と、本番前チェックリスト
  • ロック待ち・デッドロック・遅いSQL（EXPLAIN）の見方の入り口
  • AIが作ったSQLを分解して読み解く手順
なぜ自分でテーブルの地図実行順序基本の3つJOIN集計CTE・CASE・窓関数日付時刻NULL安全な更新ロック遅いSQLpsqlとクライアントAIのSQLを読むつまずき練習問題用語明日から

なぜ「自分で書ける」必要があるのか

AIに「今月の残業時間を社員ごとに出すSQL」と頼めば、それらしいSQLはすぐ出てきます。実行すれば結果も出ます。でも、その結果が正しいかどうかは、AIもあなたもまだ確かめていません。

勤怠のデータには落とし穴がたくさんあります。退勤打刻のない日（NULL）、日をまたぐ夜勤、退職者、同じ日に2回打刻された行、タイムゾーンのずれ。AIはあなたの会社のテーブル定義も運用ルールも知らないので、それらしい前提で書きます。結果の数字が少しずれていても、エラーにはなりません。エラーが出ない間違いこそ、一番危ないのです。

この章の目標は、AIを使わなくなることではありません。AIの出したSQLを1段ずつ分解して実行し、件数と中身を確かめられるようになることです。それができれば、AIは「速く書いてくれる相棒」になり、あなたは「確かめて責任を持てる人」になります。

この章のテーブルについて

ここで使うテーブル名・列名はすべて説明用の架空のものです。実際の勤怠システムの定義は、psqlの \d テーブル名 やクライアントの画面で必ず確認してください（後半で方法を説明します）。

まず地図を持つ：勤怠テーブルのER図

SQLを書く前に、「どのテーブルに何が入っていて、どの列でつながっているか」を知る必要があります。これを図にしたものがER図（Entity Relationship図）です。知らない街を歩く前に地図を見るのと同じです。

読み方のポイントは「1対多」です。1つの部署に社員は何人もいる。1人の社員に打刻の行は毎日1行ずつ増えていく。JOINしたときに行数が増えるのは、この「多」の側をつなぐからです。この感覚が、後で「なぜ合計が倍になったのか」を見抜く力になります。

自社のER図がないときは

多くの現場ではER図が古いか、存在しません。その場合は、よく使うテーブル5つだけで良いので、自分で紙に書いてみてください。\d attendance で出てくる Foreign-key constraints の行が、線を引く手がかりになります。外部キー制約が張られていない現場もあるので、そのときは列名（employee_id など）から推測し、先輩に確認しましょう。

書く順と動く順はちがう：SQLの実行順序

SQLは SELECT から書き始めますが、データベースはSELECTを最後のほうで処理します（論理的な処理順。実際の内部の処理はオプティマイザが最適化しますが、結果はこの順で考えたのと同じになります）。

AIが出した長いSQLを読むときも、FROMから読むのがコツです。「どの表から」「何とつないで」「どの行に絞って」「どうまとめて」「何を表示するか」。工場のラインのように、材料（行）が工程を順に通っていくイメージを持ってください。

エラーになる
SELECT employee_id,
       clock_out - clock_in AS worked
FROM attendance
WHERE worked > INTERVAL '10 hours';
-- column "worked" does not exist
正しく動く
SELECT employee_id,
       clock_out - clock_in AS worked
FROM attendance
WHERE clock_out - clock_in > INTERVAL '10 hours'
ORDER BY worked DESC;

基本の3つ：SELECT / WHERE / ORDER BY

まずは1つのテーブルだけで「列を選ぶ・行を絞る・並べる」です。これだけで調査の半分はできます。

特定社員の3月の打刻を日付順に
SELECT work_date, clock_in, clock_out
FROM   attendance
WHERE  employee_id = 1234
  AND  work_date >= '2026-03-01'
  AND  work_date <  '2026-04-01'   -- 月末日を書かず「翌月1日未満」
ORDER BY work_date;
  • 範囲は >= 月初 と < 翌月1日 の組み合わせが安全です。BETWEEN '2026-03-01' AND '2026-03-31' は date 型なら動きますが、timestamp 型に使うと 3月31日 00:00:00 までしか入らず、31日の日中が漏れます。
  • 文字列の比較は =、部分一致は LIKE '%山田%'、大文字小文字を無視するなら PostgreSQL では ILIKE。
  • 複数の値は IN ('APPROVED', 'PENDING')。
  • 調査では最初に LIMIT 20 を付けて、どんな行が返るか眺めると安心です。
AND と OR が混ざったら必ずカッコ

WHERE status = 'PENDING' OR status = 'RETURNED' AND app_type = 'COMMUTE' は、AND が先に結びつくので「PENDINGすべて」＋「差戻しの通勤費」になります。意図が「通勤費のうち PENDING か RETURNED」なら app_type = 'COMMUTE' AND (status = 'PENDING' OR status = 'RETURNED') と書きます。

JOIN：表と表を対応づける

JOINはよくベン図で説明されますが、実際の動きは「条件に合う行同士をペアにして横に並べる」です。表で見るほうが正確に理解できます。

-- INNER JOIN：打刻のある社員だけ
SELECT e.name, a.work_date, a.clock_in, a.clock_out
FROM   employees e
JOIN   attendance a ON a.employee_id = e.employee_id
WHERE  a.work_date = '2026-03-02';

-- LEFT JOIN：3/2に打刻が1件もない在職者
SELECT e.employee_code, e.name
FROM   employees e
LEFT JOIN attendance a
       ON  a.employee_id = e.employee_id
       AND a.work_date = '2026-03-02'   -- 右表の条件は ON に書く
WHERE  a.attendance_id IS NULL
  AND  e.retired_on IS NULL;
LEFT JOIN が INNER JOIN に化ける

上の例で a.work_date = '2026-03-02' を WHERE に書くと、相手がいなくて NULL になった行が WHERE で落ち、結果は INNER JOIN と同じになります。「左を残したいのに残らない」ときは、右表の条件が WHERE に書かれていないか見てください。

GROUP BY と集計：月別の残業時間

GROUP BY は「同じ値の行をひとまとめにして、1グループ1行にする」操作です。仕分け箱に社員ごとの打刻票を入れて、箱ごとに合計を書くイメージです。

ここでは説明のため、「所定労働8時間＋休憩1時間で、拘束9時間を超えた分を残業とする」という単純化したルールを使います。実際の残業計算は就業規則・シフト・深夜・休日などで複雑なので、本番の数字はアプリの計算ロジックや仕様書と突き合わせてください。

社員ごと・月ごとの残業時間（単純化ルール）
SELECT a.employee_id,
       date_trunc('month', a.work_date)::date              AS month,
       count(*)                                           AS days,
       sum(GREATEST(a.clock_out - a.clock_in - INTERVAL '9 hours',
                    INTERVAL '0'))                       AS overtime
FROM   attendance a
WHERE  a.work_date >= '2026-01-01'
  AND  a.clock_out IS NOT NULL          -- 打刻漏れの日は除外（別途確認）
GROUP BY a.employee_id, date_trunc('month', a.work_date)
HAVING sum(GREATEST(a.clock_out - a.clock_in - INTERVAL '9 hours',
                    INTERVAL '0')) > INTERVAL '30 hours'
ORDER BY month, overtime DESC;
  • timestamp - timestamp は interval（時間の長さ）になります。GREATEST(..., INTERVAL '0') でマイナスを0に丸めています。
  • SELECT に書く列は「GROUP BY に書いた列」か「集計関数（count, sum, avg, max, min）」のどちらかです。それ以外を書くと must appear in the GROUP BY clause or be used in an aggregate function というエラーになります。
  • count(*) は行数、count(clock_out) は clock_out が NULL でない行数。この違いで打刻漏れの件数も出せます。
JOINしてから集計すると合計が膨らむ

employees と attendance と leave_requests を一度にJOINして sum すると、打刻の行 × 休暇の行の組み合わせ分だけ行が増え、残業時間が2倍・3倍になります。「多」の表を2つ同時につなぐときは、先にそれぞれ集計してからつなぐ（次のCTEが便利）のが基本です。

サブクエリ・CTE・CASE・ウィンドウ関数

サブクエリ：SQLの中のSQL

-- 未承認の申請が1件以上ある社員
SELECT e.employee_code, e.name
FROM   employees e
WHERE  EXISTS (
         SELECT 1 FROM applications ap
         WHERE  ap.employee_id = e.employee_id
           AND  ap.status = 'PENDING'
       );

EXISTS は「相手が1件でもあれば真」。IN (SELECT ...) でも書けますが、NOT IN はサブクエリに NULL が混ざると1行も返らなくなる罠があるので、否定は NOT EXISTS が安全です（NULLの節で説明します）。

CTE（WITH）：名前を付けた中間結果

CTEは、長いSQLを「工程ごとに名前を付けた下ごしらえ」に分ける書き方です。料理のレシピで「Aを切っておく」「Bを煮ておく」と準備を分けるのに似ています。読みやすく、1工程ずつ確かめやすいので、AIのSQLを読むときにも自分で書くときにもおすすめです。

WITH daily AS (            -- 工程1：1日ごとの残業
  SELECT employee_id, work_date,
         GREATEST(clock_out - clock_in - INTERVAL '9 hours', INTERVAL '0') AS ot
  FROM   attendance
  WHERE  work_date >= '2026-03-01' AND work_date < '2026-04-01'
    AND  clock_out IS NOT NULL
),
monthly AS (                  -- 工程2：社員ごとに合計
  SELECT employee_id, sum(ot) AS ot_total
  FROM   daily
  GROUP BY employee_id
)
SELECT d.department_name, e.name, m.ot_total   -- 工程3：名前を付けて表示
FROM   monthly m
JOIN   employees   e ON e.employee_id   = m.employee_id
JOIN   departments d ON d.department_id = e.department_id
ORDER BY m.ot_total DESC;

確かめるときは、最後の SELECT を SELECT * FROM daily LIMIT 20; に差し替えれば工程1だけの結果が見られます。

CASE：条件で値を変える

SELECT application_id,
       CASE status
         WHEN 'PENDING'  THEN '承認待ち'
         WHEN 'APPROVED' THEN '承認済'
         WHEN 'RETURNED' THEN '差戻し'
         ELSE 'その他(' || status || ')'
       END AS status_label
FROM   applications;

-- 集計と組み合わせる：部署ごとの状態別件数
SELECT e.department_id,
       count(*) FILTER (WHERE ap.status = 'PENDING')  AS pending,
       sum(CASE WHEN ap.status = 'APPROVED' THEN 1 ELSE 0 END) AS approved
FROM   applications ap
JOIN   employees e ON e.employee_id = ap.employee_id
GROUP BY e.department_id;

FILTER (WHERE ...) は PostgreSQL で使える書き方で、sum(CASE ...) と同じことを短く書けます。両方とも見かけるので、どちらも読めるようにしておきましょう。

ウィンドウ関数：行を残したまま集計する

GROUP BY は行をまとめて減らしますが、ウィンドウ関数は行を残したまま「同じグループの中での順位・累計・前の行」を横に付け足します。OVER (PARTITION BY 区切り ORDER BY 並び) が目印です。

SELECT employee_id, work_date, clock_in, clock_out,
       -- 同じ社員・同じ日の打刻に番号（重複打刻の発見）
       row_number() OVER (PARTITION BY employee_id, work_date ORDER BY clock_in) AS rn,
       -- 前日の退勤時刻（勤務間インターバルの確認）
       lag(clock_out) OVER (PARTITION BY employee_id ORDER BY work_date) AS prev_out,
       -- 月内の累計労働時間
       sum(clock_out - clock_in) OVER (
         PARTITION BY employee_id, date_trunc('month', work_date)
         ORDER BY work_date) AS running_total
FROM   attendance
WHERE  employee_id = 1234;

「同じ日に2行ある打刻を探す」なら、上の rn を CTE にして WHERE rn > 1 で絞れます。ウィンドウ関数の結果は WHERE で直接使えない（実行順序を思い出してください。SELECTより前にWHEREが動きます）ので、CTEかサブクエリで包むのが定番です。

PostgreSQLの日付と時刻

勤怠システムは日付時刻のかたまりです。型と関数を正しく知っておくと、AIのSQLの間違いにも気づけるようになります。

型・関数意味例
date日付だけ'2026-03-02'::date
timestamp日付＋時刻（タイムゾーンなし）'2026-03-02 09:00'::timestamp
timestamptz日付＋時刻（タイムゾーンあり。内部はUTCで保存し、表示時にセッションのTimeZone設定で変換）now() の型
interval時間の長さINTERVAL '1 hour 30 minutes'
current_date / now()今日 / 現在日時（トランザクション開始時点）current_date - 1 は昨日
date_trunc指定単位で切り捨てdate_trunc('month', now()) → 月初0時
extract一部を数値で取り出すextract(hour FROM clock_in)、extract(epoch FROM interval) は秒数
to_char書式を付けて文字列にto_char(clock_in, 'YYYY/MM/DD HH24:MI')
AT TIME ZONEタイムゾーンの変換下で説明
-- interval を「時間(小数)」に直す。extract の戻り値の型はバージョンで違うので numeric にそろえる
SELECT round((extract(epoch FROM INTERVAL '47 hours 30 minutes') / 3600)::numeric, 1);
-- → 47.5

-- 曜日：extract(dow ...) は 0=日曜〜6=土曜、isodow は 1=月曜〜7=日曜
SELECT work_date, extract(isodow FROM work_date) AS dow FROM attendance LIMIT 5;

-- 今月の範囲（月初〜翌月1日未満）
WHERE work_date >= date_trunc('month', current_date)::date
  AND work_date <  (date_trunc('month', current_date) + INTERVAL '1 month')::date

AT TIME ZONE は向きに注意

AT TIME ZONE は、元の型によって逆向きに働きます。ここは経験者でも混乱するところです。

  • timestamp（TZなし） AT TIME ZONE 'Asia/Tokyo' → 「この時刻は東京時間です」と解釈して timestamptz にする。
  • timestamptz AT TIME ZONE 'Asia/Tokyo' → その瞬間を東京の壁時計で見た timestamp（TZなし） にする。
SHOW TimeZone;   -- 今のセッションのタイムゾーンを確認
SELECT TIMESTAMPTZ '2026-03-02 00:30:00+00' AT TIME ZONE 'Asia/Tokyo';
-- → 2026-03-02 09:30:00（UTC 0:30 は東京 9:30）
「9時間ずれている」と言われたら

DBサーバーやクライアントのタイムゾーン設定がUTCになっていて、timestamptz がUTCで表示されているのかもしれません。データが壊れているとは限りません。SHOW TimeZone; と、列の型が timestamp か timestamptz かを先に確認しましょう。

NULL：「値がない」は「0」でも「空文字」でもない

NULLは「分からない・まだない」という状態です。退勤打刻をしていない日の clock_out がまさにそれです。NULLを含む計算や比較は、結果もNULL（＝真でも偽でもない）になります。

書き方結果説明
clock_out = NULL常にNULL（1行も選ばれない）NULLとの比較は = では書けない
clock_out IS NULL真/偽正しい書き方。否定は IS NOT NULL
clock_out - clock_inNULL片方がNULLなら計算結果もNULL
sum(...)、avg(...)NULLの行は無視平均の分母も減るので注意
COALESCE(x, 0)xがNULLなら0表示や計算の既定値に
status <> 'APPROVED'statusがNULLの行は選ばれないNULLも含めたいなら status IS DISTINCT FROM 'APPROVED'
x NOT IN (SELECT y ...)yにNULLが1つでもあると0行NOT EXISTS を使う
-- 打刻漏れを含めて、日ごとの労働時間を「未確定」と表示
SELECT work_date,
       COALESCE(to_char(clock_out - clock_in, 'HH24:MI'), '未確定') AS worked
FROM   attendance
WHERE  employee_id = 1234
ORDER BY work_date;

更新系の安全な作法：UPDATE / DELETE の前に

SELECTは何度間違えてもデータは壊れません。でも UPDATE と DELETE は、WHERE を1つ間違えるだけで全社員の打刻を書き換えてしまいます。だからこそ、毎回同じ型（手順）で流すことが大切です。料理人が包丁を使う前に必ず同じ構えをとるのと同じです。

  1. 同じWHEREでSELECTして件数と中身を見る依頼された件数（例：「3件」）と一致するか。一致しなければ、そこで止まって依頼者に確認します。
  2. BEGIN; でトランザクションを開始するここから COMMIT するまでは、他の人からは変更前の状態が見えています。
  3. UPDATE / DELETE を実行し、表示される件数を見るpsqlなら UPDATE 3 のように出ます。RETURNING を付けると変更後の行も見られます。
  4. もう一度SELECTして結果を確認する意図した値になっているか、関係ない行が変わっていないか。
  5. 正しければ COMMIT;、少しでも違えば ROLLBACK;迷ったら ROLLBACK。やり直しはいつでもできます。
-- 例：通勤費申請3件を差戻し状態に戻す（申請IDは依頼票のもの）
SELECT application_id, employee_id, status
FROM   applications
WHERE  application_id IN (50121, 50122, 50130);    -- まず3件か確認

BEGIN;

UPDATE applications
SET    status = 'RETURNED'
WHERE  application_id IN (50121, 50122, 50130)
  AND  status = 'APPROVED'                       -- 想定外の状態は触らない保険
RETURNING application_id, status;
-- UPDATE 3 と出ることを確認

SELECT application_id, status FROM applications
WHERE  application_id IN (50121, 50122, 50130);

ROLLBACK;   -- 予行演習ならここで戻す。本番で確認が取れたら COMMIT;
クライアントの「自動コミット」に注意

A5:SQL Mk-2、pgAdmin、DBeaver などのクライアントには自動コミット（1文ごとに即確定）の設定があり、オンだと BEGIN を書き忘れた UPDATE は実行した瞬間に確定します。psql も既定は自動コミットです。自分の使うツールの設定がどうなっているか、更新作業の前に必ず確認してください。また、BEGIN したまま放置すると行ロックを持ち続け、他の処理を止めます（次の節）。

本番で実行する前のチェックリスト

先輩・社内Wikiに確認する項目
  • 本番DBへのデータ修正の申請・承認フローはあるか（誰の承認が必要か）
  • 本番に直接つなげるのは誰か、作業は画面共有やダブルチェックで行うか
  • 変更前データの退避方法の決まり
  • 締め処理・夜間バッチの実行時間帯

トランザクションとロック

トランザクションは「全部成功するか、全部なかったことにするか」の単位です。そして、同じ行を2人が同時に書き換えないように、データベースはロックをかけます。トイレの鍵のようなもので、誰かが入っている（ロックを持っている）間、次の人はドアの前で待ちます。

誰が何を待っているかを見る

pg_stat_activity は「今つながっているセッションの一覧」、pg_locks は「ロックの一覧」です。見るだけなら安全なので、検証環境で一度実行してみてください（他人のクエリ内容を見るには権限が必要な場合があります）。

-- 実行中・放置中のセッション（古いトランザクションほど上）
SELECT pid, usename, application_name, state,
       wait_event_type, wait_event,
       now() - xact_start  AS xact_age,
       now() - query_start AS query_age,
       left(query, 60)     AS query
FROM   pg_stat_activity
WHERE  datname = current_database()
ORDER BY xact_start NULLS LAST;

-- 待たされているセッションと、待たせている相手のpid
SELECT pid, pg_blocking_pids(pid) AS blocked_by,
       wait_event_type, left(query, 60) AS query
FROM   pg_stat_activity
WHERE  cardinality(pg_blocking_pids(pid)) > 0;

-- まだ取れていない（granted = false）ロック
SELECT locktype, relation::regclass, mode, granted, pid
FROM   pg_locks
WHERE  NOT granted;
  • state = 'idle in transaction' で xact_age が長い行は、BEGIN したまま放置されたセッションです。ロック待ちの犯人であることがよくあります。
  • wait_event_type = 'Lock' は、ロックを待っている状態です。
  • セッションを止める pg_cancel_backend(pid)（クエリを中断）や pg_terminate_backend(pid)（接続ごと切断）もありますが、本番では必ず先輩・責任者の判断で行ってください。バッチを途中で切ると、別の問題を生むことがあります。

デッドロック

AがXの行をつかんでYを待ち、BがYの行をつかんでXを待つと、永遠に終わりません。PostgreSQLはこれを検出して片方をエラーで終わらせます。ログには次のように出ます。

ERROR:  deadlock detected
DETAIL:  Process 24512 waits for ShareLock on transaction 918273; blocked by process 24877.
        Process 24877 waits for ShareLock on transaction 918270; blocked by process 24512.
HINT:  See server log for query details.

対策の基本は「複数の行を更新するときは、どの処理も同じ順番（例：employee_id の昇順）で更新する」「トランザクションを短くする」です。アプリの処理順の問題なので、見つけたらログの日時と処理名を添えて相談しましょう。

遅いSQL：EXPLAIN の読み方入門

本で「打刻」の説明を探す索引がなければ、1ページ目から最後まで全部めくる。索引があれば「打刻…p.120」を見て直接開く。
＝
データベースで行を探すインデックスがなければ全行を読む（Seq Scan）。あれば索引をたどって該当行だけ読む（Index Scan）。

ただし索引も万能ではありません。本の半分以上のページを読むなら、索引を何度も引くより最初からめくったほうが速いですよね。データベースも同じ判断をするので、「Seq Scan＝悪」ではありません。

EXPLAIN は「どうやって探すつもりか（実行計画）」を表示し、EXPLAIN ANALYZE は実際に実行してかかった時間も表示します。

EXPLAIN ANALYZE
SELECT * FROM attendance WHERE employee_id = 1234;

-- インデックスがない場合（例）
Seq Scan on attendance  (cost=0.00..18334.00 rows=52 width=40) (actual time=0.015..85.210 rows=48 loops=1)
  Filter: (employee_id = 1234)
  Rows Removed by Filter: 999952
Planning Time: 0.080 ms
Execution Time: 85.240 ms

-- CREATE INDEX idx_attendance_emp_date ON attendance (employee_id, work_date); の後（例）
Index Scan using idx_attendance_emp_date on attendance  (cost=0.42..12.31 rows=52 width=40) (actual time=0.020..0.065 rows=48 loops=1)
  Index Cond: (employee_id = 1234)
Planning Time: 0.110 ms
Execution Time: 0.090 ms
見る場所意味
Seq Scan / Index Scan / Bitmap Heap Scanどう探したか。全件読み／索引で直接／索引でまとめて当たりを付けてから読む
Rows Removed by Filter読んだけど捨てた行数。大きいほど無駄読み
rows=52（cost側）と rows=48（actual側）見積もりと実際の行数。大きくずれていたら統計情報が古い可能性（ANALYZE テーブル名）
actual time=...その工程にかかった時間（ミリ秒）。インデントが深い行から先に動く
Execution Time全体の実行時間
EXPLAIN ANALYZE は本当に実行する

UPDATE や DELETE に EXPLAIN ANALYZE を付けると、実際に更新されます。試すなら BEGIN; EXPLAIN ANALYZE UPDATE ...; ROLLBACK; の形で。また、本番でのインデックス追加は書き込みを止めることがあり（CREATE INDEX CONCURRENTLY という方法もあります）、効果と影響の検討が必要なので、自分で判断せず改修案として相談してください。

インデックスが効かなくなる典型も覚えておきましょう：列に関数をかける（WHERE to_char(work_date, 'YYYY-MM') = '2026-03'）、前方が%のLIKE（LIKE '%田'）、型の違う比較。最初の例は work_date >= '2026-03-01' AND work_date < '2026-04-01' と範囲で書けばインデックスが使えます。

psqlの基本と、GUIクライアント

psqlはPostgreSQL付属のコマンドラインのクライアントです。サーバーにSSHで入ったときなど、GUIが使えない場面で頼りになります。

psql -h dbhost -p 5432 -U kintai_user -d kintai   # 接続（値は一般的な例）
コマンドやること
\dtテーブル一覧
\d attendanceテーブルの列・型・インデックス・外部キーを表示
\x縦表示の切り替え（列が多い行を読みやすく）。\x auto で自動

GUIのクライアントでは、日本の現場でよく使われる A5:SQL Mk-2（Windows、ER図の作成機能もある）、PostgreSQL公式の管理ツール pgAdmin、多くのDBに対応する DBeaver などがあります。どれを使うかは社内の決まりに従ってください。どのツールでも、「接続先の表示」「自動コミットの設定」「結果の件数表示」の場所だけは最初に確認しておくと事故を防げます。

AIが作ったSQLを読み解く手順

AIのSQLは長く、一見正しそうに見えます。次の手順で、1段ずつ実行して件数を確かめる習慣をつけましょう。これは学習にもなります。

  1. 使っているテーブルと列を書き出すFROM / JOIN に出てくる表を全部挙げ、\d で列名・型が実在するか確認する。AIは存在しない列名を作ることがあります。
  2. FROMの表だけで件数を数えるSELECT count(*) FROM attendance WHERE ...; 条件ごとに件数がどう変わるかを見る。
  3. JOINを1つずつ足して件数を見るJOINを足したときに件数が増えたら「1対多」でつないだ証拠。意図どおりか考える。
  4. CTEは1つずつ SELECT * FROM cte名 LIMIT 20 で中身を見る工程ごとの結果を目で確かめる。
  5. 知っている1人で検算する自分や特定の社員1人に絞り、画面の表示や手計算と一致するか比べる。
  6. NULL・境界をわざと確かめる打刻漏れの日、月末日、日をまたぐ勤務、退職者が入っているとどうなるか。
  7. 分からない部分をAIに質問する「この LEFT JOIN を INNER JOIN にすると何が変わる？」のように、部分を指して聞く。丸ごと「合ってる？」と聞くより学びになります。
AIへの頼み方を変える

「〜を出すSQLを書いて」に加えて、「テーブル定義は次のとおり（\d の結果を貼る）」「打刻漏れはclock_outがNULL」「CTEで工程を分けて、各工程にコメントを付けて」と伝えると、読みやすく検証しやすいSQLが返ってきます。AIとの付き合い方は 10 AIと一緒に強くなる でも扱います。本番データの中身（氏名など）をAIに貼らないことも忘れずに。

よくあるつまずき

合計が倍になる

1対多の表を2つ同時にJOINして集計した。先に集計してからつなぐ。JOINごとに件数を確認する。

LEFT JOINなのに行が消える

右表の条件をWHEREに書いた。ONに移す。

月末の打刻が漏れる

timestampにBETWEENで月末日を指定した。「翌月1日未満」で書く。

= NULL で0件

NULLの比較は IS NULL。<> ではNULLの行が除外されることも忘れずに。

9時間ずれる

timestamptzの表示タイムゾーン。SHOW TimeZone; と列の型を確認。

画面が固まった

BEGINしたままCOMMITを忘れてロックを持っている。自分のセッションを確認してCOMMITかROLLBACK。

GROUP BYのエラー

SELECTにGROUP BYにない列を書いた。GROUP BYに足すか集計関数で包む。

round がエラー

round(double precision, integer) は存在しない。::numeric にキャストしてから丸める。

練習問題

上の架空テーブルを前提にしています。まず自分で書いてから答えを開いてください。検証環境があれば、実際のテーブルに置き換えて動かしてみるのが一番の練習です。

Q1. 今月の残業（拘束9時間超の部分の合計）が45時間を超える在職社員を、社員コード・氏名・残業時間（小数1桁）で、多い順に出してください。 
WITH daily AS (
  SELECT employee_id,
         GREATEST(clock_out - clock_in - INTERVAL '9 hours', INTERVAL '0') AS ot
  FROM   attendance
  WHERE  work_date >= date_trunc('month', current_date)::date
    AND  work_date <  (date_trunc('month', current_date) + INTERVAL '1 month')::date
    AND  clock_out IS NOT NULL
)
SELECT e.employee_code, e.name,
       round((extract(epoch FROM sum(d.ot)) / 3600)::numeric, 1) AS overtime_hours
FROM   daily d
JOIN   employees e ON e.employee_id = d.employee_id
WHERE  e.retired_on IS NULL
GROUP BY e.employee_code, e.name
HAVING sum(d.ot) > INTERVAL '45 hours'
ORDER BY overtime_hours DESC;

ポイント：月の範囲は「月初〜翌月1日未満」。集計値での絞り込みは HAVING。ORDER BY では SELECT の別名が使えます。打刻漏れの日を除外しているので、Q2の結果と合わせて見ないと残業が少なく見える点にも注意しましょう。

Q2. 昨日までの今月分で「出勤打刻はあるのに退勤打刻がない日（打刻漏れ）」を、社員コード・氏名・日付で一覧にしてください。 
SELECT e.employee_code, e.name, a.work_date, a.clock_in
FROM   attendance a
JOIN   employees e ON e.employee_id = a.employee_id
WHERE  a.clock_in  IS NOT NULL
  AND  a.clock_out IS NULL
  AND  a.work_date >= date_trunc('month', current_date)::date
  AND  a.work_date <  current_date          -- 今日は勤務中かもしれないので除く
ORDER BY a.work_date, e.employee_code;

clock_out = NULL と書くと0件になります。「今日」を除く理由（まだ退勤していないだけ）まで考えられたら十分です。夜勤で日付をまたぐ運用がある場合は、退勤が翌日の行に入っていないかも確認が必要です。

Q3. 社員ID 1234 について、今月の平日（月〜金）で打刻の行が1件もない日を出してください（祝日・休暇は考えなくて構いません）。 
SELECT d::date AS work_date
FROM   generate_series(date_trunc('month', current_date),
                       current_date - 1,
                       INTERVAL '1 day') AS g(d)
LEFT JOIN attendance a
       ON  a.employee_id = 1234
       AND a.work_date   = d::date
WHERE  extract(isodow FROM d) BETWEEN 1 AND 5
  AND  a.attendance_id IS NULL
ORDER BY work_date;

generate_series で「あるべき日付の一覧」を作り、LEFT JOIN で相手がいない日を探します。「ないもの」を探すには、まず「あるべきもの」の表を用意する、という考え方は調査でよく使います。実務では休暇（leave_requests）や会社カレンダーのテーブルを NOT EXISTS で除外します。

Q4. 先輩から「申請ID 70001 の通勤費申請を削除して」と頼まれました。安全に実行するためのSQLの流れを書いてください。 
SELECT * FROM applications WHERE application_id = 70001;   -- 1件・対象の申請か確認
BEGIN;
DELETE FROM applications WHERE application_id = 70001 RETURNING *;   -- DELETE 1 を確認
SELECT count(*) FROM applications WHERE application_id = 70001;    -- 0 を確認
COMMIT;   -- 少しでもおかしければ ROLLBACK;

加えて確認したいこと：明細や承認履歴など、この申請を参照している別テーブルはないか（外部キー制約でエラーになる、または孤児データが残る）。物理削除ではなく「取消」ステータスにする運用ではないか。変更前の行を保存したか。これらは依頼者に聞いてよい質問です。

用語まとめ

主キー（PK）
行を1つに特定する列。employee_id など。
外部キー（FK）
他のテーブルの主キーを指す列。テーブル同士をつなぐ線になる。
INNER JOIN
両方の表に相手がいる行だけをペアにする。
LEFT JOIN
左の表の行は相手がいなくても残し、右側をNULLで埋める。
GROUP BY / HAVING
同じ値でまとめる / まとめた後の組を条件で絞る。
CTE（WITH）
名前を付けた中間結果。長いSQLを工程に分けられる。
ウィンドウ関数
行を残したまま、グループ内の順位・累計・前後の行を計算する。OVER (...) が目印。
interval
時間の長さを表す型。timestamp同士の引き算の結果。
NULL
値がない状態。比較は IS NULL / IS NOT NULL。
トランザクション
BEGIN〜COMMIT/ROLLBACKの、全部やるか全部やめるかの単位。
ロック / デッドロック
同時更新を防ぐ鍵 / 互いに相手の鍵を待って進めない状態。
実行計画（EXPLAIN）
データベースがどうやってデータを探すかの計画。ANALYZEを付けると実測。
インデックス
本の索引のような、検索を速くする仕組み。更新は少し遅くなる。
Seq Scan / Index Scan
全行を順に読む / インデックスをたどって読む。
