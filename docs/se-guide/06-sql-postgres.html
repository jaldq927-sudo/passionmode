SCENE 3

表が絞られていく様子

SELECT   emp, sum(ot) AS total     -- ⑤
FROM     attendance                 -- ①
WHERE    work_date >= '2026-03-01'  -- ②
GROUP BY emp                        -- ③
HAVING   sum(ot) >= 1               -- ④
ORDER BY total DESC LIMIT 1;      -- ⑥

SCENE 4

JOINは行のペア作り

両方に相手がいる行だけ残る。

-- 3/2に打刻が1件もない社員
SELECT e.name
FROM   employees e
LEFT JOIN attendance a
       ON  a.employee_id = e.employee_id
       AND a.work_date = '2026-03-02'  -- 右表の条件はONに
WHERE  a.attendance_id IS NULL;

右表の条件をWHEREに書くと、INNERに化ける。

SCENE 5

GROUP BYは仕分け箱

SELECTに書ける列GROUP BYの列か、sum・countなど集計関数だけ
集計で絞るWHEREではなく HAVING
合計が倍になる「多」の表を2つJOINしてから集計した。先に集計してからつなぐ
SCENE 6

エラーが出ない落とし穴

0件になるclock_out = NULL
→
正しいclock_out IS NULL
NULL＝まだ無い0でも空文字でもない。計算に混ざると結果もNULL
NOT IN のわな中にNULLが1つあると0件。否定は NOT EXISTS
月の範囲>= 月初 AND < 翌月1日。timestampにBETWEENだと月末が漏れる
9時間ずれる壊れたとは限らない。SHOW TimeZone;と列の型を確認

AIはこの会社のデータの癖を知らない。件数と中身を自分で見る。

SCENE 7

更新はいつも同じ型で

SELECT同じWHEREで件数確認
BEGINやり直せる状態に
UPDATE書き換える
件数確認UPDATE 3 か？
COMMIT違えば ROLLBACK
SELECT * FROM applications WHERE application_id IN (50121,50122,50130); -- 3件?①
BEGIN;
UPDATE applications SET status = 'RETURNED'
WHERE  application_id IN (50121,50122,50130)
  AND  status = 'APPROVED'            -- 想定外は触らない保険
RETURNING application_id, status;      -- UPDATE 3 ?②
ROLLBACK;  -- 予行演習。本番で確認が取れたら COMMIT;
1依頼の件数と違えば、ここで止めて確認
2表示される件数を必ず見る
自動コミットに注意ONだとBEGIN忘れのUPDATEは即確定
迷ったら ROLLBACKやり直しはいつでもできる
接続先を声に出す本番か検証か、DB名とホスト名で確認
SCENE 8

インデックスは本の索引

本の索引インデックス
全ページめくるSeq Scan

EXPLAIN ANALYZE SELECT * FROM attendance WHERE employee_id = 1234;
-- 索引なし（例）

  Rows Removed by Filter: 999952②
Execution Time: 85.240 ms③
-- 索引 (employee_id, work_date) を作った後（例）

1どう探したか
2読んだのに捨てた行。多いほどムダ

Seq Scan＝悪ではない。半分以上読むなら全部めくる方が速い。

ANALYZE 付きは本当に実行される。UPDATEは BEGIN〜ROLLBACK で。

SCENE 9

-- 誰が誰を待たせているか（見るだけなら安全）
SELECT pid, state, now() - xact_start AS xact_age,
       pg_blocking_pids(pid) AS blocked_by, left(query, 60)
FROM   pg_stat_activity
WHERE  datname = current_database();
