システムの全体像

勤怠システムは「ブラウザ → Apache → Tomcat → Spring Boot アプリ → PostgreSQL」という層の積み重ねです。この地図が頭に入ると、ログをどこから見ればよいか、障害がどの層で起きているかを自分で考えられるようになります。

この章でわかること
  • 勤怠システムを構成する5つの層と、それぞれの役割・ログの場所
  • 打刻ボタンを押してから画面が返るまでに、裏で何が起きているか
  • HTTP の基本（GET / POST、ステータスコード）と、障害時の「どの層か」の切り分け方
  • WAR 配備と Spring Boot 実行可能 jar の違い、現場のシステムがどちらかを確かめる方法
なぜ地図が要るかレストランでたとえる構成図とログHTTPの基礎リクエストの一生バッチとオンライン複数台構成WARとjar障害の切り分けつまずき練習問題用語明日から

なぜ「地図」が要るのか

ログ調査を AI に頼んで解決できた。でも、なぜそのログを見ればよかったのか、自分では説明できない。そんなもやもやを感じているなら、足りていないのは個々の知識よりも全体の地図かもしれません。

勤怠システムは、1つの大きなプログラムではありません。ブラウザ、Web サーバ（Apache）、AP サーバ（Tomcat）、アプリ（Spring Boot）、データベース（PostgreSQL）という、役割の違う部品がリレーのように仕事を受け渡しています。障害が起きたときに「どこで止まったのか」を考えるには、このリレーの順番と、それぞれの部品がどこに記録（ログ）を残すかを知っている必要があります。

逆に言えば、地図さえあれば AI への質問も変わります。「エラーが出ました、どうすれば？」ではなく、「Apache のアクセスログでは 503、Tomcat の catalina.out には起動完了の行がない。Tomcat が上がっていない可能性をどう確かめればよいか」と聞けるようになります。これは AI に頼らない力であると同時に、AI をうまく使う力でもあります。

この章の前提

ここで示す構成・パス・設定は一般的な例です。あなたの現場のサーバ台数、インストール先、ログのファイル名は違う可能性があります。章の途中に「先輩・社内 Wiki に確認する項目」をまとめているので、読み終えたら一度答え合わせをしてください。

レストランでたとえる

まずは細かい用語を置いておいて、レストランの姿で全体をつかみましょう。

レストラン受付係：お客さんを迎え、席へ案内する。メニュー表（決まった印刷物）はその場で渡せる。
=
勤怠システムApache：リクエストを最初に受ける。画像や CSS などの静的ファイルは自分で返し、それ以外は奥へ取り次ぐ。SSL（https）の暗号化もここ。
レストラン厨房：コンロや冷蔵庫がそろった、料理をつくる場所。料理人はここで働く。
=
勤怠システムTomcat：Java のアプリが動く場所（サーブレットコンテナ、AP サーバ）。同時に来た注文をさばくスレッドもここが用意する。
レストラン料理人とレシピ：「打刻の注文が来たら、この手順でつくる」という決まりごと。
=
勤怠システムSpring Boot アプリ：会社が作った業務ロジック。打刻の記録、残業時間の計算、締め処理などの手順が Java で書かれている。
レストラン食料庫：材料を保管しておく場所。料理人は必要な分だけ取り出し、余ったら戻す。
=
勤怠システムPostgreSQL：打刻データ、社員マスタ、有給残日数などを保存するデータベース。アプリは SQL で出し入れする。

お客さん（ブラウザ）は厨房の中を見ることはできません。受付係に注文を伝え、しばらくすると料理（画面）が届く、という体験だけをします。「料理が来ない」というクレーム1つでも、原因は受付・厨房・レシピ・食料庫のどこにでもありうる。これが障害調査の難しさであり、地図が必要な理由です。

たとえの限界も知っておく

実際の Tomcat は「厨房」でありながら、注文の受付（HTTP の受信）も自分でできます。Apache を置かずに Tomcat や Spring Boot が直接ブラウザと話す構成もあります。たとえは入口としてだけ使い、細部は次の図で確かめましょう。

各層の役割をもう少しくわしく

ブラウザ

HTML を画面に描き、JavaScript を動かし、ボタンが押されたらサーバへリクエストを送ります。Cookie を覚えておき、次のリクエストに自動で付けて送るのもブラウザの仕事です。F12 キーで開く開発者ツールで、送ったリクエストと返ってきたレスポンスを見られます。

Apache httpd

443 番ポートで https を受け、暗号を解きます（SSL 終端）。/images/ のような静的ファイルは自分のディスクから返し、/kintai/ 以下などアプリ宛てのリクエストは、モジュールを使って Tomcat へ転送します。この「代わりに奥へ取り次ぐ」働きをリバースプロキシと呼びます。

Tomcat

Java のサーブレットという仕組みに沿ってアプリを動かす入れ物です。受け取ったリクエスト1件ごとにスレッドを割り当て、アプリの処理を呼びます。セッション（ログイン状態）の管理もここで行い、JSESSIONID という Cookie で利用者を見分けます。

Spring Boot アプリ

会社の業務ロジックそのものです。Controller が URL ごとの入口、Service が計算や判定、Repository が DB 操作、という役割分担が一般的です。くわしい仕組みは 04 Spring Bootの正体 で扱います。

PostgreSQL

データを表（テーブル）の形で保存し、SQL で読み書きされます。複数の更新を「全部成功か、全部なかったことにするか」でまとめるトランザクションもここが保証します。SQL は 06 自分で書くSQL で練習します。

Apache から Tomcat へのつなぎ方は3種類

Apache が Tomcat へリクエストを渡す方法には、主に次の3つがあります。どれを使っているかで、見るべき設定ファイルが変わります。

方式通信設定の例特徴
mod_proxy_ajpAJP（通常 8009）ProxyPass /kintai ajp://localhost:8009/kintaiApache 標準のモジュール。AJP は Apache と Tomcat の間専用のバイナリ形式。
mod_jkAJP（通常 8009）JkMount /kintai/* worker1 と workers.propertiesTomcat プロジェクトが配布する別モジュール。昔からのシステムに多い。
mod_proxy_httpHTTP（通常 8080）ProxyPass /kintai http://localhost:8080/kintaiふつうの HTTP で転送。Spring Boot の組み込み Tomcat と組み合わせやすい。
httpd.conf（または conf.d/kintai.conf）の一般的な例
# 静的ファイルは Apache が直接返す
Alias /static /var/www/kintai/static

# アプリ宛ては Tomcat へ（mod_proxy_ajp の場合）
ProxyPass        /kintai ajp://localhost:8009/kintai secret=xxxxx
ProxyPassReverse /kintai ajp://localhost:8009/kintai
AJP の注意点

2020 年に AJP コネクタの脆弱性（通称 Ghostcat）が公表され、Tomcat 9.0.31・8.5.51 以降では AJP コネクタが初期状態で無効になり、使う場合は secret の設定が求められるようになりました。バージョンアップ後に「Apache からつながらない」場合、この変更が関係していることがあります。

HTTP の基礎：ブラウザとサーバの会話

層と層の間の会話には決まった形式があります。ブラウザと Apache、Apache と Tomcat（mod_proxy_http の場合）は HTTP で話します。HTTP は「リクエスト（お願い）」と「レスポンス（返事）」の1往復が基本です。

打刻ボタンを押したときに飛ぶリクエストの例（一般的な例）
POST /kintai/punch/in HTTP/1.1
Host: kintai.example.co.jp
Cookie: JSESSIONID=3F2A9C...E81
Content-Type: application/x-www-form-urlencoded

_csrf=8d1e...&memo=
返ってくるレスポンスの例
HTTP/1.1 302 Found
Location: /kintai/punch?done=in
Set-Cookie: ...

1行目がいちばん大事です。リクエストは「メソッド（何をしたいか）＋URL（どこに）」、レスポンスは「ステータスコード（結果はどうだったか）」です。

GET と POST

メソッド意味勤怠での例データの載せ方
GET取得する。何度送っても結果が変わらないのが原則月次勤怠一覧を表示 /kintai/monthly?ym=2026-10URL の ? 以降（クエリ文字列）
POST送る・登録する。サーバの状態が変わる出勤打刻、残業申請の提出リクエストの本文（ボディ）
PUT / DELETE更新・削除（API でよく使う）JSON API で申請を取り消す、などボディ／URL

打刻のように「データを登録する」操作は POST にするのが原則です。GET にしてしまうと、ブラウザの再読み込みや履歴からの再アクセスで二重打刻が起きかねません。

ステータスコード表

3桁の数字の、百の位で大まかな意味が決まります。2xx は成功、3xx は「別の場所へ」、4xx は「リクエスト側の問題」、5xx は「サーバ側の問題」です。

コード名前意味勤怠での典型的な場面
200OK成功月次一覧が表示された
302Found別の URL へ移動してほしい打刻後に完了画面へ、未ログインでログイン画面へ
304Not Modified前回から変わっていないCSS や画像をブラウザのキャッシュで済ませた
400Bad Requestリクエストの形がおかしい日付パラメータの形式が不正
401Unauthorized認証が必要API をログインなしで呼んだ
403Forbidden権限がない／拒否一般社員が承認画面へ、CSRF トークン切れ
404Not Foundその URL はないURL の打ち間違い、アプリが配備されていない
405Method Not Allowedそのメソッドは受け付けないPOST 専用の URL に GET で来た
500Internal Server Errorサーバ内部で想定外のエラーアプリで例外（NullPointerException など）
502Bad Gateway奥のサーバから正しい返事が来ないApache が Tomcat から不正な応答を受けた
503Service Unavailable今は処理できないTomcat が停止中・起動中、メンテナンス中
504Gateway Timeout奥のサーバの返事が時間切れ重い集計が Apache 側のタイムアウトを超えた
「誰が」返したステータスかを意識する

502・503・504 は、多くの場合 Apache が「奥（Tomcat）とうまく話せなかった」ことを伝えるコードです。一方 500 は、Tomcat やアプリが「処理中に失敗した」ことを伝えるコードです。同じ 5xx でも、疑う層が違います。

打刻ボタンを押してから画面が返るまで：リクエストの一生

ここからは、朝 9:00 に社員の田中さんが「出勤」ボタンを押した場面を、時間の順に追いかけます。ここは本当に順番がある処理です。

  1. ブラウザが HTTP リクエストをつくるボタンを押すと、ブラウザはフォームの内容を集めて POST /kintai/punch/in というリクエストをつくります。前回ログインしたときに受け取った Cookie（JSESSIONID=...）も自動で付けます。
  2. DNS で行き先を調べ、Apache に届くURL のホスト名（例：kintai.example.co.jp）を IP アドレスに変換し、そのサーバの 443 番ポートへ接続します。https なので通信は暗号化されています。
  3. Apache が受け取り、振り分けるApache は暗号を解き、URL を見ます。/kintai/ で始まるので静的ファイルではない、と判断し、ProxyPass などの設定に従って Tomcat へ転送します。このとき access_log に1行記録されます（記録されるのは応答を返し終えたタイミングです）。
  4. Tomcat がスレッドを割り当てるTomcat はリクエストを受けると、待機中のスレッドを1つ割り当てます。ログに出る [nio-8080-exec-3] や [ajp-nio-8009-exec-3] のような名前は、このスレッドの名前です。Cookie の JSESSIONID からセッションを探し、「これは田中さんのログイン状態だ」とわかります。
  5. Spring が URL に合う Controller を呼ぶSpring の DispatcherServlet が、/punch/in と POST の組み合わせに対応するメソッド（例：PunchController.punchIn()）を探して呼び出します。ログイン中かどうか、CSRF トークンが正しいかといったチェックもこの前後で行われます。
  6. Service が業務ルールを判定するController は Service（例：PunchService.punchIn(社員ID, 現在時刻)）を呼びます。Service は「今日すでに出勤打刻していないか」「休日出勤の扱いは」といったルールを判定します。
  7. トランザクションを開始し、SQL を発行するService のメソッドに @Transactional が付いていると、ここでトランザクションが始まります。Repository が JDBC ドライバを通じて PostgreSQL に SQL を送ります。たとえば「今日の打刻があるか」の SELECT と、出勤時刻を書き込む INSERT です。
  8. PostgreSQL が処理し、コミットするメソッドが例外なく終わると、トランザクションがコミットされ、データが確定します。途中で例外が起きればロールバックされ、INSERT はなかったことになります。
  9. レスポンスをつくるController は結果に応じて、画面用なら Thymeleaf や JSP などのテンプレートで HTML を組み立てるか、完了画面へのリダイレクト（302）を返します。画面の一部だけを JavaScript で書き換える方式なら、{"status":"ok","time":"09:00"} のような JSON を返します。
  10. 同じ道を逆にたどって、画面が変わるレスポンスは Tomcat → Apache → ブラウザへと戻ります。ブラウザは HTML を描画し（302 なら指定された URL を GET し直し）、田中さんの画面に「09:00 出勤しました」と表示されます。ここまで多くの場合、1 秒もかかりません。
このとき発行される SQL のイメージ（テーブル名・列名は一般的な例）
BEGIN;
SELECT id, clock_in FROM attendance_record
 WHERE employee_id = 1001 AND work_date = '2026-10-31';
-- 0件なら、まだ出勤していないので登録する
INSERT INTO attendance_record (employee_id, work_date, clock_in)
 VALUES (1001, '2026-10-31', '2026-10-31 09:00:12');
COMMIT;

セッションと Cookie のしくみ

HTTP には「前のリクエストと同じ人だ」と覚えておく仕組みがありません。そこで、ログインに成功したとき Tomcat が受付番号のような文字列（セッション ID）を発行し、Set-Cookie: JSESSIONID=... でブラウザに渡します。ブラウザはそれ以降のリクエストにこの Cookie を付けて送り、Tomcat はその番号でサーバ側のメモリにある「田中さんの情報」を取り出します。

セッションはサーバのメモリにある

Tomcat を再起動すると、メモリ上のセッションは（特別な設定をしていなければ）消えます。「再起動したら全員ログアウトされた」「入力中の申請が消えた」という問い合わせは、この仕組みが理由です。サーバが複数台のときにセッションをどう扱うかは、後の「複数台構成」で触れます。

オンライン処理とバッチ処理

ここまでの「ボタンを押すとすぐ返る」処理をオンライン処理と呼びます。勤怠システムには、もう1つ大事な処理の形があります。決まった時刻に、まとめて大量のデータを処理するバッチ処理です。

オンライン処理
  • きっかけ：利用者の操作（打刻、申請、承認）
  • 1回に扱うデータ：少ない（その人の1日分など）
  • 求められること：すぐ返ること（数秒以内）
  • 失敗したら：画面にエラー。利用者がやり直せる
  • ログ：Apache・Tomcat・アプリのログ
バッチ処理
  • きっかけ：時刻（cron、ジョブ管理ツール、Spring の @Scheduled など）
  • 1回に扱うデータ：多い（全社員の1か月分など）
  • 求められること：決められた時間内に、確実に終わること
  • 失敗したら：誰も画面を見ていない。翌朝の問い合わせで発覚することも
  • ログ：バッチ専用ログ、ジョブ管理ツールの実行結果

勤怠でよくあるバッチの例は次のとおりです。

  • 夜間集計：毎晩、その日の打刻から実労働時間・残業時間・深夜時間を計算して集計テーブルに書き込む。
  • 月次締め処理：月末や翌月初に、その月の勤怠を確定させ、給与システムへ渡すデータ（CSV など）を作る。締め後は一般社員が修正できないようにロックする。
  • 有給付与：入社日や基準日に合わせて、有給休暇の日数を付与する。
  • 打刻漏れ通知：退勤打刻がない社員にメールを送る。
起動ジョブ管理や cron が毎月1日 2:00 に起動
読み込み全社員の前月分の打刻・申請を SELECT
計算残業・深夜・休日労働を集計
書き込み集計テーブルへ登録、締めフラグを立てる
連携給与システム向けファイル出力・終了コード
バッチがどこで動いているかは現場ごとに違う

バッチは、オンラインと同じ Tomcat の中で @Scheduled で動く場合もあれば、別のサーバで java -jar kintai-batch.jar のように独立して起動される場合も、シェルスクリプトから SQL を直接流す場合もあります。自分の現場のバッチが「いつ・どこで・何によって」起動されているかは、必ず確認しておきましょう。

サーバが複数台のとき：Web / AP / DB の分離と冗長化

小さなシステムでは、Apache・Tomcat・PostgreSQL を1台のサーバに同居させることもあります。利用者が多いシステムや止められないシステムでは、役割ごとにサーバを分け（分離）、同じ役割のサーバを2台以上用意します（冗長化）。次の図はよくある一般例です。

こうした構成では、調査の手順も変わります。

  • ログが台数分に分かれる：ap01 と ap02 のどちらでエラーが出たかわからないと、片方のログだけ見て「何も出ていない」と勘違いします。時刻とサーバ名をセットで確認しましょう。
  • セッションの扱い：ap01 でログインした人のリクエストが ap02 に行くと、ap02 はその人のセッションを持っていません。そのため、同じ人を同じサーバに送り続ける設定（スティッキーセッション）や、セッションを共有する仕組みが使われます。
  • 片方だけおかしい：「ときどきエラーになる」という症状は、2台のうち1台だけが不調なときの典型です。
  • DB の切り替え：プライマリが止まったとき、スタンバイを新しいプライマリに昇格させる運用があります。切り替えの手順と判断者は、運用設計書などで決まっているはずです。

「Tomcat の上で Spring Boot が動いている」と書いてきましたが、実はその「乗り方」に2種類あります。どちらなのかで、起動・停止の方法、設定ファイルの場所、ログの場所が大きく変わります。

Spring Boot は「jar 1つで動く」手軽さが売りですが、既存の Tomcat 運用に合わせて WAR で配備している現場も少なくありません。ビルドの話は 05 開発環境をつくる でくわしく扱います。

自分の現場がどちらか確かめる方法

サーバにログインできる権限があるなら、次のような確認ができます（実行前に、本番サーバで操作してよいか先輩に確認してください。以下はどれも「見るだけ」のコマンドです）。

動いている Java プロセスを見る
$ ps -ef | grep java
# A のとき：Tomcat の起動クラスが見える
tomcat  1234  1 ... java ... -Dcatalina.base=/opt/tomcat ... org.apache.catalina.startup.Bootstrap start
# B のとき：-jar で jar を直接起動している
kintai  5678  1 ... java -Xmx2g -jar /opt/kintai/kintai.jar
ファイルの置き場所を見る（パスは一般的な例）
$ ls /opt/tomcat/webapps/          # kintai.war や kintai/ があれば A
$ ls /opt/tomcat/conf/server.xml   # Connector の port="8009" protocol="AJP/1.3" など
$ systemctl status tomcat          # サービス名は現場ごとに違う
$ cat /etc/systemd/system/kintai.service   # ExecStart=java -jar ... なら B
先輩・社内 Wiki に確認する項目
  • 勤怠システムのサーバは何台で、それぞれのホスト名と役割（Web / AP / DB / バッチ）は？
  • アプリは WAR 配備ですか、実行可能 jar ですか？　起動・停止はどのコマンド（または手順書）で行いますか？
  • Apache と Tomcat は mod_proxy_ajp / mod_jk / mod_proxy_http のどれでつないでいますか？　設定ファイルはどこですか？
  • Apache・Tomcat・アプリ・PostgreSQL・バッチのログは、それぞれどのパスにありますか？　何日分残りますか？
  • 夜間バッチ・締め処理は、いつ・どのサーバで・何（cron、ジョブ管理ツールなど）から起動されていますか？
  • 本番サーバで自分が見てよい範囲・やってはいけない操作はどこまでですか？

障害が起きたとき：「どの層の問題か」を切り分ける

「勤怠システムがおかしい」と連絡が来たら、いきなりソースを読み始めるのではなく、まず症状から疑う層を絞るのが近道です。次の図は、よくある症状と最初に疑う層の対応です。

切り分けの基本の流れ

層の地図を手前（ブラウザ）から奥（DB）へたどるのが基本です。次の問いに順番に答えると、迷いにくくなります。

  1. いつから、誰が、どの画面で？全員か一部の人か、全画面か特定の画面か。全員・全画面なら Apache や Tomcat、DB 停止など土台の問題、特定の画面ならアプリのその機能の問題を疑います。
  2. ブラウザでステータスコードを確かめるF12 の Network タブで、そのリクエストが何番で返ったか見ます。そもそもリクエストが出ていなければブラウザ側（JavaScript）です。
  3. Apache の access_log にそのリクエストがあるか時刻と URL で探します。なければネットワークや DNS、LB など Apache より手前。あればステータスと応答時間を確認します。
  4. Tomcat・アプリのログに同じ時刻のエラーがあるか500 ならスタックトレースが出ているはずです。読み方は 03 読めるJava と 07 ログと障害調査 で扱います。
  5. DB の状態を確かめる遅い SQL、ロック待ち、接続数の上限、ディスク容量など。PostgreSQL のログや、権限があれば pg_stat_activity で実行中の SQL を確認します。
Apache access_log の1行の読み方（combined 形式の一般例）
192.168.10.25 - - [31/Oct/2026:09:00:12 +0900] "POST /kintai/punch/in HTTP/1.1" 503 299 "https://kintai.example.co.jp/kintai/punch" "Mozilla/5.0 ..."
# 送信元IP / 日時 / メソッドとURL / ステータス / 返したバイト数 / 参照元 / ブラウザ
同じ時刻の Apache error_log の例
[Sat Oct 31 09:00:12.345 2026] [proxy:error] [pid 2345] (111)Connection refused: AH00957: AJP: attempt to connect to 127.0.0.1:8009 (localhost) failed
# → 8009 番に誰も待ち受けていない ＝ Tomcat が止まっている／AJP が無効、を疑う
時刻をそろえる

Apache・Tomcat・アプリ・DB のログはファイルが別々なので、「同じ時刻」を手がかりに横断して読みます。サーバの時計やログのタイムゾーン（+0900 か UTC か）がずれていないかも、最初に確認しておくと安心です。

よくあるつまずき

つまずき1：アプリのログだけを見る

アプリのログに何も出ていないので「アプリは正常」と判断。実はリクエストが Apache で 503 になっていて、アプリまで届いていなかった。

こう考える

「ログに何もない」は「その層まで来ていない」可能性を示す情報です。手前の層のログに戻って、どこまで届いたかを確かめます。

つまずき2：Tomcat の設定を探して迷子

server.xml を探しても見つからない。実は実行可能 jar 構成で、設定は application.properties にあった。

こう考える

まず ps -ef | grep java などで「どの形で動いているか」を確かめてから、設定の場所を探します。

つまずき3：1台だけ見て結論を出す

ap01 のログにはエラーがないので「再現しない」と報告。実はエラーは ap02 で出ていた。

こう考える

冗長構成では全台のログを見ます。「どのサーバで起きたか」も報告に含めます。

つまずき4：バッチの存在を忘れる

「夜中に誰も操作していないのに残業時間が変わった」と悩む。実は夜間集計バッチが再計算していた。

こう考える

データが変わった時刻を確認し、その時刻に動くバッチがないかを疑います。バッチの一覧と実行時刻を手元に持っておきましょう。

「再起動で直った」は解決ではない

Tomcat の再起動で症状が消えても、原因（メモリ不足、スレッドの詰まり、DB 接続の取りっぱなしなど）は残っている可能性があります。再起動前に、ログや状態をできる範囲で保存しておく習慣をつけましょう。何を残すかは現場の手順に従ってください。

練習問題

Q1. 朝9時、全社員から「勤怠画面を開くと 503 Service Unavailable と出る」と連絡がありました。最初に疑う層と、見るログは？

503 は多くの場合、Apache が「奥の Tomcat と話せない」ことを示します。全員・全画面で起きているので、Tomcat が停止している、または起動途中の可能性が高いです。Apache の error_log で接続失敗（Connection refused など）が出ていないか、Tomcat の catalina.out などで停止や起動失敗の記録がないかを確認します。夜間にサーバのメンテナンスや再起動がなかったかも確かめましょう。

Q2. 出勤打刻を押したら 500 エラーになった、と1人の社員から連絡がありました。他の人は打刻できています。どこを見ますか？

500 はアプリ内部の例外が典型で、1人だけならその人のデータに特有の状態（たとえば前日の退勤打刻がない、社員マスタの所属が空など）が原因のことが多いです。アプリログで、その時刻・その社員のリクエストのスタックトレースを探します。そのうえで、SQL でその社員のデータを確認します。

Q3. 次のうち、Apache が自分で返すのが自然なものはどれ？　(a) 打刻の登録　(b) ロゴ画像 logo.png　(c) 月次勤怠の一覧画面

(b) です。ロゴ画像は誰がいつ見ても同じ内容の静的ファイルなので、Apache がディスクから直接返せます。(a) は DB への登録、(c) は社員ごとに内容が違う画面なので、Tomcat 上のアプリが処理します（ただし構成によっては静的ファイルもアプリから返していることがあります）。

Q4. ps -ef | grep java の結果に org.apache.catalina.startup.Bootstrap start が出てきました。アプリの配備形態はどちらの可能性が高く、ポート設定はどこを見ますか？

外部にインストールされた Tomcat が起動しているので、WAR ファイルを Tomcat に配備する形の可能性が高いです。ポートは Tomcat の conf/server.xml の <Connector> 要素を見ます。webapps/ 配下に勤怠アプリの WAR やフォルダがあるかも確認しましょう。

用語まとめ

Web サーバ
HTTP リクエストを最初に受けるサーバ。ここでは Apache httpd。静的ファイルの配信、SSL 終端、リバースプロキシを担当。
AP サーバ
アプリケーションサーバ。業務アプリを動かす。ここでは Tomcat。
サーブレットコンテナ
Java のサーブレット仕様に沿ってアプリを動かす入れ物。Tomcat がその代表。
リバースプロキシ
利用者の代わりに、奥のサーバへリクエストを取り次ぐ仕組み。
AJP
Apache と Tomcat の間で使われる通信形式。mod_proxy_ajp や mod_jk が使う。
静的ファイル
画像・CSS・JavaScript など、誰が見ても同じ内容のファイル。
HTTP メソッド
リクエストの種類。GET は取得、POST は送信・登録。
ステータスコード
レスポンスの結果を表す3桁の数字。2xx 成功、3xx 移動、4xx リクエスト側、5xx サーバ側。
Cookie
サーバがブラウザに預け、ブラウザが次から自動で送り返す小さなデータ。
セッション
同じ利用者の一連のリクエストをつなげて扱う仕組み。Tomcat では JSESSIONID で識別。
トランザクション
複数の DB 操作を「全部成功（コミット）か全部取り消し（ロールバック）」でまとめる単位。
オンライン処理
利用者の操作に即座に応える処理。
バッチ処理
決まった時刻に大量データをまとめて処理する。夜間集計、締め処理など。
冗長化
同じ役割のサーバを複数用意し、1台が止まってもサービスを続けられるようにすること。
WAR
Web アプリをまとめたファイル形式。外部の Tomcat の webapps に配備する。
実行可能 jar
Tomcat を内蔵し、java -jar だけで起動できる Spring Boot の成果物。
