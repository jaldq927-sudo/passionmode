XMLのWeb申請

「シートがいろいろあって、SQLが書かれている」申請定義XMLを、画面・ワークフロー・DBの3つに分けて読めるようになる章です。製品名に依存しない一般的な構造で説明し、自社のXMLで確かめる項目をまとめます。

この章でわかること
  • XMLの基本ルール（要素・属性・入れ子・CDATA・エンティティ・整形式と妥当性）
  • Web申請システムが「定義 → データ → 承認 → DB反映」でできていること
  • 「シート」が何を指しているのかを見分ける方法
  • 通勤費申請の架空XMLを、画面の部品とDBのテーブルに対応づけて読む方法
  • 改修時に壊さないための注意点と、構文エラーの見つけ方
なぜ読めると強いかたとえ話XMLの基礎申請システムの構造「シート」の正体通勤費申請XML改修時の注意読み解き手順つまずき練習問題用語明日から

なぜ申請XMLが読めると強いのか

氏名変更届、結婚の届出、通勤費申請。どれも社員にとっては「画面で入力して送信するもの」ですが、裏側ではXMLファイルが「どんな項目を出すか」「誰が承認するか」「確定したらどのテーブルを更新するか」を決めています。つまり、XMLは申請の設計図そのものです。

いまはXMLを開くと、タグがたくさん並び、途中にSQLが埋め込まれていて、どこから読めばいいか分からない状態かもしれません。でも、申請システムがやっていることは実はシンプルで、次の4つしかありません。

  1. 画面に項目を並べる（入力欄、選択肢、添付）
  2. 入力をチェックして保存する
  3. 承認者に回す（差戻しもある）
  4. 最終承認されたら、社員マスタなどの本番データに反映する

XMLのどの塊がこの4つのどれに当たるかが分かれば、知らないタグが出てきても「たぶんここは画面の話だな」と当たりをつけられます。改修の相談を受けたときも、「その変更は画面定義だけで済むのか、DB列追加が必要か、承認ルートも変わるか」を自分で切り分けられるようになります。

この章の前提

製品名やタグ名は会社ごとに違います。この章のXMLはすべて説明用の架空の例です。実際のタグ名・属性名は自社のXMLや社内Wikiで確認してください。確認すべき項目は最後にリストにしています。

たとえ話：申請XMLは「紙の届出用紙＋回覧ルール＋台帳への転記メモ」

昔の会社では、通勤費申請は紙で出していました。その紙の仕組みを思い浮かべると、XMLの役割がつかみやすくなります。

紙の時代届出用紙の書式（記入欄、チェックボックス）＋「課長→人事」の回覧ハンコ欄＋「承認後に人事が台帳を書き換える」という手順メモ
＝
Web申請XMLの項目定義（画面）＋承認ルート定義（ワークフロー）＋確定時SQL（社員マスタ更新）

紙の用紙に「経路」「金額」の欄があるように、XMLには項目の定義があります。用紙の右上にハンコ欄があるように、XMLには承認ルートがあります。そして人事担当者が台帳を書き換えていた作業を、XMLに書かれたSQLが代わりにやっています。

XMLを読むときは「いま読んでいるのは用紙の書式か、回覧ルールか、転記メモか」と自分に問いかけてみてください。

XMLの基礎：これだけ押さえれば読める

XMLは「タグで囲んで、データに名前をつける」ための書き方です。HTMLと見た目は似ていますが、タグ名は自由に決められ、ルールはHTMLよりずっと厳しいのが特徴です。

要素・タグ・属性・入れ子

基本の形（架空の例）

<?xml version="1.0" encoding="UTF-8"?>   <!-- XML宣言 -->
<form id="commute" name="通勤費申請">       <!-- ルート要素 -->
  <field id="route" type="text" required="true">
    <label>経路</label>
  </field>
  <field id="memo" type="textarea"/>     <!-- 中身がない要素は /> で閉じてよい -->
</form>

図1 要素・タグ・属性の関係

  • 要素：開始タグから終了タグまでの全体。<label>経路</label> が1つの要素です。
  • 属性：開始タグの中に 名前="値" で書く補足情報。値は必ず引用符で囲みます。
  • 入れ子：要素の中に要素を入れられます。ただし交差は禁止です（<a><b></a></b> はエラー）。
  • ルート要素：ファイル全体を包む、ただ1つの一番外側の要素。上の例では <form>。
  • 大文字・小文字は区別されます。<Field> と <field> は別物です。

宣言とエンコーディング

1行目の <?xml version="1.0" encoding="UTF-8"?> は「このファイルはXML 1.0で、文字コードはUTF-8です」という宣言です。古いシステムでは encoding="Shift_JIS" や Windows-31J のこともあります。宣言と実際の保存形式が食い違うと文字化けや読み込みエラーになるので、エディタで保存するときは文字コードを宣言に合わせてください。

コメント

<!-- ここはコメント --> の中は無視されます。コメントの中に --（ハイフン2つ）を書くのは禁止なので、SQLのコメント -- 説明 をそのままXMLコメントの中に貼ると壊れることがあります。

エンティティ：< や & を文字として書く方法

XMLでは < は「タグの始まり」、& は「エンティティの始まり」という特別な意味を持つので、文字としてそのまま書けません。代わりに次の書き方を使います。

書きたい文字XMLでの書き方よく出る場面
<&lt;SQLの WHERE amount < 50000
>&gt;SQLの比較（書かなくても通ることが多いが、揃えると安全）
&&amp;URLのクエリ文字列、会社名「A&B」
"&quot;属性値の中にダブルクォートを書くとき
'&apos;属性値をシングルクォートで囲んでいるとき

CDATA：SQLをまるごと書くための囲い

SQLには < や <= がよく出てきます。毎回 &lt; に置き換えると読みにくいので、<![CDATA[ と ]]> で囲みます。この中は「ただの文字」として扱われ、< をそのまま書けます。

<sql><![CDATA[
  SELECT code, name FROM m_transport
  WHERE valid_from <= CURRENT_DATE
]]></sql>
CDATAの注意

CDATAの中に ]]> という並びは書けません。また、CDATAの外側（タグの直下）で < を使うとエラーになります。「SQLに比較演算子を足したら申請が読み込まれなくなった」は典型的な事故です。

整形式と妥当性

XMLの「正しさ」には2段階あります。

整形式（well-formed）

XMLの文法として正しいこと。タグが閉じている、入れ子が交差していない、ルート要素が1つ、属性値が引用符で囲まれている、など。これが崩れるとどのツールでも読めません。

妥当（valid）

整形式であるうえで、XSD（XML Schema）やDTDという「この申請XMLにはこのタグを、この順番で書く」という規則に従っていること。規則ファイルがあるかは製品次第です。

ファイルの先頭付近に xsi:schemaLocation="... form.xsd" や <!DOCTYPE form SYSTEM "form.dtd"> があれば、規則ファイルが存在する手がかりです。規則ファイルがあれば、エディタで「このタグはここに書けない」と教えてもらえます。

申請システムの一般的な構造

多くのWeb申請（ワークフロー）製品は、次の流れでできています。製品によって呼び名は違いますが、役割の分け方はほぼ共通です。

図2 申請フォーム定義 → 申請データ → 承認 → 確定時のDB反映

大事なポイントは、申請中のデータと本番データは別の場所にあることです。通勤費申請を出しただけでは社員マスタは変わりません。人事が最終承認した瞬間に、確定SQLが走って初めて本番データが変わります。差戻しされたら申請データだけが修正され、本番には何も起きません。

この構造を知っていると、障害の切り分けがしやすくなります。

  • 「画面に項目が出ない」→ ①フォーム定義、または選択肢を取るSQL
  • 「上長に届かない」→ ③承認ルート（組織マスタ、承認者の解決SQL）
  • 「承認されたのに社員マスタが変わらない」→ ④確定SQL、またはその実行ログ

確定SQLのエラーはアプリのログに出ることが多いので、07 ログと障害調査の手順がそのまま使えます。

「シート」とは何か：推測パターンと見分け方

「XMLにシートがいろいろある」という言い方は、製品や社内の呼び方によって意味が変わります。よくあるパターンを挙げるので、自社のXMLがどれに近いか見比べてください。

パターンシートの意味XMLでの見え方（例）見分けるヒント
A 画面のタブ／ページ1つの申請画面を「基本情報」「経路」「添付」のように分けた単位<sheet name="経路"> の下に <field> が並ぶ実際の申請画面のタブ名・ページ名とシート名が一致する
B 帳票・印刷様式承認後に出力するPDFや印刷レイアウト座標（x, y）、フォント、ページサイズの属性がある帳票出力機能で同じ見た目のものが出る
C Excel由来の定義Excelで設計した定義をXMLに変換したもの。Excelのシート1枚がXMLの1ブロック行・列番号、セル番地（A1 など）が出てくる元のExcel設計書がどこかにある。XMLの冒頭に生成ツール名や生成日時のコメント
D 処理の段階「入力」「承認」「確定」など、段階ごとの定義<sheet type="approve"> の中にSQLやルートシートごとに入力欄ではなく処理（SQL）が中心

自社でどれかを見分ける方法

  1. シート名を一覧にするXMLの中の「sheet」に当たるタグの name 属性を全部書き出します。VS Codeで <sheet を検索すると早いです。
  2. テスト環境の申請画面と見比べる画面のタブ名・ページ名と一致するならパターンA。印刷物と一致するならB。
  3. 中身の種類を数えるそのシートの中が入力項目中心か、SQL中心か、座標中心かを見ます。
  4. 小さく変えて確かめる（テスト環境のみ）ラベル文字を1つ変えて画面に反映されるか見ます。必ずテスト環境で、元に戻せる状態で行ってください。
  5. 先輩に答え合わせする「シートは画面のタブ単位という理解で合っていますか」と、推測を添えて聞くと短時間で答えてもらえます。

実物：通勤費申請の架空XMLを読む

ここでは説明用に作った通勤費申請のXMLを使います。タグ名・属性名は架空です。自社のXMLでは名前が違っても、似た役割の塊があるはずです。

commute_request.xml（架空の例）

<?xml version="1.0" encoding="UTF-8"?>
<form id="COMMUTE" name="通勤費申請" version="3">

  <!-- (A) 画面項目の定義 -->
  <sheet name="申請内容">
    <field id="startDate" type="date" label="適用開始日" required="true"/>
    <field id="transport" type="select" label="交通手段" required="true">
      <!-- (B) 選択肢をマスタからSQLで取得 -->
      <options>
        <sql><![CDATA[
          SELECT transport_cd AS value, transport_nm AS label
            FROM m_transport
           WHERE valid_from <= CURRENT_DATE
           ORDER BY sort_no
        ]]></sql>
      </options>
    </field>
    <field id="route" type="text" label="経路" maxLength="200" required="true"/>
    <field id="monthlyFare" type="number" label="1か月定期代" required="true">
      <check type="range" min="1" max="100000" message="1〜100,000円で入力してください"/>
    </field>
    <field id="attachment" type="file" label="経路の資料" required="false"/>
  </sheet>

  <!-- (C) 承認ルート -->
  <route>
    <step no="1" name="上長承認" approver="BOSS_OF_APPLICANT" canReturn="true"/>
    <step no="2" name="人事承認" approver="ROLE:HR" canReturn="true"/>
  </route>

  <!-- (D) 最終承認時にDBへ反映 -->
  <onComplete>
    <sql><![CDATA[
      UPDATE t_commute_allowance
         SET transport_cd = #{transport},
             route        = #{route},
             monthly_fare = #{monthlyFare},
             updated_at   = CURRENT_TIMESTAMP
       WHERE emp_no = #{applicantEmpNo}
         AND start_date = #{startDate}
    ]]></sql>
  </onComplete>
</form>

※ 実務では、該当行がないときにINSERTする処理や、履歴を残す処理が加わることが多いです。ここでは読み方の説明のため単純化しています。

XMLの塊 ↔ 画面の部品 ↔ DB の対応

図3 XMLの塊が、画面のどの部品とDBのどのテーブルにつながるか

SQLの中の #{transport} は何か：バインド変数

#{transport} は「ここに画面で入力された交通手段の値を入れてね」という差し込み口（バインド変数）です。XMLの field id="transport" と名前が対応しています。システムは値を安全にSQLへ渡すので、入力値に記号が含まれていてもSQLが壊れたり、悪意あるSQLが実行されたり（SQLインジェクション）しにくくなります。

書き方は製品によって違います。

書き方よく見る場所例
#{名前}MyBatis系、独自製品WHERE emp_no = #{empNo}
:名前Oracle系、JPA、一部製品WHERE emp_no = :empNo
?JDBCの素のSQLWHERE emp_no = ?（順番で対応）
${名前}MyBatisなど文字列をそのまま埋め込む方式。安全性が下がるので要注意
DBツールでそのまま実行しない

XMLから抜き出したSQLをDBツールに貼っても、#{empNo} のままでは動きません。テスト環境で、具体的な値（架空の社員番号など）に置き換えてから実行します。UPDATE文は本番で試さないこと、まず同じ条件のSELECTで対象件数を確認すること。SQLの読み方は06 自分で書くSQLも参照してください。

また、applicantEmpNo のように画面項目にない変数が使われていることがあります。これは「申請者の社員番号」「申請日」「申請ID」など、システムが自動で用意する変数です。どんな変数が使えるかは製品マニュアルや既存XMLを見て一覧にしておくと便利です。

改修時の注意：壊さないための5つの観点

1. 既存の申請中データへの影響

XMLを変えた瞬間、すでに上長承認待ち・差戻し中の申請がシステムの中に残っています。たとえば項目を削除すると、申請中データにはその値があるのに画面に出せない、確定SQLが値を見つけられない、といったことが起こりえます。

  • 申請中の件数を事前に確認する（申請データテーブルを状態で絞ってSELECT）
  • 製品がXMLのバージョン管理をしているか（古い申請は古い定義で動くか）を確認する
  • 必要なら「リリース前に申請中のものを処理してもらう」運用を相談する

2. 項目追加とDB列追加はセット

「通勤費申請に駐車場代の欄を追加したい」となったら、XMLのfieldを足すだけでは終わりません。確定時に保存したいならテーブルに列（例：parking_fee）を追加し、確定SQLにも追加します。列追加はDBの変更なので、手順書・ロールバック手順・リリース順序（DB変更が先、XMLが後）を決めます。

XMLfield 追加
DBALTER TABLE で列追加
確定SQLUPDATE に列を追加
周辺帳票・CSV・連携先

3. XML構文エラーの見つけ方

  • エディタのXML検証：VS Codeなら Red Hat の「XML」拡張を入れると、閉じ忘れや不正な文字に赤い波線が出ます。XSDがあれば、書けないタグも指摘してくれます。
  • xmllint（Linuxサーバーやgit bashで使えることが多い）：xmllint --noout commute_request.xml で、エラーがあれば行番号つきで表示されます。何も出なければ整形式です。XSDがあるなら xmllint --noout --schema form.xsd commute_request.xml。
  • ブラウザ：XMLファイルをブラウザで開くと、整形式でない場合はエラー位置が表示されます。
$ xmllint --noout commute_request.xml
commute_request.xml:14: parser error : StartTag: invalid element name
           WHERE valid_from <= CURRENT_DATE
                             ^
# → CDATAの外で < を使っている。CDATAで囲むか &lt; に置き換える

4. 差分比較で「何を変えたか」を必ず見る

XMLは長いので、意図しない変更（タブが崩れた、別の場所を消した）が紛れ込みやすいです。変更前と変更後を必ず比較してください。

  • WinMerge：Windowsで2つのファイルを左右に並べて差分表示。フォルダ単位の比較もできます。
  • git diff：Gitで管理されていれば git diff commute_request.xml で変更行だけが見られます。
  • レビュー依頼のときに差分を添えると、先輩も短時間で確認できます。

5. 文字コードと改行コード

宣言が Shift_JIS なのにUTF-8で保存した、改行コードがCRLFからLFに変わって差分が全行になった、というのもよくある事故です。保存前にエディタ右下の文字コード・改行表示を確認しましょう。

読み解き手順と、先輩に確認するリスト

知らない申請XMLを渡されたときは、次の順番で読むと迷いにくくなります。

  1. 全体を折りたたむVS Codeで「すべて折りたたむ」（Ctrl+K → Ctrl+0）をして、ルート要素の直下にある大きな塊だけを見ます。
  2. 塊に役割のラベルを貼る各塊が「画面」「選択肢」「チェック」「承認ルート」「確定処理」「帳票」のどれかをメモします。
  3. 画面と1対1で照合テスト環境で同じ申請画面を開き、項目のラベルとXMLのlabelを照らし合わせます。
  4. SQLを抜き出して読むSELECT（選択肢・初期値）とUPDATE/INSERT（確定処理）に分けて、対象テーブルを書き出します。
  5. バインド変数の出どころを確認#{...} が画面項目か、システム変数かを分類します。
  6. 承認ルートを紙に描く誰から誰へ、差戻しはどこへ戻るかを矢印で描きます。
  7. 自分の言葉で1枚にまとめる「この申請は、○○を入力し、上長→人事で承認され、確定時に○○テーブルを更新する」と3行で書けたら完了です。

自社のXMLで確認する項目（先輩・社内Wikiに聞くリスト）

よくあるつまずき

つまずき

SQLに < を足したら、申請画面ごと開かなくなった。

対策

CDATAの中に書いているか確認。外なら &lt; に。保存前に xmllint かエディタ検証を通す。

つまずき

XMLから抜いたSQLをDBツールで実行したら「構文エラー」。

対策

#{...} を値に置き換える。&lt; が残っていたら < に戻す。

つまずき

項目を追加したのに、承認後のデータに値が入らない。

対策

fieldだけでなく、確定SQLとテーブル列も追加したか確認。field id とバインド変数名のつづりも照合。

つまずき

XML全体をAIに貼って「解説して」と頼み、そのまま信じた。

対策

社員番号や実データが入っていないか確認してから使う。AIの説明は画面・テスト環境で1つずつ確かめる（10 AIと一緒に強くなる）。

小さな成功体験のつくり方

テスト環境で、ラベル文字を1つだけ変えて画面に反映させてみる。それができたら、選択肢SQLにORDER BYを足してみる。「XMLを触ると画面がこう変わる」を自分の手で一度体験すると、XMLが急に身近になります。

練習問題

Q1. 次のXMLは整形式ではありません。どこが問題でしょう？
<field id="fare"><label>定期代</field></label>

入れ子が交差しています。<label> を先に閉じてから </field> で閉じる必要があります。正しくは <field id="fare"><label>定期代</label></field>。

Q2. 「通勤費申請に経路の資料の添付を必須にしたい」。架空のXMLでは、まずどこを見ますか？

(A) の field id="attachment" の required="false" を見ます。ただし、変えるだけで終わりではありません。申請中のデータ（添付なしで出された申請）が差戻しされたとき再提出できるか、確定SQLで添付を使うか、帳票に影響するかも確認します。

Q3. 人事が最終承認したのに、通勤手当テーブルが更新されていません。疑う順番は？

①アプリのログで確定SQLのエラーを確認 → ②確定SQLのWHERE条件（emp_no と start_date が一致する行が本当にあるか。UPDATEは0件でもエラーにならない）→ ③バインド変数名と field id の対応 → ④承認が本当に「最終」ステップまで進んだか、の順が効率的です。

Q4. SQL中の #{empNo}、:empNo、? の共通点と違いは？

どれも「後から値を差し込む場所（バインド変数）」です。違いは書き方で、名前で対応づけるか（#{} や :）、出現順で対応づけるか（?）です。どれを使うかは製品・ライブラリが決めます。

用語まとめ

要素
開始タグから終了タグまでのひとかたまり。
属性
開始タグの中に 名前="値" で書く補足情報。
ルート要素
XML全体を包む唯一の一番外側の要素。
XML宣言
1行目の <?xml ... ?>。バージョンと文字コードを示す。
エンティティ
&lt; &amp; など、特別な文字を表す書き方。
CDATA
<![CDATA[ ... ]]>。中身をただの文字として扱う囲い。SQLを書くのに便利。
整形式
XMLの文法として正しい状態。
妥当（valid）
整形式であり、さらにXSD/DTDの規則に従っている状態。
XSD / DTD
「どのタグをどこに書けるか」を決める規則ファイル。
バインド変数
SQL中の値の差し込み口。#{}、:名前、? など。
承認ワークフロー
申請者 → 上長 → 人事のように、申請を回して承認・差戻しする仕組み。
確定処理
最終承認時に本番データ（社員マスタ等）を更新する処理。
xmllint
XMLの構文や規則をチェックするコマンドラインツール。
