CHAPTER 03 ・ ことばを読む

読めるJava

目標は「書ける」より先に「読める」です。勤怠の打刻や残業計算のコードを題材に、Java の文法を「読むのに必要な分だけ」押さえ、ソースのたどり方とスタックトレースの読み始め方を身につけます。

この章でわかること
  • クラス・フィールド・メソッド・コンストラクタなど、Java のコードの「形」の見分け方
  • 勤怠でよく出る型（int / long / String / BigDecimal / LocalDate / LocalDateTime / Duration）の意味
  • null・例外・インタフェース・アノテーションを「読んで意味がわかる」レベル
  • Controller から呼び出しをたどるソースの読み方と、スタックトレースの読み始め方
  • .java が JVM で動くまでの流れと、JDK / JRE / JVM の関係
なぜ「読める」からたとえ動くまでクラスの形型if・for・List・Mapnull と例外インタフェース等パッケージラムダ・Streamソースを読むコツスタックトレースつまずき練習問題用語明日から

なぜ「書ける」より「読める」が先なのか

11か月目のいま、あなたの仕事で Java に触れる場面を思い出してみてください。ゼロから新しいクラスを書く機会より、すでにあるコードを読んで「なぜこの残業時間になったのか」「このエラーはどこで起きたのか」を調べる機会のほうが、ずっと多いはずです。

改修も同じです。既存の処理の流れを読めないまま書き足すと、思わぬところを壊します。逆に、読めるようになると、AI が出してきた修正案が「本当にその場所でよいのか」を自分で判断できるようになります。AI の答えをうのみにする不安は、読む力でかなり小さくできます。

この章では、Java の文法をすべて覚えることはしません。勤怠システムのコードを読むときに出てくる頻度が高いものに絞って、「これは何をしている行か」を見分けられるようになることを目指します。

この章のコードについて

登場するクラス名・パッケージ名（com.example.kintai、AttendanceRecord など）は説明用の一般的な例です。実際の現場のコードとは名前や構成が違います。読み終えたら、現場のコードで「似た形」を探してみてください。

たとえ：Java のコードは「業務マニュアル」

コードを外国語の文章だと思うと身構えてしまいますが、Java のコードは構造のはっきりした業務マニュアルに近いものです。

業務マニュアル「勤怠記録票」という書式。社員番号・日付・出勤時刻・退勤時刻の欄がある。
=
Javaクラスとフィールド。AttendanceRecord クラスが書式、clockIn などのフィールドが欄にあたる。
業務マニュアル「残業時間の求め方：退勤−出勤−休憩、そこから所定 8 時間を引く」という手順。
=
Javaメソッド。calcOvertimeMinutes() のように、名前の付いた手順のまとまり。
業務マニュアル記録票の1枚1枚。田中さんの 10/31 分、佐藤さんの 10/31 分…。
=
Javaオブジェクト（インスタンス）。new AttendanceRecord(...) で書式から1枚つくる。

マニュアルを読むとき、最初から最後まで一字一句追う人はいません。目次を見て、関係ある章へ飛び、そこから「詳細は○ページ参照」をたどります。コードも同じで、入口を見つけて、参照をたどる読み方をします。その方法は後半の「ソースを読むコツ」で扱います。

.java が動くまで：コンパイルと JDK / JRE / JVM

あなたが読む .java ファイルは、そのままでは動きません。コンパイラ（javac）が、JVM 向けの命令であるバイトコード（.class ファイル）に変換し、それを JVM（Java 仮想マシン）が実行します。

  • JVM：.class を実行するエンジン。Tomcat も Spring Boot アプリも、JVM の上で動く「1つの Java プロセス」です。前章の ps -ef | grep java で見えたのがこれです。
  • JRE：JVM ＋ 標準ライブラリ。「動かすだけ」に必要なもの。
  • JDK：JRE ＋ 開発ツール（コンパイラなど）。開発するなら JDK が必要です。なお Java 11 以降、Oracle などは JRE 単体の配布をやめ、JDK として配布するのが一般的になりました。

実際の開発では javac を手で打つことはほとんどなく、Maven や Gradle といったビルドツールが、コンパイル・ライブラリの取得・jar/war へのまとめをまとめて行います。これは 05 開発環境をつくる で扱います。

Java のバージョンを確かめる

java -version で実行環境のバージョンがわかります。Java 8 と 17 では使える書き方が少し違い、エラーメッセージの親切さも違います。現場のシステムが何のバージョンで動いているかは、確認しておきたい項目の1つです。

クラスの形を見分ける：フィールド・コンストラクタ・メソッド

まずは勤怠記録1件を表すクラスを読んでみましょう。最初は意味がわからなくて大丈夫です。後の図で、どの部分が何かを見分けます。

AttendanceRecord.java（一般的な例）
package com.example.kintai.domain;

import java.time.Duration;
import java.time.LocalDate;
import java.time.LocalDateTime;

/** 1人・1日分の勤怠記録 */
public class AttendanceRecord {

    // ---- フィールド（このクラスが持つデータ）----
    private long employeeId;          // 社員ID
    private LocalDate workDate;        // 勤務日
    private LocalDateTime clockIn;     // 出勤時刻
    private LocalDateTime clockOut;    // 退勤時刻（未打刻なら null）
    private int breakMinutes;          // 休憩（分）

    private static final int STANDARD_MINUTES = 8 * 60;  // 所定労働 480分

    // ---- コンストラクタ（new したときに呼ばれる初期化）----
    public AttendanceRecord(long employeeId, LocalDate workDate, LocalDateTime clockIn) {
        this.employeeId = employeeId;
        this.workDate = workDate;
        this.clockIn = clockIn;
        this.breakMinutes = 60;
    }

    // ---- メソッド（このクラスができること）----
    public void punchOut(LocalDateTime time) {
        this.clockOut = time;
    }

    public long calcOvertimeMinutes() {
        if (clockOut == null) {
            return 0;                    // 退勤前は残業なし扱い
        }
        long worked = Duration.between(clockIn, clockOut).toMinutes() - breakMinutes;
        return Math.max(0, worked - STANDARD_MINUTES);
    }

    public LocalDateTime getClockOut() {   // ゲッター：値を取り出すだけ
        return clockOut;
    }
}

読むときのポイント

  • private / public：アクセスできる範囲です。private はそのクラスの中だけ、public はどこからでも。フィールドは private にして、外からは getClockOut() のようなメソッド経由で触らせるのが一般的です。
  • this.clockIn = clockIn;：左の this.clockIn はフィールド、右の clockIn は引数です。名前が同じなので this. で区別しています。
  • static final：static は「1枚1枚の記録票ではなく、書式そのものに属する」、final は「変更できない」。大文字の名前は定数の慣習です。
  • 使う側：AttendanceRecord rec = new AttendanceRecord(1001L, today, now); で1枚つくり、rec.punchOut(now); や rec.calcOvertimeMinutes() のように「変数名.メソッド名(…)」で呼びます。
Lombok に注意

現場のコードで、フィールドだけ並んでいてゲッターが見当たらないのにクラスの上に @Data や @Getter が付いている場合、Lombok というライブラリがコンパイル時にゲッター等を自動生成しています。「定義が見つからない」と焦らなくて大丈夫です。

勤怠でよく出る型

Java では、変数やフィールドには必ず型（どんな種類の値を入れるか）があります。型を見れば、その値で何ができるかの見当がつきます。

型中身勤怠での例読むときの注意
int整数（約±21億）休憩分数、有給残日数整数どうしの割り算は小数が切り捨て（90 / 60 は 1）
longより大きな整数社員ID、分単位の時間数字の後ろの L（1001L）は long の印
booleantrue / false締め済みフラグisClosed() のような名前が多い
String文字列氏名、申請種別コード中身の比較は == ではなく equals()
BigDecimal正確な10進数通勤費、時給、手当額計算は add() などのメソッド。比較は compareTo()
LocalDate日付（時刻なし）勤務日、有給取得日タイムゾーンを持たない
LocalDateTime日付＋時刻出勤・退勤時刻isBefore() / isAfter() で前後比較
Duration時間の長さ実労働時間Duration.between(開始, 終了).toMinutes()
お金に double を使わない理由
double a = 0.1 + 0.2;
System.out.println(a);           // 0.30000000000000004  ← 2進数の誤差

BigDecimal fare = new BigDecimal("320");      // 通勤費 片道
BigDecimal monthly = fare.multiply(BigDecimal.valueOf(2 * 20));
System.out.println(monthly);     // 12800  ← 正確

小文字で始まる int・long・boolean などはプリミティブ型で、値そのものを持ち、null になりません。大文字で始まる String・BigDecimal・LocalDate などは参照型（クラス）で、null になりえます。Integer・Long のように、プリミティブ型をクラスにした版もあり、こちらも null になりえます。

if・for・List・Map：処理の流れとデータのまとまり

メソッドの中身は、上から順に実行されるのが基本です。そこに「条件で分ける（if）」「繰り返す（for）」が加わります。複数のデータをまとめて扱うのが List と Map です。

1か月分の残業を合計する（一般的な例）
public long sumMonthlyOvertime(List<AttendanceRecord> records) {
    long total = 0;
    for (AttendanceRecord rec : records) {      // records の1件ずつを rec に入れて繰り返す
        if (rec.isHoliday()) {
            continue;                          // 休日はこの集計の対象外。次の1件へ
        }
        total += rec.calcOvertimeMinutes();     // total = total + … と同じ
    }
    return total;
}
  • List<AttendanceRecord>：AttendanceRecord が順番に並んだリスト。< > の中は「何のリストか」を表します（ジェネリクス）。
  • for (型 変数 : リスト)：拡張 for 文。リストの要素を1つずつ取り出して繰り返します。for (int i = 0; i < n; i++) という数を数える形もあります。
  • continue は「今回の繰り返しを飛ばして次へ」、break は「繰り返しを終わる」、return は「メソッドを終わって値を返す」です。
  • if の条件で使う && は「かつ」、|| は「または」、! は「〜でない」です。
Map：キーで値を引く（社員IDごとの残業合計）
Map<Long, Long> overtimeByEmployee = new HashMap<>();
overtimeByEmployee.put(1001L, 1260L);    // 田中さん 21時間
overtimeByEmployee.put(1002L, 300L);     // 佐藤さん 5時間

Long tanaka = overtimeByEmployee.get(1001L);   // 1260
Long nobody = overtimeByEmployee.get(9999L);   // キーがないと null が返る

Map<キーの型, 値の型> は、辞書のように「キーを渡すと値が返る」入れ物です。get() でキーが見つからないと例外ではなく null が返ってくる点が、次の節につながります。

null と NullPointerException、そして例外

null は「何も入っていない」

参照型の変数には、null（何も指していない）が入ることがあります。null の変数に対してメソッドを呼ぶと、NullPointerException（略して NPE）が起きます。勤怠システムで最もよく見る例外の1つです。

退勤打刻を忘れた日に起きる NPE（一般的な例）
LocalDateTime out = rec.getClockOut();          // 退勤未打刻なので null
if (out.isAfter(lateNightStart)) {             // null.isAfter(…) → NPE！
    ...
}

Java 14 以降（標準で有効になったのは 15 以降）では、NPE のメッセージに「何が null だったか」が出るようになりました。

java.lang.NullPointerException: Cannot invoke "java.time.LocalDateTime.isAfter(java.time.chrono.ChronoLocalDateTime)" because "out" is null

変数名（ここでは "out"）が表示されるかはコンパイル時の設定によります。表示されない場合は "<local4>" のような番号になります。

防ぎ方として、コードの中に if (out != null) のような null チェックが書かれていることがよくあります。読むときは「この値が null になるのはどんなときか（業務的には、どんな操作をした・しなかったときか）」を考えると、原因に近づけます。

例外：うまくいかなかったことを知らせる仕組み

例外は「ここで処理を続けられない」ことを呼び出し元に知らせる仕組みです。例外が起きると、その場で処理が中断され、呼び出し元へ、さらにその呼び出し元へと投げ上げられていきます。どこかで catch されれば、そこで対処されます。誰も catch しなければ、最終的に Tomcat まで届いて 500 エラーになります。

try-catch と throws（一般的な例）
// throws：このメソッドは IOException を投げることがある、という宣言
public void exportCsv(Path file, List<AttendanceRecord> list) throws IOException {
    Files.writeString(file, toCsv(list));
}

public void runMonthlyClose() {
    try {
        exportCsv(Path.of("/data/out/kintai_202610.csv"), records);
    } catch (IOException e) {
        log.error("給与連携CSVの出力に失敗しました", e);   // ログに残す
        throw new IllegalStateException("締め処理中断", e); // 包んで投げ直す
    } finally {
        // 成功しても失敗しても必ず実行される（後片付け）
    }
}
種類意味例コード上の特徴
チェック例外起こりうると予想でき、対処を強制されるものIOException、SQLExceptioncatch するか、throws で宣言しないとコンパイルエラー
非チェック例外主にプログラムの誤りや想定外の状態NullPointerException、IllegalArgumentException、Spring の DataAccessExceptionRuntimeException の子孫。宣言なしで投げられる
「握りつぶし」に注意して読む

catch (Exception e) { } のように、catch して何もしないコードを見かけたら要注意です。エラーが起きてもログに何も残らず、「エラーは出ていないのにデータがおかしい」という調査の難しい障害の原因になります。

インタフェース・継承・アノテーションの最低限

インタフェース：「できること」の約束

インタフェースは、メソッドの名前と形だけを決めた約束です。中身（実装）は別のクラスが書きます。

public interface OvertimeCalculator {
    long calc(AttendanceRecord rec);           // 本体がない：約束だけ
}

public class StandardOvertimeCalculator implements OvertimeCalculator {
    @Override
    public long calc(AttendanceRecord rec) {    // 約束を守って中身を書く
        return rec.calcOvertimeMinutes();
    }
}

読むときに困るのは、「定義へ移動」でインタフェースに飛ぶと中身がないことです。そのときは IDE の「実装へ移動」（IntelliJ IDEA なら Ctrl+Alt+B、Eclipse なら Ctrl+T など）で、implements しているクラスを探します。Spring Data JPA の Repository のように、実装クラスがソース上に存在せず、実行時に自動で作られるものもあります（04章で扱います）。

継承：既存のクラスを土台にする

class ShiftAttendanceRecord extends AttendanceRecord のように extends と書くと、親クラスのフィールドやメソッドを引き継いだ子クラスになります。子クラスで同じ名前のメソッドを書き直すことをオーバーライドと呼び、@Override はその目印です。「このメソッドが見つからない」と思ったら、親クラスに書かれていないか確かめましょう。

アノテーション：@ から始まる「目印」

@Override、@Controller、@Transactional のように @ から始まるものはアノテーションです。それ自体は処理を書いたものではなく、コンパイラやフレームワーク（Spring など）に向けた付箋・目印です。「このクラスは画面の入口です」「このメソッドはトランザクションで囲んでください」と、裏で動く仕組みに伝えています。

Spring Boot のコードはアノテーションだらけで、ここが「何が起きているのかわからない」原因になりがちです。それぞれの意味は 04 Spring Bootの正体 でくわしく扱います。この章では「@ は目印。誰かがそれを見て動いている」とだけ覚えておけば十分です。

パッケージとフォルダ構成、import

Java のクラスはパッケージという名前空間に分けて整理されます。パッケージ名はそのままフォルダの階層に対応します。

Maven / Gradle プロジェクトの一般的なフォルダ構成
kintai/
├── pom.xml                         ← ビルド設定（05章）
└── src/
    ├── main/
    │   ├── java/
    │   │   └── com/example/kintai/
    │   │       ├── KintaiApplication.java   ← 起動クラス
    │   │       ├── controller/   PunchController.java     ← 画面・APIの入口
    │   │       ├── service/      PunchService.java        ← 業務ロジック
    │   │       ├── repository/   AttendanceRepository.java← DBアクセス
    │   │       └── domain/       AttendanceRecord.java    ← データの形
    │   └── resources/

    │       └── static/                 ← CSS・JS・画像

com/example/kintai/controller/PunchController.java の先頭には package com.example.kintai.controller; と書かれています。パッケージ名は、会社のドメインを逆にした形（com.example）から始めるのが慣習です。

import は「別のパッケージのクラスを、短い名前で使います」という宣言です。import java.time.LocalDate; があるから、本文で LocalDate とだけ書けます。読むときは、import の一覧を眺めるだけで「このクラスは何に依存しているか」（DB を触るのか、ファイルを書くのか、Spring の何を使うのか）の見当がつきます。

Java 8 以降の記法：ラムダ・Stream・Optional を「読める」ように

最近のコードには、矢印 -> や .stream() がよく出てきます。書けなくてよいので、for 文に読み替えられることを目指しましょう。

for 文で書いた場合 
List<Long> ids = new ArrayList<>();
for (AttendanceRecord r : records) {
    if (r.calcOvertimeMinutes() > 45 * 60) {
        ids.add(r.getEmployeeId());
    }
}
Stream で書いた場合（同じ意味） 
List<Long> ids = records.stream()
    .filter(r -> r.calcOvertimeMinutes() > 45 * 60)
    .map(r -> r.getEmployeeId())
    .collect(Collectors.toList());
  • r -> 式（ラムダ式）：「r を受け取って、式の結果を返す小さな関数」です。r は1件ずつの要素だと読めば OK です。
  • .filter(条件)：条件に合うものだけ残す（for ＋ if）。
  • .map(変換)：1件ずつ別の値に変える（ここでは記録 → 社員ID）。
  • .collect(...)：結果をリストなどにまとめる。Java 16 以降は .toList() と書くこともあります。
  • AttendanceRecord::getEmployeeId：メソッド参照。r -> r.getEmployeeId() の省略形です。
Optional：「ないかもしれない」を表す箱
Optional<AttendanceRecord> today = repository.findByEmployeeIdAndWorkDate(1001L, date);

if (today.isPresent()) { ... }                      // 中身があるか
AttendanceRecord rec = today.orElseThrow(
    () -> new IllegalStateException("出勤打刻がありません"));  // なければ例外
long ot = today.map(AttendanceRecord::calcOvertimeMinutes).orElse(0L);  // なければ 0

Optional は null を直接返す代わりに「中身があるかもしれないし、ないかもしれない箱」を返す書き方です。orElse(…) は「なければこれ」、orElseThrow(…) は「なければ例外」と読みます。

ソースを読むコツ：入口から呼び出しをたどる

勤怠システム全体のソースは数百〜数千ファイルあるかもしれません。全部を読む必要はありません。調べたい画面操作の入口を見つけ、そこから呼び出しを1本たどるのが基本です。

IDE の3つの機能を使い倒す

ソースを読むときに、テキストエディタで目で探すのは大変です。IDE（IntelliJ IDEA、Eclipse、VS Code など）の機能を使いましょう。キー操作は IDE や設定によって違うので、メニューの名前で覚えておくと安心です。

機能何がわかるか操作の例
定義へ移動このメソッド・クラスの中身はどこ？IntelliJ：Ctrl+クリック、Ctrl+B／Eclipse：F3／VS Code：F12
実装へ移動インタフェースの中身を書いたクラスはどれ？IntelliJ：Ctrl+Alt+B／Eclipse：Ctrl+T
呼び出し階層このメソッドを誰が呼んでいる？IntelliJ：Ctrl+Alt+H／Eclipse：Ctrl+Alt+H
全文検索URL・メッセージ文言・テーブル名はどこに出てくる？IntelliJ：Ctrl+Shift+F／Eclipse：Ctrl+H

ログ出力の位置を手がかりにする

アプリのログに出ている文言（例：「出勤打刻を登録しました employeeId=1001」）をソース全体から検索すると、その行を出力している場所がすぐ見つかります。ログは「実際にその行まで処理が進んだ」証拠なので、ログに出ている最後のメッセージの次の処理あたりで何かが起きた、と範囲を絞れます。

PunchService.java（一般的な例）
@Service
public class PunchService {
    private static final Logger log = LoggerFactory.getLogger(PunchService.class);
    private final AttendanceRepository attendanceRepository;

    public PunchService(AttendanceRepository attendanceRepository) {
        this.attendanceRepository = attendanceRepository;
    }

    @Transactional
    public void punchIn(long employeeId, LocalDateTime now) {
        log.info("出勤打刻 開始 employeeId={}", employeeId);
        if (attendanceRepository.existsByEmployeeIdAndWorkDate(employeeId, now.toLocalDate())) {
            throw new AlreadyPunchedException(employeeId);
        }
        attendanceRepository.save(new AttendanceRecord(employeeId, now.toLocalDate(), now));
        log.info("出勤打刻を登録しました employeeId={}", employeeId);
    }
}

{} はログの埋め込み位置で、後ろの引数の値が入ります。「開始」は出ているのに「登録しました」が出ていなければ、その間（存在チェックか save）で何かが起きた、と読めます。

スタックトレースの読み方・入門

例外が起きると、ログに何十行もの at ... が並んだスタックトレースが出ます。これは「例外が起きた場所」と「そこに至るまでの呼び出しの道のり」の記録です。全部読む必要はありません。まず見るのは3か所です。

アプリログに出たスタックトレース（一般的な例・一部省略）

  2. 自社パッケージの最初の行：どこで起きたか上から見ていき、com.example.kintai で始まる最初の行を探します。PunchService.java:24、つまり PunchService の 24 行目です。その下の行が「誰が呼んだか」（PunchController の 31 行目）です。Spring や Tomcat の行は、ふだんは読み飛ばして構いません。
  3. Caused by：本当の原因例外が別の例外に包まれていると、Caused by: が続きます。複数あるときは一番下の Caused by が根本原因であることが多いです。ここでは PostgreSQL が「同じ社員・同じ日の行がすでにある」と言っています。

この3か所から、「田中さん（1001）の 10/31 の出勤が二重に登録されようとして、DB の一意制約で止まった」とわかります。次に考えるのは、なぜ PunchService の存在チェックをすり抜けたのか（ボタンの連打で同時に2リクエスト来た？）です。ログの読み方と障害調査の進め方は 07 ログと障害調査 でくわしく扱います。

1. 先頭行例外名＋メッセージで「何が」
2. 自社の最初の atファイル名:行番号で「どこで」
3. 最後の Caused by根本原因「なぜ」
4. ソースを開くその行と前後を読む

よくあるつまずき

文字列を == で比べる 
if (kind == "OVERTIME") { ... }

見た目が同じ文字列でも、別々に作られたオブジェクトだと false になることがあります。

equals で比べる 
if ("OVERTIME".equals(kind)) { ... }

定数を左に書くと、kind が null でも NPE になりません。

整数の割り算で時間を求める 
int minutes = 90;
double hours = minutes / 60;   // 1.0

int 同士の割り算で先に小数が切り捨てられ、その後で double になります。

どちらかを小数にする 
double hours = minutes / 60.0; // 1.5

勤怠の丸め（15分単位切り捨てなど）が意図的に書かれていることもあるので、仕様と照らします。

BigDecimal を equals で比べる 
new BigDecimal("1.0").equals(new BigDecimal("1.00")) // false

equals は小数点以下の桁数（スケール）まで比べます。

compareTo で比べる 
new BigDecimal("1.0").compareTo(new BigDecimal("1.00")) == 0 // true
スタックトレースの1行目だけ見て判断する

「DataIntegrityViolationException だからアプリのバグ」と決めつける。

Caused by まで読む

根本原因は DB の一意制約違反で、二重送信が引き金かもしれません。最後の Caused by と、自社コードの行をセットで見ます。

わからない行に出会ったら

1行ずつ AI に「この行は何をしていますか」と聞くのは良い使い方です。ただし、答えを読んだら「自分の言葉で、業務の意味に言い換える」（例：「退勤が null なら残業 0 として返している」）ところまでやると、知識が残ります。

練習問題：コードを読んで結果を当てる

Q1. 次のコードを実行すると、何が表示されますか？ 
int worked = 530;         // 実労働（分）
int standard = 480;
int over = worked - standard;
System.out.println(over / 60 + "時間" + over % 60 + "分");

0時間50分 です。over は 50。50 / 60 は整数の割り算なので 0、50 % 60（余り）は 50 です。+ は文字列とつなぐと文字列の連結になります。

Q2. 次のメソッドに、退勤打刻のない（clockOut が null の）記録を渡すとどうなりますか？ 
public boolean isLateNight(AttendanceRecord rec) {
    LocalTime t = rec.getClockOut().toLocalTime();
    return t.isAfter(LocalTime.of(22, 0));
}

NullPointerException が発生します。rec.getClockOut() が null を返し、その null に対して .toLocalTime() を呼んでいるためです。呼び出し元で catch されなければ、画面なら 500 エラー、バッチなら処理が異常終了します。防ぐには、先に if (rec.getClockOut() == null) return false; のようなチェックを入れます（null のときに何を返すべきかは業務仕様で決めます）。

Q3. 次の Stream の結果 names には何が入りますか？ 
// members: 田中(残業30h), 佐藤(5h), 鈴木(50h), 高橋(46h)
List<String> names = members.stream()
    .filter(m -> m.getOvertimeHours() >= 45)
    .map(m -> m.getName())
    .collect(Collectors.toList());

["鈴木", "高橋"] です。filter で残業 45 時間以上の人だけ残し、map で名前に変換し、リストにまとめています。for 文に直すと「残業が45以上なら名前をリストに追加する」繰り返しです。

Q4. スタックトレースに次の3行がありました。最初に開くべきソースはどれで、何行目ですか？ 
java.lang.IllegalArgumentException: breakMinutes must be >= 0
	at com.example.kintai.domain.AttendanceRecord.setBreakMinutes(AttendanceRecord.java:58)
	at com.example.kintai.service.CorrectionService.apply(CorrectionService.java:41)

例外が投げられたのは AttendanceRecord.java の 58 行目（休憩がマイナスなら例外を投げるチェック）です。ただし、それは「おかしな値を見つけて止めた」場所なので、実際に調べたいのはその値を渡した CorrectionService.java の 41 行目、つまり「打刻修正で休憩時間をどう計算したか」です。両方を開き、下（呼び出し元）から値の出どころをたどります。

用語まとめ

クラス
データ（フィールド）と手順（メソッド）をまとめた設計図・書式。
オブジェクト
クラスから new で作られた1つ1つの実体。インスタンスとも呼ぶ。
フィールド
クラスが持つデータ。メソッドの外に「型 名前;」で書く。
メソッド
名前の付いた処理のまとまり。「戻り値の型 名前(引数)」。
コンストラクタ
new したときに呼ばれる初期化処理。クラスと同名で戻り値の型がない。
型
値の種類。プリミティブ型（int など、null にならない）と参照型（String など、null になりうる）。
null
参照型の変数が何も指していない状態。
NullPointerException
null に対してメソッドを呼んだときなどに起きる例外。
例外
処理を続けられないことを呼び出し元へ知らせる仕組み。try-catch で受け止める。
チェック例外
catch か throws 宣言が必須の例外。IOException など。
非チェック例外
RuntimeException の子孫。宣言なしで投げられる。
インタフェース
メソッドの形だけを決めた約束。implements したクラスが中身を書く。
継承
extends で親クラスの機能を引き継ぐこと。
アノテーション
@ から始まる目印。コンパイラやフレームワークに意味を伝える。
パッケージ
クラスを整理する名前空間。フォルダ階層と対応する。
ラムダ式
x -> 式 の形の小さな関数。
Stream
filter・map などでデータの流れを処理する書き方。
Optional
値が「あるかもしれない・ないかもしれない」ことを表す箱。
スタックトレース
例外が起きた場所と、そこまでの呼び出しの道のりの記録。
JVM / JRE / JDK
実行エンジン / それ＋標準ライブラリ / それ＋開発ツール。
