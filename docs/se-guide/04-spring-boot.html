Spring Bootの正体

勤怠システムの中で毎日動いている Spring Boot を「何となく使っているもの」から「仕組みを説明できるもの」に変えます。DI、3層構造、アノテーション、設定ファイル、トランザクション、起動の流れを、勤怠の例で順番に見ていきます。

Spring Boot とは何か（一言でいうと）

勤怠システムのソースを開くと、@RestController や @Autowired といった「@ から始まる謎の記号」がたくさん出てきます。ログ調査のたびにAIに聞けば答えは返ってきますが、毎回その場限りで終わってしまう。そう感じているなら、まずは全体の正体をつかむのが近道です。

一言でいうと

Spring Boot は、Java で業務Webアプリを作るためのフレームワーク（Spring Framework）を、面倒な設定をほとんど書かずにすぐ動かせるようにしたものです。

もともと Spring Framework という巨大な仕組みがあり、昔は XML の設定ファイルを何百行も書かないと動きませんでした。Spring Boot はそこに「よく使う組み合わせを最初から用意しておく（自動設定）」「Tomcat を中に組み込んで、main メソッドを実行するだけで起動できる」という仕組みを足したものです。つまり Spring Boot は Spring の代わりではなく、Spring を使いやすくする包み紙です。

フレームワークとライブラリの違い：ハリウッドの原則

「フレームワーク」と「ライブラリ」は似た言葉ですが、主導権がどちらにあるかが違います。

ライブラリ：自分が呼ぶ

自分のコードが主役で、必要なときに道具を呼び出します。例：日付計算のために LocalDate.now() を呼ぶ、CSV読み込みライブラリを呼ぶ。流れは自分が決めます。

フレームワーク：自分が呼ばれる

枠組み（フレームワーク）が主役で、自分のコードは「決められた場所」に書いておくと、必要なときに呼ばれます。例：/api/timecards にリクエストが来たら、Spring が打刻メソッドを呼ぶ。

これをハリウッドの原則（Don't call us, we'll call you. ＝ 「こちらから連絡するので、電話してこないでください」）と呼びます。オーディションに来た俳優に向けた言葉が由来です。Spring Boot のコードを読んでいて「このメソッド、どこからも呼ばれていないのに動いている」と感じたら、それは Spring が呼んでいるのです。main から順に追っても処理が見つからないのは、あなたの読み方が悪いのではなく、フレームワークの性質です。

読むときのコツ

「誰が呼んでいるか」ではなく「どんな条件で呼ばれるか」を探します。URL（@GetMapping("/xxx")）、時刻（@Scheduled）、起動時（@PostConstruct）などが「呼ばれる条件」です。

DI（依存性注入）と IoC コンテナ

Spring の中心にある考え方が DI（Dependency Injection：依存性注入）です。難しそうな名前ですが、やっていることは単純です。

たとえ話新しい部署に配属された日、机の上にはもうPC・電話・文房具が置いてある。自分でPCを組み立てたり、電話回線を引いたりしない。会社の備品係が用意して置いてくれる。
＝
Spring ではクラスが必要とする部品（Mapper や他の Service）を自分で new しない。IoC コンテナが起動時に部品を作っておき、コンストラクタ経由で渡してくれる。

「依存」とは、あるクラスが仕事をするために必要な別のクラスのことです。残業申請を処理する OvertimeService は、DB を操作する OvertimeMapper に依存しています。それを外から「注入」するので依存性注入です。IoC（Inversion of Control：制御の反転）は、前の節のハリウッドの原則と同じ意味で、「部品の生成や呼び出しの主導権がフレームワーク側にある」ことを指します。部品を管理する入れ物を IoC コンテナ（または ApplicationContext）と呼び、管理されている部品を Bean（ビーン）と呼びます。

Bean にするための目印（ステレオタイプ・アノテーション）

クラスに次のアノテーションを付けると、起動時に Spring が見つけて Bean として登録します（これをコンポーネントスキャンと言います）。機能的にはどれも「Bean にして」という意味で、名前は役割を人間に伝えるためのラベルです（一部、例外変換などの小さな違いはあります）。

アノテーション付ける場所勤怠での例
@Component汎用の部品日付計算ユーティリティ、CSV出力部品
@Service業務ロジック層TimecardService（打刻）、OvertimeService（残業申請）
@RepositoryDBアクセス層EmployeeRepository（JPA や JdbcTemplate の場合）
@Controller画面（HTML）を返す入口勤怠一覧画面（Thymeleaf や JSP を返す）
@RestControllerJSON を返す入口打刻API /api/timecards
@Autowired注入してほしい場所フィールドやコンストラクタに付ける

MyBatis の Mapper インターフェースには @Repository ではなく @Mapper が付くのが一般的です（後述）。

コンストラクタインジェクションが推奨される理由

注入の書き方は主に2種類あります。現場の古いコードではフィールドに @Autowired が付いていることも多いですが、今はコンストラクタで受け取る書き方が推奨されています。

フィールドインジェクション（古いコードでよく見る）
@Service
public class OvertimeService {
    @Autowired
    private OvertimeMapper overtimeMapper;   // Springが後から差し込む
}
コンストラクタインジェクション（推奨）
@Service
public class OvertimeService {
    private final OvertimeMapper overtimeMapper;
    private final MailSender mailSender;

    // コンストラクタが1つだけなら @Autowired は省略できる（Spring 4.3以降）
    public OvertimeService(OvertimeMapper overtimeMapper, MailSender mailSender) {
        this.overtimeMapper = overtimeMapper;
        this.mailSender = mailSender;
    }
}

コンストラクタ方式だと、final にできる（途中で入れ替わらない）、必要な部品が一目でわかる、テストで偽物（モック）を渡しやすい、という利点があります。Lombok の @RequiredArgsConstructor が付いていたら、「final フィールドを受け取るコンストラクタを自動生成している」という意味です。コンストラクタが見当たらなくても驚かないでください。

3層構造：Controller → Service → Repository/Mapper → DB

Spring Boot の業務アプリは、ほぼ必ず役割ごとに層（レイヤー）が分かれています。役所の窓口にたとえると、Controller は受付窓口（用件を聞き、書類の不備をチェック）、Service は担当課（ルールに従って判断）、Mapper/Repository は書庫係（台帳の出し入れだけをする）です。窓口の人が勝手に台帳を書き換えないのと同じで、層を飛ばさないのが原則です。

勤怠の例1：打刻API

// Controller：受付。中身の判断はしない
@RestController
@RequestMapping("/api/timecards")
public class TimecardController {
    private final TimecardService timecardService;
    public TimecardController(TimecardService timecardService) {
        this.timecardService = timecardService;
    }

    @PostMapping
    public PunchResult punch(@RequestBody PunchRequest req) {
        return timecardService.punch(req.getEmployeeId(), req.getType());
    }
}

// Service：判断。業務ルールはここに集まる
@Service
public class TimecardService {
    private final TimecardMapper timecardMapper;
    public TimecardService(TimecardMapper timecardMapper) {
        this.timecardMapper = timecardMapper;
    }

    @Transactional
    public PunchResult punch(long employeeId, String type) {
        if (timecardMapper.countToday(employeeId, type) > 0) {
            throw new BusinessException("本日はすでに打刻済みです");
        }
        timecardMapper.insert(employeeId, type, LocalDateTime.now());
        return PunchResult.ok();
    }
}

勤怠の例2：残業申請の承認

上長が「承認」ボタンを押すと、POST /api/overtime/{id}/approve が呼ばれ、Controller → OvertimeService.approve(id) → Mapper の流れで「申請ステータスを承認済みに更新」「承認履歴を追加」「申請者に通知」が行われる、という形が一般的です。2つ以上の更新をまとめて行うので、Service に @Transactional が付きます（後述）。

各層の責務と、バグが入りやすい場所

層責務入りやすいバグ
ControllerURLの受付、入力の形式チェック、結果の返却パラメータ名の不一致で値が null、入力チェック漏れ、HTTPメソッドの間違い（GET/POST）
Service業務ルール、複数処理のまとめ、トランザクション条件分岐の漏れ（深夜をまたぐ打刻、締め後の修正）、@Transactional の付け忘れ、例外の握りつぶし
Mapper/RepositorySQLの実行のみWHERE 条件の誤り、NULL の扱い、日付の境界（< と <=）、タイムゾーン
DBデータの保存、制約一意制約違反、型の桁あふれ、インデックス不足による遅延
改修検討のときの目安

「計算結果がおかしい」なら Service か SQL、「画面で値が送られていない」なら Controller、「遅い」なら SQL とDB。ログのスタックトレースに出てくるクラス名の末尾（…Controller、…Service、…Mapper）を見るだけで、どの層で起きたかの見当がつきます。詳しくは 07 ログと障害調査 で扱います。

主要アノテーション辞典

アノテーションは「このクラス／メソッドをこう扱ってね」と Spring に伝える付箋です。全部覚える必要はありません。下の表を、コードを読むときの辞書として使ってください。

アノテーション意味例
@SpringBootApplication起動クラスの目印。自動設定・コンポーネントスキャン・設定クラスの3つをまとめたもの。このクラスのパッケージ以下がスキャン対象KintaiApplication

@PathVariableURLの一部 {id} を引数で受け取る/api/overtime/123 の 123
@RequestParamクエリ文字列やフォームの値を受け取る?month=2026-10 の month
@RequestBodyリクエスト本文の JSON をオブジェクトに変換して受け取る打刻APIの PunchRequest

application.properties / application.yml

DB の接続先やログの細かさなど、環境によって変わる値はコードではなく設定ファイルに書きます。場所は通常 src/main/resources/ です。.properties と .yml は書き方が違うだけで、中身は同じです。

application.properties（一般的な例）
# DB接続（値はダミー）
spring.datasource.url=jdbc:postgresql://localhost:5432/kintai
spring.datasource.username=kintai_app
spring.datasource.password=********

# 使うプロファイル（環境の切り替え）
spring.profiles.active=local

# ログ設定
logging.level.root=INFO
logging.level.com.example.kintai=DEBUG
logging.file.name=logs/kintai.log

# 組み込みTomcatのポート
server.port=8080
application.yml（同じ内容を YAML で）
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/kintai
    username: kintai_app
  profiles:
    active: local
logging:
  level:
    com.example.kintai: DEBUG

YAML はインデント（字下げ）で階層を表します。スペースの数がずれると読み込めないので、タブではなくスペースを使います。

プロファイル：環境ごとの切り替え

spring.profiles.active=local のとき、Spring は application.properties に加えて application-local.properties を読み、同じキーは後者で上書きします。本番は application-prod.properties、検証は application-staging.properties のように分けるのが一般的です。プロファイルは起動時の引数 --spring.profiles.active=prod や環境変数 SPRING_PROFILES_ACTIVE でも指定できます。

「ローカルでは動くのに本番で動かない」の典型

プロファイルごとに設定ファイルが違うため、DB 接続先やタイムアウト値が環境で異なります。障害調査では「本番はどのプロファイルで起動しているか」「その設定ファイルはどこにあるか（WAR の中か、サーバー上の外部ファイルか）」を最初に確かめます。

DBアクセス方式：JPA / MyBatis / JdbcTemplate

Java から DB を操作する方法は複数あり、現場によって使っているものが違います。どれを使っているかで「SQLがどこに書いてあるか」が変わるので、最初に見分けておくと調査が速くなります。

JPA / Hibernate

@Entity を付けたクラスとテーブルを対応させ、SQL を書かずに repository.save(emp) のように操作する。SQL は Hibernate が自動生成するので、ログで確認する。

MyBatis

SQL を自分で書き、Mapper XML（例：TimecardMapper.xml）に置く。Java 側は @Mapper 付きのインターフェースだけ。業務システムで非常に多い。

JdbcTemplate

Java のコードの中に SQL 文字列を直接書き、jdbcTemplate.query(...) で実行する。小さな処理や古いコードで見かける。

MyBatis：Mapper インターフェースと XML の対応
// TimecardMapper.java
@Mapper
public interface TimecardMapper {
    int countToday(@Param("employeeId") long employeeId, @Param("type") String type);
}

<!-- resources/mapper/TimecardMapper.xml -->
<mapper namespace="com.example.kintai.mapper.TimecardMapper">
  <select id="countToday" resultType="int">
    SELECT COUNT(*) FROM timecard
     WHERE employee_id = #{employeeId}
       AND type = #{type}
       AND punch_at >= CURRENT_DATE
  </select>
</mapper>

XML の namespace がインターフェースの完全な名前、id がメソッド名と一致することで結びつきます。#{employeeId} は値を安全に埋め込む書き方です（${...} は文字列をそのまま埋め込むので SQL インジェクションの危険があります）。

@Transactional とロールバック

残業申請の承認では「申請ステータスを承認済みにする」「承認履歴を追加する」の2つの更新があります。1つ目だけ成功して2つ目で失敗したら、「承認済みなのに履歴がない」という中途半端なデータが残ります。これを防ぐのがトランザクションで、@Transactional を付けたメソッドの中の更新は全部成功するか、全部なかったことになるかのどちらかになります。

@Service
public class OvertimeService {
    @Transactional
    public void approve(long requestId, long approverId) {
        overtimeMapper.updateStatus(requestId, "APPROVED");   // ①
        approvalHistoryMapper.insert(requestId, approverId);    // ②ここで例外 → ①も取り消し
    }
}

知っておくべき3つの落とし穴

  • チェック例外ではロールバックしない：標準では RuntimeException とその子（と Error）のときだけロールバックします。IOException などのチェック例外でも戻したいときは @Transactional(rollbackFor = Exception.class) と書きます。
  • 例外を catch して握りつぶすとロールバックされない：メソッドの中で try { ... } catch (Exception e) { log.error(...); } として外に投げないと、Spring は「正常終了」と判断してコミットします。
  • 同じクラス内からの呼び出しでは効かない：Spring は Bean を包む「代理（プロキシ）」を通してトランザクションを開始します。同じクラスの中で this.approve() のように直接呼ぶとプロキシを通らず、@Transactional が無視されます。

起動の流れ

Spring Boot アプリが起動するとき、内部では次の順番で処理が進みます。起動ログを読むときの地図になります。

① main メソッド@SpringBootApplication の付いたクラス
② SpringApplication.run設定ファイルとプロファイルを読む
③ Bean 生成スキャン → 自動設定 → 依存を注入
④ Tomcat 起動ポート 8080 で待ち受け開始
@SpringBootApplication
public class KintaiApplication {
    public static void main(String[] args) {
        SpringApplication.run(KintaiApplication.class, args);
    }
}
起動ログの例（抜粋・一般的な形）
:: Spring Boot ::                (v3.x.x)
INFO  c.e.kintai.KintaiApplication : The following 1 profile is active: "local"
INFO  o.s.b.w.e.tomcat.TomcatWebServer : Tomcat initialized with port 8080 (http)
INFO  o.s.b.w.e.tomcat.TomcatWebServer : Tomcat started on port 8080 (http) with context path '/'
INFO  c.e.kintai.KintaiApplication : Started KintaiApplication in 6.2 seconds

③の途中で失敗すると、UnsatisfiedDependencyException（注入したい Bean が見つからない）や、DB に接続できないエラーで起動が止まります。エラーメッセージは長いですが、一番下の Caused by: が本当の原因であることが多いです。

WAR として外部の Tomcat にデプロイする場合

勤怠システムのように Apache ＋ Tomcat の構成では、組み込み Tomcat を使わず、アプリを WAR ファイルにして、サーバーにインストールされた Tomcat の webapps に配置することがあります。この場合、起動クラスは SpringBootServletInitializer を継承し、pom.xml の <packaging> が war になっています。main メソッドではなく Tomcat がアプリを呼び出して起動します（ここでもハリウッドの原則です）。

JAR（組み込みTomcat）

java -jar kintai.jar で起動。Tomcat はアプリの中に入っている。ログはアプリの設定どおり。

WAR（外部Tomcat）

Tomcat の webapps に置く。Tomcat 側の catalina.out などにもログが出る。Tomcat のバージョンも確認が必要。

自分の現場がどちらかは、pom.xml の <packaging> と、本番サーバーに Tomcat が別途インストールされているかで判断できます。全体の構成は 02 システムの全体像 も参照してください。

現場コードを読む手順

いきなり全部を読もうとすると挫折します。1つの機能（たとえば「残業申請の承認」）を選び、入口から出口まで1本の線をたどります。

  1. pom.xml を見るSpring Boot のバージョン、<packaging>（jar/war）、DBアクセス方式（JPA/MyBatis）を確認する。
  2. 起動クラスを探す@SpringBootApplication で全文検索。そのパッケージ構成（controller / service / mapper など）を眺める。
  3. 設定ファイルを読むapplication*.properties / *.yml のプロファイルと DB 接続先を確認する。
  4. 入口の URL を探す画面の操作で呼ばれる URL をブラウザの開発者ツール（Network タブ）で確認し、その文字列でコントローラーを検索する。
  5. Service へ進むController が呼んでいる Service のメソッドへジャンプ（IDE で Ctrl+クリック／F3）。業務ルールと @Transactional を確認する。
  6. SQL にたどり着くMapper のメソッド名で XML を検索し、実際の SQL を読む。

練習問題

Q1. Spring Boot の Controller のメソッドを、自分のコードのどこからも呼んでいないのに動くのはなぜですか？

フレームワークである Spring が、URL とメソッドの対応（@GetMapping など）を起動時に覚えておき、リクエストが来たときに呼び出すからです。「呼ぶのではなく呼ばれる」ハリウッドの原則です。

Q2. OvertimeService の中で OvertimeMapper mapper = new OvertimeMapperImpl(); と書くのは何が問題ですか？

コンテナが管理する Bean ではなくなるため、DB 接続などの設定が注入されず動かない（または null になる）可能性があります。また差し替えやテストが難しくなります。コンストラクタで受け取る（DI）形にします。

Q3. 月次締め処理で「勤怠を確定済みに更新」「締め履歴を追加」の2つを行います。履歴追加で SQLException 系のエラー（Spring では DataAccessException という RuntimeException に変換される）が起きたとき、@Transactional が付いていれば1つ目の更新はどうなりますか？

ロールバックされ、1つ目の更新も取り消されます。ただし、メソッド内で例外を catch して外に投げなかった場合はコミットされてしまう点に注意します。

Q4. 自分の現場が MyBatis かどうかを、5分で確かめる方法を2つ挙げてください。

例：pom.xml に mybatis-spring-boot-starter があるか見る／ソース全体で @Mapper を検索する／resources 配下に <mapper namespace= を含む XML があるか探す。

用語まとめ

Spring Framework
Java で業務アプリを作るためのフレームワーク。DI が中心。
Spring Boot
Spring を自動設定と組み込みサーバーで、すぐ動かせるようにしたもの。
フレームワーク
処理の枠組み。自分のコードは決まった場所に書き、フレームワークから呼ばれる。
DI（依存性注入）
クラスが必要とする部品を、外から（コンテナから）渡してもらう仕組み。
IoC（制御の反転）
部品の生成や呼び出しの主導権がフレームワーク側にあること。
IoC コンテナ
Bean を作り、保持し、注入する入れ物。ApplicationContext とも。
Bean
コンテナが管理しているオブジェクト。
アノテーション
@ で始まる付箋。クラスやメソッドの扱い方を Spring に伝える。
プロファイル
local / prod など環境ごとの設定の切り替え単位。
トランザクション
複数のDB更新を「全部成功か、全部取り消しか」にまとめる単位。
ロールバック
トランザクション内の更新を取り消すこと。逆はコミット。
Mapper
MyBatis で SQL とメソッドを結びつけるインターフェース（＋XML）。
WAR / JAR
アプリをまとめたファイル形式。WAR は外部Tomcat用、JAR は java -jar で単独起動。
