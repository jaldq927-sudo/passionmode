CHAPTER 10 ・ 学び方

AIと一緒に強くなる

AIで問題は解決できているのに、自分の力になっている気がしない。その不安を、AIの使い方を少し変えることで「学び」に変える章です。プロンプト例、習慣の仕組み、間違いの見抜き方、情報の扱い方をまとめます。

  • 機密情報・個人情報を守る使い方

「解決できているのに不安」の正体

ログの調査も、SQLも、改修の検討も、AIに聞けば答えが出る。それで仕事は回っている。でも、先輩に「なんでそうなるの？」と聞かれると答えられない。同じようなエラーが来ると、また最初からAIに聞いている。

この不安は、とても健全な感覚です。なぜなら、それは「答えは手に入ったが、理解は手に入っていない」という事実を正しく感じ取っているからです。

理解が身につかない理由はシンプルで、頭を使う部分をまるごとAIに任せているからです。人は「思い出そうとする」「説明しようとする」「間違えて直す」ときに一番よく覚えます。AIの回答をコピーして貼るだけだと、そのどれも起きません。

だからといって、AIを使うのをやめる必要はありません。むしろAIは、24時間いつでも何度でも質問に付き合ってくれる、ものすごく我慢強い先生にもなれます。違いを生むのは使い方です。この章では、同じAIを「答えの自販機」から「自分専用の家庭教師」に変える方法を扱います。

たとえ話：カーナビと地図

カーナビだけで運転毎日同じ道を走っても、ナビの指示どおりに曲がるだけなので道を覚えない。ナビが止まると、どこにいるかも分からない。
≠
地図を見ながらナビも使う「今どの辺で、なぜこの道か」を意識しながら走る。数回で道を覚え、ナビが間違えたときにも気づける。

AIはカーナビのようなものです。便利で速く、ほとんどの場合は正しい。でも、ナビの指示に従うだけでは道は覚えられません。ナビが工事中の道を案内してきたとき、地図を知っている人だけが「この道は今通れない」と気づけます。

このガイドの他の章（システムの全体像、Spring Boot、SQLなど）は「地図」です。この章は、カーナビ（AI）を見ながら地図を育てる方法です。

丸投げと、学びになる使い方の違い

丸投げ（答えをもらって送るだけ）
  • エラーログを貼って「直して」
  • 出てきたSQLをそのまま実行
  • 動いたら次の仕事へ
  • 同じ種類の問題で、また最初から聞く
  • 先輩に聞かれると「AIがそう言っていたので」

残るもの：解決した事実だけ

学びになる使い方
  • まず自分で仮説を立ててから聞く
  • 答えの前に「考え方」を聞く
  • 1行ずつ意味を説明してもらう
  • 自分の言葉で要約し、AIに採点してもらう
  • テスト環境で動かして確かめる
  • ノートに3行残す

残るもの：解決＋理解＋次に使える知識

学びになる使い方は、丸投げより時間がかかります。目安として、1つの問題にプラス10〜15分。毎回は無理でも、1日1件だけでもこのやり方をすると、1か月で20件以上の「自分で説明できること」が増えます。

図1 イメージ図：解決の数は同じでも、理解の積み上がり方が違う（実測ではなく概念図）

学びに変えるプロンプト例

そのままコピーして使える形にしました。自分の状況に合わせて言葉を変えてください。共通するコツは、AIに「答え」ではなく「自分が理解するための手伝い」を頼むことです。

1. 答えの前に考え方を聞く

このエラーの直し方を、すぐに答えないでください。
まず、原因を探すときにどういう順番で考えればよいかを説明してください。
そのあと、私が自分で原因を予想するので、ヒントを1つずつください。

2. 1行ずつの意味を聞く

次のSQLを1行ずつ、何をしているか説明してください。
特に JOIN と GROUP BY の部分は、どんな表がどう変わるかを
小さな例（社員3人・3日分の打刻）で見せてください。

SELECT e.dept_cd, SUM(a.overtime_min)
  FROM t_attendance a
  JOIN m_employee e ON e.emp_no = a.emp_no
 WHERE a.work_date BETWEEN '2026-10-01' AND '2026-10-31'
 GROUP BY e.dept_cd;

3. 初心者向けにたとえで

Spring Boot の DI（依存性の注入）を、
勤怠システムの開発をしている新人向けに、身近なたとえで説明してください。
たとえのあとに、そのたとえが当てはまらない点も1つ教えてください。

「たとえが当てはまらない点」まで聞くと、たとえを本物と勘違いするのを防げます。

4. 私の理解をチェックして（自分で説明 → AIが採点）

Tomcat と Apache の役割の違いを、私の理解で説明します。
間違い・足りない点・あいまいな点を指摘して、100点満点で採点してください。
正解をすぐ全部書かず、まず指摘だけしてください。

私の説明：
Apache は外からのリクエストを最初に受けて、静的ファイルを返したり
Tomcat に転送したりする。Tomcat は Java のアプリを動かす場所で……

これがいちばん効果の高い使い方です。説明しようとすると、「分かったつもり」だった部分がはっきりします。

5. わざと間違いを含めて出題して

PostgreSQL の UPDATE 文を5つ出題してください。
そのうち2つには、本番で事故になる間違い（WHERE 漏れなど）を
わざと含めてください。どれが間違いか、私が当てます。
答え合わせは私が回答してからにしてください。

6. なぜ他の方法ではないのか

あなたが提案した「サブクエリで最新の打刻を取る方法」について、
なぜ window 関数や GROUP BY ではなくその方法なのか、
それぞれの長所と短所を比べてください。

7. その他の便利な型

前提を出させる

「この回答で、あなたが仮定していることを全部挙げて」

確かめ方を聞く

「この回答が正しいか、私がテスト環境で確かめる方法を教えて」

公式情報への道案内

「この設定について、公式ドキュメントのどの章を読めばいい？」（URLは自分で開いて確認）

理解度に合わせる

「私はJavaのクラスとメソッドは分かるが、アノテーションは分からない。その前提で説明して」

復習クイズ

「今日の会話の内容から、明日の朝に解く復習問題を3問作って」

先輩への質問づくり

「この件で、社内の先輩に確認すべきことを3つに絞って」

質問する前に、自分で3つ書いておく

どのプロンプトを使う場合でも、送信する前に次の3つをメモ帳に書いてから聞くと、学びの量が大きく変わります。

  1. 自分の予想：「たぶんDBの接続設定が原因」など、外れてもいいので一言。
  2. 分かっていること・分からないこと：「エラーは朝9時だけ出る。原因の場所は分からない」。
  3. 知りたいことのレベル：「直し方だけ」ではなく「なぜ起きたかも理解したい」。

予想を先に書くと、AIの答えを読んだときに「当たった」「ここが違った」という比較が生まれます。この比較こそが記憶に残る部分です。先輩に相談するときにもそのまま使える形なので、11 伝える技術の練習にもなります。

3回ルール：受け取る → 要約する → 動かす

プロンプトを工夫しても、受け取ったあとに何もしなければ学びは残りません。そこで、AIの回答を使うときは必ず次の3回、頭を通すことにします。

図2 3回ルール：AIの回答を3回、自分の頭に通してからノートに残す

習慣にするための仕組み

  • きっかけを決める：「AIの回答をコピーする前に」と決めておく。コピーのたびに「要約したか？」と自分に聞く。
  • 小さく始める：最初は1日1件。うまくいったら増やす。
  • 見える化する：ノートの日付が並んでいくと、続けている実感が持てます。
  • 完璧を求めない：忙しい日は3回目（動かす）だけでもOK。ゼロの日を減らすことが大事です。
「予想してから動かす」がポイント

SQLを実行する前に「たぶん3件返ってくる」と予想を一言書いてから実行します。当たれば理解の確認になり、外れれば「なぜ違ったか」が最高の教材になります。動画を見るだけの学習と違い、自分の頭と手で予想→確認をするので記憶に残ります。

AIの間違いに気づく方法

AIはもっともらしい文章を作るのが得意ですが、事実を保証してはいません。特に次のような間違いはよくあります。

間違いの種類例気づき方
存在しないメソッド・設定Spring Bootの設定キーをそれらしく作る、ライブラリにないメソッドを使う公式ドキュメントで検索。IDEで補完に出てくるか、コンパイルが通るか
バージョン違い古いSpring BootやJavaの書き方、PostgreSQLの別バージョンの関数自社のバージョンを伝える。pom.xml や SELECT version(); で確認
自社の構造を勝手に想像テーブル名・カラム名・クラス名を推測で書くgrepやDBのテーブル一覧で実在を確認
業務ルールの誤解端数処理、締めの扱い、深夜の定義を一般論で書く就業規則・仕様書・先輩に確認
危険な操作WHERE のない UPDATE、本番で DROP実行前にSELECTで件数確認。テスト環境で試す
自信満々の言い切り「必ず〜です」「これで解決します」「確実ですか？根拠は？」と聞き返す。実行で確かめる

図3 AIの回答は「実行」「公式」「自社の実物」のどれかで裏を取ってから使う

実例：AIのSQLを確かめる流れ

たとえばAIに「10月の部署別残業時間を出すSQL」を作ってもらったとします。そのまま実行する前に、次の順番で確かめます。

  • テーブル名・カラム名の実在：\d t_attendance（psql）やDBツールのテーブル定義で、overtime_min のような列が本当にあるか確認します。
  • 件数の予想：部署が12あるなら、結果は12行前後のはず。0行や1000行なら条件かJOINがおかしいと分かります。
  • 小さく手計算：社員1人・1日分だけに絞って実行し、画面に表示される残業時間と一致するか比べます。
  • 境界の確認：BETWEEN '2026-10-01' AND '2026-10-31' で、日付型か日時型かによって31日分が漏れないかを確かめます。

この4つを習慣にすると、AIのSQLを「信じる」のではなく「検証して使う」状態になります。最初は面倒でも、2〜3回やると数分でできるようになります。

ログ調査でAIを使うときも同じです。AIが「原因はこれです」と言っても、07 ログと障害調査の手順で、ログの該当行・時刻・再現で裏を取ってから報告しましょう。

機密情報・個人情報の扱い

勤怠・申請システムは、社員の氏名、社員番号、勤務時間、住所（通勤経路）、家族情報（結婚・扶養）など、個人情報のかたまりです。AIに貼り付ける前に、必ず次を確認してください。

AIに出してはいけないもの（原則）
  • 顧客名・取引先名・プロジェクトの非公開情報
  • 社員番号・氏名・住所・メールアドレス・電話番号
  • 実データ（打刻データ、申請内容、給与額）
  • パスワード、APIキー、接続文字列、サーバーのIPアドレスや内部URL

使う前に確認すること

  1. 社内ルールを確認する使ってよいAIサービス、入力してよい情報の範囲は会社・顧客との契約で決まっています。分からなければ上司に確認します。この章の内容より社内ルールが優先です。
  2. マスキングする貼る前に、固有の情報をダミーに置き換えます。
  3. 最小限にするファイル全体ではなく、質問に必要な部分だけを貼ります。
  4. 貼った後に見直すログの途中に氏名やメールアドレスが混ざっていないか、送信前にもう一度見ます。

マスキングの例（ログ）

# 変更前（そのまま貼ってはいけない）
2026-10-15 09:02:11 ERROR [CommuteService] update failed: emp_no=A102938 name=山田太郎
  customer=株式会社○○商事 url=jdbc:postgresql://10.0.12.5:5432/kintai

# 変更後（ダミーに置き換え）
2026-10-15 09:02:11 ERROR [CommuteService] update failed: emp_no=EMP001 name=社員A
  customer=顧客X url=jdbc:postgresql://DBHOST:5432/kintai
テーブル名・クラス名は？

テーブル名や業務ロジックそのものも、顧客によっては機密扱いのことがあります。「どこまでならOKか」は人によって判断がぶれやすいので、自己判断せず社内ルールを確認してください。

学習ノートの付け方

ノートは、未来の自分のための「地図」です。きれいに書く必要はありません。続けられる形が一番です。テキストファイル、OneNote、社内で許可されたツールなど、すぐ開ける場所に置きます（個人情報や顧客情報は書かない）。

3つのページを作る

今日わかったこと（3行）

毎日、終業前に3行だけ。「何があったか」「何がわかったか」「次に試すこと」。

用語集

知らない言葉が出たら1行で追加。「Bean：Springが管理するオブジェクト」。自分の言葉で書き直すのがコツ。

エラー集

出会ったエラーメッセージ、原因、直し方、確かめ方。2回目に同じエラーが出たとき、AIより先にここを見る。

ノートの例（テキストファイル）

## 2026-11-02
[今日わかったこと]
- 通勤費申請XMLの #{transport} は画面項目 id="transport" の値が入る
- CDATA の中なら SQL の < をそのまま書ける。外だと XML エラー
- 次：確定SQL が 0 件更新のとき、ログに何が出るか見る

[用語]
- バインド変数：SQL の値の差し込み口。#{} や ? で書く

[エラー集]
- エラー：parser error : StartTag: invalid element name
  原因：CDATA の外で < を使った
  直し方：CDATA で囲む or &lt; に置換
  確かめ方：xmllint --noout ファイル名

「AIに作らせたものを自分で説明できるか」チェック

AIに作ってもらったSQL、コード、調査結果を提出・実行する前に、次のチェックをします。全部に答えられなくても大丈夫です。答えられなかった項目が、次に学ぶポイントです。

よくあるつまずき

つまずき

「学びになる使い方」を全部やろうとして疲れ、3日でやめてしまった。

対策

1日1件、3行ノートだけから始める。忙しい日は「動かして確かめる」だけでも合格にする。

つまずき

AIの説明を読んで「分かった気」になったが、翌日には説明できない。

対策

読んだ直後に自分の言葉で要約し、AIに採点してもらう。翌朝に復習クイズを解く。

つまずき

AIの答えが自社の環境で動かず、何度も聞き直してぐるぐる回る。

対策

バージョン・構成・実際のエラー全文（マスキング済み）を伝える。3往復で解決しなければ、先輩に相談する（そのときAIとのやり取りの要点を整理しておくと話が早い）。

つまずき

動画やAIの解説を眺める時間ばかり増え、手を動かしていない。

対策

見る時間と同じだけ、テスト環境で実行する時間をとる。「予想→実行→比較」を1回やってから次の動画へ。

練習問題

Q1. 次のプロンプトを「学びになる使い方」に書き換えてください。「このエラー直して（ログを貼る）」

例：「このエラーの原因を探す考え方を、答えを言う前に順番に説明してください。私の予想は、DB接続の設定ミスです。その予想が合っているか、確かめる方法も教えてください。（ログは社員番号・ホスト名をマスキング済み）」。考え方を先に聞く、自分の仮説を添える、確かめ方を聞く、マスキングする、の4点が入っていれば良いです。

Q2. AIが「application.properties に spring.kintai.auto-close=true を追加すれば締めが自動化されます」と回答しました。どう対応しますか？

この設定キーが存在するかを疑います。spring. で始まるキーはSpring Bootの公式ドキュメントに載っているはずなので、まず公式で検索します。業務固有の「締め」の機能がSpring Boot標準の設定にあるとは考えにくく、AIが作った架空の設定である可能性が高いです。自社のソースをgrepして、そのキーを読んでいるコードがあるかも確認します。

Q3. ログをAIに貼る前に、マスキングすべき項目を4つ挙げてください。

社員番号、氏名、顧客名（会社名）、サーバーのIPアドレスや内部ホスト名。ほかにメールアドレス、住所、パスワードや接続情報なども対象です。どこまで必要かは社内ルールを確認します。
